# M18.10 Core Hot Path Optimization

## 結果

- 開始HEAD: `8d5d3390492b5879ba22608b7894f595ce2024a5`
- 判定: **製品最適化は不採用。** Core CPUの改善を再現できず、retained heapの減少案は全Consumer bundleを増加させ、`index-full`の既存budgetも超えた。
- 公開API、Runtime、bundle budgetは変更していない。

## Profile

Node `v24.21.0`、Windows x64、AMD Ryzen 7 PRO 6850Uで、`pnpm build:runtime`後に`benchmarks/core.mjs`をCPU profileした。profileは1 warmup / 2 samples、各case 300,000 operation、raw Alien Signals・RFSG・Preact adapterを含む。プロファイルは診断用の一回計測であり、速度の比較値としては使用していない。

RFSG側の上位sampled frameは`attachProtocol` 1,553 samples、GC 730、`registerHelperBrand` 487、`makeNode` 268、`updateComputed` 136、`readComputed` 82、`runEffect` 55だった。生成経路ではnode、brand descriptor、interop getterの初期化とGCが目立つ。これらのsample数はCPU samplerの観測であり、関数ごとの正確な実行時間や割当量を示さない。

Core graphは公開`signal`/`computed`に加え、object identity、`Object.is`更新、effect ownership、cross-copy interop、speculative renderのrevisionを維持する。`renderRevision`は従来すべてのnodeで初期化される。M14のbrand descriptor共有PoCは既にheap差が小さく、CPUが一貫して改善せず、gzipも増えたため不採用とされている。同じdescriptor案は再試行していない。

## 検証した候補

Core-only RuntimeでRender Adapterがまだない間、nodeの`renderRevision`を保持せず、Render Adapter接続後に初めてdependencyをcaptureするときにrevisionを作る案を試した。Render Adapterが既に接続されたRuntimeでは従来どおりnode生成時にrevisionを初期化する。これならcore-only Consumerが作るnodeからrender bookkeepingのslotを省ける。

初期PoCは、Render Adapter有無にかかわらずrevisionを遅延させたため、内部テストが期待するrevisionの進行を壊した。revisionのeager契約を持つReact Runtimeでは従来の初期化を保ち、Core-onlyでのみ遅延する形へ修正した。候補状態で`tests/reactive-runtime.test.ts`は54/54 pass、`pnpm typecheck:runtime`もpassした。広い複数fileの初回実行では初期PoCのrevision assertion failureに加え、Vitest worker起動timeoutが発生したため、その結果を最終候補の全体回帰としては扱っていない。候補は最終的に不採用とし、製品ソースと追加テストはすべて開始HEADへ戻した。

## CPU比較

baselineと候補を別worktreeでbuildし、同じNode/依存/fixtureを使用した。各variantは独立processで3 warmup、9 samples、300,000 operation。baseline/candidateの順で3 roundを交互に実行した。全raw sampleは[paired benchmark JSONL](m18.10-core-paired.jsonl)。値は`benchmarks/core.mjs`のRFSG adapterから得たroundごとのmedian秒を使い、candidate / baselineで算出した。

| Case | paired median比 | 3 roundの範囲 |
|---|---:|---:|
| signal/read | 1.506 | 1.214–2.658 |
| signal/write | 1.841 | 0.783–1.938 |
| signal/observed-write | 1.233 | 0.541–2.149 |
| computed/create | 1.077 | 0.674–1.131 |
| computed/read | 1.438 | 0.745–1.714 |
| computed/update-and-read | 1.149 | 0.719–2.111 |
| batch/two-observed-writes | 0.677 | 0.380–1.982 |

同一process内のp25–p75も広く、Alien/Preactの対照値もround間で数倍動いた。測定環境の大きな変動を制御できておらず、候補が速い/遅いとは結論できない。`computed/create`は3 round中1 roundだけcandidateが速く、改善としては不十分。CPU改善を主張しない。

## retained heapとbundle

heapは`--expose-gc`、独立processを交互に実行し、Core-only Runtimeに同数のobjectを作ってGC後に保持した。各processで50,000個を5回測り、3 processの中央値を比較した。Signalはread/writeなし、computedはgetterを評価しない生成・保持fixtureである。raw値は[retained heap JSONL](m18.10-retained-heap.jsonl)。

| Fixture | Baseline median / 50,000 | Candidate median / 50,000 | 差 | 減少率 |
|---|---:|---:|---:|---:|
| Signal | 8,805,632 B | 8,406,848 B | -398,784 B | -4.5% |
| un-evaluated computed | 14,804,656 B | 14,411,904 B | -392,752 B | -2.7% |

この差はCore-onlyの未追跡nodeでrevision slotを遅延した場合のGC後保持heapであり、実アプリ全体の削減量や評価済computed/React利用時の削減保証ではない。

同じexact size scriptで、baselineは全7 scenarioがbudget内。候補のgzip byteとbaselineとの差は次のとおり。

| Scenario | Baseline | Candidate | 差 |
|---|---:|---:|---:|
| signal-only | 6,249 B | 6,258 B | +9 B |
| core | 6,303 B | 6,312 B | +9 B |
| core+hooks | 10,021 B | 10,034 B | +13 B |
| deep | 14,588 B | 14,593 B | +5 B |
| index-full | 24,703 B | 24,720 B | +17 B |
| jsx-runtime | 13,552 B | 13,564 B | +12 B |
| utils | 9,719 B | 9,739 B | +20 B |

`index-full`の既存上限は24,704 Bで、候補は16 B超過した。budgetを引き上げず、不採用とした。signal-onlyやcoreのbundleも小さくならず、M18.9のCore-only bundle改善を維持できない。

## React correctnessと採否

遅延slotを実装する上では、Concurrent renderから見えるrevisionをread時に初期化し、capture後のwriteは従来どおり進行させる必要がある。また、既にRender Adapterが接続された内部Runtimeでは既存の初期revision契約を保持する必要があり、初期PoCの失敗でこの境界を確認した。修正後のfocused `reactive-runtime.test.ts`は54/54 passした。

ただし、bundle budget超過とCPU改善を確認できなかったため、Concurrent/SSR/cross-copyを含む全Runtime suiteを候補の資格判定として完走させる価値はないと判断し、candidateの全件qualificationは実施していない。M18.9の開始HEADではfull Runtime 915/915、packed Consumer、duplicate-copy、mixed-version、React SSR/Concurrent、既存size budgetがpass済み。M18.10はそれらの既存ソースを変更しない。

## 残課題と次の候補

- このhostではCPU benchmarkのnoiseが大きく、Core hot pathの速度改善を決められなかった。必要なら静かな専用runner、process負荷記録、適切な長時間warmupを持つ計測環境で再取得する。
- 次の性能調査は、profile上のcomputed生成/interop初期化を実Consumer workloadで再現し、CPUとallocationを別々に測る。小さなheap差だけでCore nodeの公開/内部shapeを変えない。
- M18.4のリストPoC、M14のshared brand descriptor PoCの不採用判断は維持する。
- 製品Runtime、API、version、package dependency、size budgetは変更なし。npm publish、Git tag、GitHub Release、Pages deployも行っていない。
