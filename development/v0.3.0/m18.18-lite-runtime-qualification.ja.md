# M18.18 — Lite JSX Runtime Hardening & Consumer Qualification

## 結論

LiteはSignal children専用の明示opt-in runtimeとして維持する。今回、Vite Fast Refresh、Vite / Webpack / Rspack、package copy間Signal、Fullとの同一tree共存、SSR/hydration、実Consumer bundleを確認した。製品runtimeの追加変更は不要だった。

Full Runtimeは既定であり、Liteは`react-fine-grained-signals/lite`を指定した場合だけ使われる。LiteはSignal children以外の直接bindingをサポートしない。Fullを同じ初期chunkに含めると、Lite単独のサイズ削減は保証されない。

## Fast Refresh

Vite development server上でLiteとFullのconsumer componentのソースを編集した。HMR後の表示、component stateとSignal値の保持、追加のSignal更新を確認した。StrictModeによる意図的な再実行を含み、編集によるrender countは各componentで4から6になった。signal updateでは対象readerの親component render countは増えなかった。

両componentをunmountした後にSignalを更新し、再mount後に最新値を表示することも確認した。browser console/page errorは0件。開発runtimeが`jsxDEV`経路を選ぶVite fixtureで実行した。これは単一Chromiumでの実操作で、全ブラウザやあらゆるHMR境界の網羅を意味しない。

## Bundler / package qualification

- Vite 8.3.4 + `@vitejs/plugin-react` 6.1.2、React 19.3.0: 独立Consumerのproduction buildとChromium操作を確認。
- Webpack: `jsxImportSource`からpackage exportsのLite JSX runtimeを解決し、production bundle内でSignal child更新を確認。
- Rspack: 同じConsumer構成でLite runtime解決、production bundleとSignal child更新を確認。
- TypeScript: root typecheck成功。M18.17のpacked Consumer smokeも再実行し、pack/install/typecheck/build/browser smoke成功。
- React Compiler: `tests/react-compiler.test.ts` 30 tests passed。Vite HMR fixtureではCompiler変換自体は有効化していないため、Compiler + 実Fast Refreshの組み合わせは未検証。
- classic `createElement` fallback、`jsxDEV`、package exports/types、Liteの非対応direct binding診断は、M18.17のfocused qualificationを前提とした。今回はbundler間の実際のSignal更新経路を追加確認した。

## Cross-copy / React lifecycle

`tests/cross-copy-smoke.mjs`が独立buildした3つのpackage copyを用い、copy B由来のSignalをcopy AのLite runtimeへ渡し、同一React treeのFull runtimeとも共存させる。StrictMode下のSignal更新、Lite readerの親が更新でre-renderしないこと、unmount後の購読解除、remount後の再購読、SSRからhydrationした後の更新を確認した。console/page errorなし。新しいinterop protocolや公開APIの変更は不要だった。

Concurrent abandoned renderや全てのFast Refresh edge caseを個別に網羅する新テストは追加していない。既存のRuntime/SSR/Suspense/StrictMode/Compiler focused suiteは再利用した。

## Consumer bundle size

同一Vite production fixture、同一React / package copy、初期chunkと遅延chunkを別々に集計した。値はJS chunkのexact bytesで、gzip/Brotliは同一スクリプトによる圧縮値。CSSやHTMLを含むサイト総量ではない。

| Fixture | 初期JS raw | gzip | Brotli | Full binding dispatcher |
| --- | ---: | ---: | ---: | --- |
| Lite only | 456,507 B | 137,095 B | 113,059 B | 含まれない |
| Full only | 468,769 B | 143,145 B | 118,268 B | 含む |
| Full + Lite同期import | 476,521 B | 143,688 B | 118,628 B | 含む |
| Lite + lazy Full（初期） | 458,707 B | 137,977 B | 113,838 B | 含まれない |
| lazy Full（遅延chunk） | 19,733 B | 7,055 B | 6,364 B | 含む |

このfixtureではLite-onlyはFull-onlyよりgzip 6,050 B小さい（Brotli 5,209 B小さい）。M18.17の小さなfixtureではgzip差6,029 Bだった。Full + Liteを同期importするとFull-only比でgzipが543 B増え、Lite-onlyより6,593 B増える。Fullを遅延すると初期chunkはLite-only比でgzip 882 B増え、Full分の7,055 Bはそのchunkを要求した後に転送される。

つまりLiteは、Fullを同じ初期読み込み経路に含めないConsumerでのみ約6 KB gzipの差を提供する。Full + Liteの同梱Consumerに同じ効果を約束しない。共通Core/React adapterのchunk重複はViteが単一initial chunkへまとめたため発生しなかった。Webpack/Rspackでは別々のbundler outputで、共通chunkの同条件比較はしていない。

## JSX construction cost

Production Vite bundleをChromiumで実行し、各条件12,000 JSX element constructionを行った。2回warm-up後、順序を交互にした10サンプルの中央値とmin–maxを記録した。React tree mount、DOM commit、paintを計測したものではない。

| Runtime / workload | Median | Range |
| --- | ---: | ---: |
| React JSX, plain | 15.6 ms | 13.9–24.2 ms |
| Full, plain | 19.4 ms | 18.0–34.8 ms |
| Lite, plain | 19.1 ms | 18.0–30.2 ms |
| Full, Signal child | 36.9 ms | 34.2–89.1 ms |
| Lite, Signal child | 36.5 ms | 32.6–61.2 ms |

LiteとFullの差は観測ばらつきより小さく、Liteのprops検査が通常JSXで明確な追加コストを生む根拠は得られなかった。一方でReact標準JSXとの差はこのmicrobenchmarkで見られるが、負荷変動が大きく、1 browser / 1 machineの測定から実Consumerの性能差とは結論しない。診断処理の正確性を変える最適化は行わない。

## 判断・残課題

Liteの明示opt-in、Signal children限定、Full既定という既存の設計を維持する。追加binding、Runtime variant、公開設定、製品コード修正は不要。bundle上の利点はLite単独読み込み経路でのみ示し、同期import構成では効果を約束しない。

全OS・全ブラウザでのHMR、Webpack/RspackのFast Refresh、React Compilerと実Fast Refresh同時使用、cross-copyの全SSR streaming経路は未確認。今回の目的に必要な未検証Vite/bundler/cross-copy経路は通過し、残課題を新たな互換性問題としては確認していない。

M18.18でLite Runtime qualificationを完了した。release freeze、npm publish、version/tag/release、Pages deployは行っていない。
