統合時に追加した判断:
- **R1はReactの内部に依存しない方式にした。** 直前のsiblingが開いたままにしたbare windowは閉じずに一時停止し、後で元に戻す。過剰に購読して再描画が1回増えることはあるが、stale renderにはならない。

## M17.6.1 — 追加指摘2件

### A. `for...in`変換の意味論

**再現**
- M17.6の`captureForIn`は、内側でnativeの`for...in`を最後まで回してkeyを集め、その後に各keyを`key in target`で確認していた。
- Proxy(prototypeもProxy)に対して、変換しない`for...in`とtrapのログを比較した。8つのloop形のうち7つでログが一致しなかった。
  - 2番目のkeyで`getOwnPropertyDescriptor`がthrowする場合: nativeは最初のkeyでbreakすれば例外にならない。helperは列挙を先に全部行うのでthrowした。
  - nativeが呼ばない`has` trapを、keyごとに呼んでいた。
  - nativeでは、`getOwnPropertyDescriptor`とprototypeの走査がloopの進行に合わせて遅延して行われる。helperでは開始時にすべて行われていた。loop中にpropertyを削除した場合も、trapの呼ばれる順序が違った。
- managed transformのReact実行テストで`signal(proxy)`に対して`for (k in box.value) { …; break; }`を実行すると、`Error: gOPD b`になった。

**修正**
- nativeの`for...in`をgenerator内で実行し、各`next()`/`return()`をcaptureする方式に変えた。`for...of`の`iterate`と同じ構造である。
- これにより、key順、継承key、順番が来る前に削除されたkey、break/continue/例外、trapの呼び出し順序とタイミングがnativeと一致する。

**テスト**
- runtime: 4つのloop形について、throwする場合としない場合のtrapログを、nativeとの完全一致で比較する(8ケース)。
- transform: `signal(proxy)`に対する`for...in`+`break`(`auto`/`all`)。DOMとtrapログがnativeの1回分の倍数になっていること、Signalを更新したときに再描画されることを確認する。

### B. `pureMethodNames`の誤判定

**再現**
- `import { extStore } from "./ext"`の`extStore.map()`などで、`map`、`filter`、`toString`、`join`、`valueOf`のどれでもSignalを更新した後もDOMが変わらなかった(5件すべて)。
- module内で定義したobject literalのmethodは、関数として解決できるため正しく動いた。

**修正**
- 組み込みと同じ名前のmethodを組み込みとみなすのは、選択した関数が所有するdataをreceiverにするときだけにした。対象は、parameter、literal、callの結果でない局所変数、React state(`useState`、`useReducer`など)、それらに組み込みmethodを適用した結果(`const visible = items.filter(...)`)である。
- import、module-level、`this`、ほかのcallが返した局所変数(custom Hookの結果)の同名methodは、ほかの未解決callと同じくcaptureする。

**影響**
- 既存のtransform出力のsnapshotは変わらなかった。
- examples(12ファイル)のcapture数は7件のままで変化しなかった。

## M17.6.2 — ローカル別名経由の追跡漏れ

開始基準: `217a3a688b01478d413884f51d539ae8c3bd0f0c`

**再現**
- M17.6.1の判定では、callの結果でない局所変数を、関数が所有するdataとみなしていた。そのため、importしたobjectに別名を付けると、組み込みと同名のmethodがcaptureされなかった。
- React実行テストで、`map`・`filter`・`toString`のそれぞれに対して次の6通りを確認し、`auto`/`all`の両modeで18件すべてstale renderを再現した。
  - `const localStore = extStore`
  - 2段階の別名
  - object property (`{ store: extStore }.store`)
  - 分割代入 (`const { store } = { store: extStore }`)
  - 配列要素 (`const [store] = [extStore]`)
  - 再代入した`let`
- 直接呼び出しは、M17.6.1の修正で正しく動いていた。条件式に入れる場合 (`cond ? extStore : null`) は、条件に含まれるSignal readによって式全体がcaptureされるため、もともと正しく動いていた。

**修正**
- 局所変数であることではなく、値の出所を証明できるかどうかで判定するようにした(`isOwnedData`)。
- 所有するdataとみなすもの:
  - 配列・文字列・テンプレート・数値のliteral
  - parameterとそのmember
  - `useState`などのstateの分割代入
  - それらに組み込みmethodを適用した結果
  - 両辺が所有するdataである条件式・論理式
  - 上記で初期化され、再代入されない局所変数
- object literalは、propertyに何でも入れられるため、所有するdataとはみなさない。証明できない場合は安全側に倒してcaptureする。

**テスト**
- React実行テスト18件(3 method × 6形、各`auto`/`all`)
- 出力形状テスト1件(`auto`/`all`)
  - 通常の`items.filter(Boolean)` → `visible.map(String).join(",")`、`title ?? "none"`、配列literalはcaptureされないこと
  - 別名・object property経由の呼び出しはcaptureされること
- 修正前は19件が失敗し、修正後はすべて通過した。

**影響**
- 既存のtransform出力snapshotは変化しなかった。
- examples(12ファイル)のcapture数は、`auto`で7件のまま、`all`で9件のままだった。
- `pnpm lint`、`pnpm typecheck`は成功した。
- `pnpm test:coverage`は、runtime 902件、transform 557件がすべて通過した。branch coverageは90.92%と91.06%である。
- Hookをcapture closureへ移さないことを確認するguardテストと、M17.6/M17.6.1の回帰テストも通過した。

**残る制約**
- parameterとして受け取ったobjectが組み込みと同名の独自methodを持ち、その中でSignalを読む場合は捕捉しない。propsの配列や文字列に対する通常の呼び出しで、不要なcaptureを増やさないための判断である。

## 未対応事項と既知の制約

- managed transformは静的解析で追跡する方式であり、v0.2.1のambient追跡より範囲が狭い。新たに見つかった形の追跡漏れは不具合として扱う。
- 次の場合、呼び出しの戻り値はaliasとして扱わない。
  - importした関数の呼び出し
  - 解決できない呼び出し
- generatorの展開がcaptureされない。
  - `[...gen()]`
  - `Array.from(gen())`
  - captureされるのは`for...of`だけである。
- 組み込み名の判定はreceiverの出所で行っている。parameterとして受け取ったobjectが、独自に組み込みと同名のmethodを持ち、その中でSignalを読む場合は捕捉できない(M17.6.2で、局所別名を経由する場合の漏れは解消した)。
- R1の方式では、siblingのbare windowが閉じるまで、後続componentのcaptureされないreadを過剰に購読することがある。
- J1とJ2の修正はjsdomでのみ確認した。Chromium用のテストを追加するにはexamplesの変更が必要なため、追加していない。
- 実行していない検証: React Compilerとの組み合わせ、selective hydration、Node 24のネイティブ`getOrInsert*`。
