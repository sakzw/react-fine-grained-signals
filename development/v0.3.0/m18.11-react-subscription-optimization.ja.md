# M18.11 React Subscription & Commit Optimization

## 結果

- 開始HEAD: `d1c6265eee957b7cab782cbd6f10fab3e92d01f4`
- fetch後の`origin/main`も同じHEADで、作業開始時に差分はなかった。
- 判定: **安定依存commitの一時allocation削減を採用。** Reactのrender/commit/DOM更新や購読意味論は変えず、依存集合が変わらないcommitで一時配列とSetの生成を避ける。
- Public API、Core、Managed Transform、package依存、size budget、versionは変更なし。

## 現行経路とPoC

`RenderStore.commit()`のcombined modeでは、毎回`desired.keys()`を配列化し、`filter()`した配列からSetを作り、そのSetをさらに配列化して既存集合と比較していた。200行が親state更新で再renderするConsumerでは、同じ依存集合を持つ200 componentのcommitごとに同じ比較処理が繰り返される。

PoCでは一回の走査でlocal dependency数とmembershipを既存Setに対して比較する。一致する場合はSetや配列を作らない。依存が増減・切り替わった場合だけ次のSetを作り、従来どおりcombined subscriptionを張り直す。per-readable、interop protocol、unsubscribe、render-attempt promote/settleの経路は変更していない。

安定集合の各commitで、従来作られていたキー配列、filter配列、Set、比較配列を避ける。これらの一時オブジェクトの正確なbyte数をheap profilerで測ったわけではない。コード経路から確実に省けるallocation数として評価した。

## Consumer workloadと計測条件

Windows x64、Node `v24.21.0`、React `19.3.0`、Chromium `156.0.8078.4`、AMD Ryzen 7 PRO 6850Uで、baselineとcandidateのdistを分けて測った。JSDOMの正確性・回数fixtureは200行、12更新、2 warmup、5 samples。Chromiumはproduction Vite bundleを作り、同じページ内にbaseline/candidateを載せ、各sampleで実行順を交互にした。A/B/Dは5更新×7 samples、Cは5更新または10更新×9 samples、いずれも3 warmup。

測定したworkload:

- **A Independent Signals:** 200行中1つだけ更新。
- **B Shared Signal Fan-out:** 1 Signalを200行で購読し、各更新で全行を確認。
- **C Stable Dependencies:** 親のReact stateを更新し、同じSignal依存を持つ200行が再render。
- **D Dynamic Dependencies:** computedが依存するSignalを条件で切り替える。

Browser計測は`flushSync`で1 updateごとにcommitし、更新処理時間、render回数、各行のlayout effect commit回数、DOM mutationを別々に記録した。React production buildでは`Profiler.onRender`が提供されないため、layout effect回数は**commitされた行component数**として扱い、root commit数とは呼ばない。heap APIはunmount後GC後も全試行でちょうど`10,000,000` bytesを返し、retained-heap差を比較できる精度ではなかった。

## 性能結果

JSDOMの別processによる単回baseline/candidate測定は以下。時間値は中央値、括弧内はp25–p75で、独立process間の比較なので方向性の参考に留める。

| Workload | Baseline | Candidate | Render/commit結果 |
| --- | ---: | ---: | --- |
| Independent | 24.0 ms (19.9–29.1) | 33.1 ms (25.4–43.6) | 対象leaf 12 render / commit、他199行は更新なし |
| Shared fan-out | 525.7 ms (503.1–597.9) | 471.0 ms (451.5–481.4) | 200行すべてが各12回render / commit |
| Stable dependencies | 703.5 ms (681.2–743.6) | 597.2 ms (534.6–746.1) | 親12 render、200行×12 render / commit |
| Dynamic dependencies | 19.4 ms (18.7–19.5) | 14.1 ms (11.7–16.3) | 切替対象leafのみ12 render / commit |

production Chromiumの同一ページpaired結果:

| Workload | Baseline median | Candidate median | Candidate / baseline paired median | p25–p75（baseline / candidate） |
| --- | ---: | ---: | ---: | ---: |
| Independent, 5更新 | 0.5 ms | 0.4 ms | 0.80 | 0.4–0.5 / 0.3–0.4 ms |
| Shared fan-out, 5更新 | 4.5 ms | 4.2 ms | 0.902 | 4.25–5.25 / 3.45–4.55 ms |
| Stable, 5更新 | 3.9 ms | 3.6 ms | 0.921 | 3.8–4.2 / 3.5–3.8 ms |
| Stable, 10更新 | 5.1 ms | 5.2 ms | 1.036 | 4.3–5.6 / 4.6–5.5 ms |
| Dynamic, 5更新 | 0.5 ms | 0.4 ms | 1.00 | 0.5–0.55 / 0.4–0.55 ms |

安定依存の5更新paired ratioは9 pairで`0.72–1.00`、10更新では`0.81–1.27`。5更新runのcandidate中央値は少し短かった一方、10更新runではほぼ同じで、IQRが重なった。独立・dynamicは1操作あたり1 ms未満で計時粒度に近い。従って、**ブラウザ処理時間の一貫した改善は確認できていない**。一方、全workloadでrender数、commitされたleaf数、DOM mutation数はbaselineとcandidateで一致し、console/page errorはなかった。A/B/Dのcandidate比にも大きな回帰は見られない。

まとめると、時間短縮は採用根拠にせず、stable dependency時に無条件に作っていたtemporary arrays/Setが消えることを採用理由とする。subscription作成回数はstable rerenderごとに増えず、追加testで`subscribeReadables`が初回の1回だけ呼ばれることを確認した。snapshot比較とsnapshot call数は今回変更・計測していない。

## 残課題

- production browserのwall-clock差はrun条件で反転し、統計的な速度向上は主張できない。確実に示せたのはstable commit経路の一時container生成削減とsubscription churnの不変性。
- allocation byte数、subscription create/dispose総数、snapshot call count、retained heapの精密比較は未計測。Chromium heap値は今回のretained比較に使えなかった。
- `index-full`のsize余裕が25–26 Bと小さい。以後のReact Adapter変更では同じexact size checkを続ける。
- snapshot dependency Mapの比較は次の候補として残すが、今回の計測で必要性を示せなかったため変更していない。
