# M17.7.1 — Synchronous execution boundary check

- 開始基準: `main` / `2469099968ba9bcda095fb27a96ab9c710c0f1a1`(M17.7終了時点)
- 対象: Promise executorとasync関数の同期部分の追跡判定に限定

## 結論

確認した懸念は2件とも実在した。

- **A. 名前付きのPromise executorがcaptureされなかった。** `function executor() { seen = count.value; }` + `new Promise(executor)`では、`count.value`を更新しても`auto`/`all`のどちらも再描画されなかった。
  - 原因: M17.7の`calledBackIsKnown()`は、局所関数を「本体を別の箇所で判定する既知の関数」として扱う。ところが、その本体判定は普通のcall(`items.filter(isBig)`)にしかなく、`new`式とhelper本体の中のcallには存在しなかった。つまり、calleeの「既知」判定と、渡す関数の本体解析が噛み合っていなかった。
  - inline executorは修正前から正しく動いていた(inline callbackの本体解析で判定される)。importしたexecutor、およびconstに入れたarrowのexecutorも同様に正しく動いていた。
- **B. async callbackのうち、一部の経路で同期部分を見ていなかった。**
  - inline callbackとして渡す場合(`items.some(async () => ...)`)は、async関数を一律に「同期readなし」として除外していた。
  - 名前付きasync関数の直接呼び出し、async IIFE、`forEach`へのasync callbackは、修正前から正しく動いていた(別の経路で本体を判定している)。

## 修正

- `namedArgumentMayRead()`を追加した。名前で渡した局所・module関数の本体判定を、普通のcall・`new`式・helper本体の中のcallで共通に行う。`calledBackIsKnown()`は「その関数がこのmoduleから見える」ことだけを判定し、本体の判定はこの関数が担う。
- async関数(generatorを除く)は、callに渡す関数として扱う場合も本体で判定する。最初の`await`までの部分はcall中に同期実行されるためである。
- M17.7で追加した「async IIFEは無条件にcapture」を、本体による判定に戻した。Signalを読まないasync IIFEはcaptureしない。
- 呼び出し結果をaliasとして扱う判定には、async関数を含めない。結果はPromiseであり、読んだ値ではないためである。
- Hookを呼ぶ関数は従来どおり対象外で、capture closureへは移さない。

## await後のread

- 最初の`await`以降のreadは、render中のcaptureが閉じた後にmicrotaskで実行される。そのため依存として記録されない。テストでは、await後だけで読むSignalを更新しても再描画回数が増えないことを確認した。
- async関数の本体はawait前後を区別せずに判定する。そのため、await後にしかSignalを読まないasync関数の呼び出しもcaptureされる。この場合captureは何も記録しないので、追加の再描画は起きない。

## 仕様として除外するもの

| ケース | 影響 | 回避方法 |
|---|---|---|
| 最初の`await`より後のread | render dependencyにならない。値が変わっても再描画されない(これは正しい挙動で、render後に行われる処理である) | 表示に使う値はawait前に読むか、`useSignalValue`/effectで購読する |
| `.then()`のcallback、`setTimeout`などで後から実行される処理の中のread | 同上 | 同上 |
| Hookを呼ぶexecutorやasync関数 | Hookをclosureへ移さないため、callごとcaptureしない(既存の警告対象) | Hookを別の文で呼ぶ |

## テスト

`packages/unplugin-react-fine-grained-signals/tests/react-execution.test.ts`の`M17.7.1: synchronous execution boundaries`(React 19 + jsdom、各`auto`/`all`)。

- Signal更新で再描画されることを確認する形(11件): 名前付きexecutor、constのexecutor、inline executor、importしたexecutor、helperが起動するexecutor、名前付きasync関数、constのasync arrow、async IIFE、`forEach`へのasync callback、`some`へのasync callback、名前で渡したasync callback
  - 修正前(`2469099`)に失敗したのは3件: 名前付きexecutor、helperが起動するexecutor、`some`へのasync callback。ほかは修正前から通過する対照ケース。
- await後のread: await後にだけ読むSignalを更新しても再描画回数が変わらないこと、await前のreadは更新されること。
- 意味論: executorの実行順序(`before,executor,failing,early,after`)、Promiseの結果(`fulfilled:1`)、executorが投げた例外がrejectになること(`TypeError`)、async関数のawait前の例外がrejectになること(`RangeError`)。
