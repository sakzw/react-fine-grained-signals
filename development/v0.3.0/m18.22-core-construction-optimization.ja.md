# M18.22 — Core Signal Construction & Allocation Optimization

## 判定

`makeNode`が各nodeを作るたびに受け取っていたkind別`fields`一時オブジェクトとspread mergeを取り除いた。50,000個を保持した際のGC後retained heapがSignal / readonly computed / writable computedのすべてで一貫して約8 B/object減少し、bundle budgetも維持した。CPU時間はprocess間の分布が大きく重なり、改善とは結論しない。Core node constructionの単純な変更であること、保持heapの差が独立processで再現したこと、契約テストが通ったことから、この1案を採用する。

## 基準とコード経路

- 開始HEAD: `8f884bed575c847191b9c411d50e8236c8654983`
- 作業時の開始branch: `main`、開始時worktreeはclean。
- `makeNode`はbase nodeを返した後、Signal / computed / effect / foreign bridgeの生成箇所でkind固有フィールドを設定する。
- 変更前は、各生成箇所で`Partial<RuntimeNode>`を作り、`makeNode`内でbase objectへspreadしていた。
- M14で導入済みのprotocol lazy materialization、`readableNodes` WeakMap、`READABLE_INTEROP_V1` identity、brand descriptorは変更していない。brand共有descriptorや`renderRevision`遅延も試していない。

## 実装

- `src/core/alien-derived-runtime-core.mts`: `makeNode(kind, flags)`をbase node生成に限定。source / computed / effect / child-effectへは生成直後に必要フィールドを設定。
- `src/core/foreign-readable-v1.mts`: external bridge nodeも同じ2段階生成に変更。
- `src/core/alien-derived-types.ts`: foreign adapterの内部callback型から未使用の`fields`引数を削除。
- 公開API、alien-signals backend、React adapter、interop protocol、tracking semanticsは変更していない。

## 測定方法

再実行用scriptは`m18.22-core-construction-bench.mjs`、profile要約scriptは`m18.22-heap-profile-summary.mjs`。baselineとcandidateは開始HEADと変更を適用した別worktreeでbuildし、同じnode/fixtureを使用した。CPU測定はNode `v24.21.0`、Windows x64、AMD Ryzen 7 PRO 6850U。各caseで3 warmup、9 sample、新規process、GC exposed。process単位にbaseline/candidateを交互順で直列実行し、同時benchmarkは行っていない。

Heap測定は各variantを新規processで実行し、GC後に50,000個を5回保持計測した。allocation profileはV8 sampling profilerを用いた補助確認で、Node startup・native allocationの影響が大きく、node一個あたりの一時allocation差の帰属には使えなかった。

測定JSONを同じdirectoryへ保存している。`m18.22-baseline*.json`、`m18.22-candidate-round*.json`、`m18.22-heap-*.json`、`m18.22-consumer-500-*.json`および`m18.22-allocation-*.json`がraw結果。profileの大きな`.heapprofile`生成物と重複する小規模consumer runは記録後削除した。

### Retained heap

各セルは独立したprocessのGC後中央値。単位は50,000 object全体のbyte。5回の反復値の中央値を使用。

| object | baseline pair 1 / 2 / 3 | candidate pair 1 / 2 / 3 | 差（各pair） | 差/object |
|---|---:|---:|---:|---:|
| Signal | 8,803,912 / 8,800,640 / 8,803,984 | 8,406,272 / 8,403,528 / 8,404,720 | -397,640 / -397,112 / -399,264 | 約7.94–7.99 B |
| getter-only computed | 14,803,096 / 14,801,248 / 14,801,320 | 14,403,872 / 14,401,336 / 14,401,336 | -399,224 / -399,912 / -399,984 | 約7.98–8.00 B |
| writable computed | 18,013,168 / 18,012,448 / 18,014,872 | 17,615,896 / 17,621,024 / 17,618,632 | -397,272 / -391,424 / -396,240 | 約7.83–7.94 B |

保持量の差は3 process pairにわたり同じ方向・ほぼ同じ大きさで再現した。個々のobjectの破棄後heapはGC・runtime揺れの範囲で分布が重なり、candidateに残留参照やcleanup不良がある証拠は見つからなかった。

### CPU・allocation・consumer

生成/破棄、生成/保持、readonly/writable computed生成、初回評価、cached read、依存Signal更新後の再評価、effect graph生成/破棄、cross-copy readable取得/subscribe/disposeを計測した。個々の測定のprocess中央値とp25–p75はCPU負荷の影響で大きく変動し、baseline/candidateの範囲が多く重複した。別process pairで逆転もあり、CPU短縮は主張しない。

Consumer workloadは500 computed + effectを構成し、各cycleでSignalを更新して結果を読み、最後に全subscriptionをdisposeし、その後effectが再実行されないことをassertした。3 process pair、各process 7 sampleの中央値(ms)は次の通り。

| pair | baseline | candidate |
|---|---:|---:|
| 1 | 86.715 | 86.774 |
| 2 | 102.458 | 84.754 |
| 3 | 126.630 | 79.759 |

各processのp25–p75は広く重複した。候補が更新・購読解除を大幅に悪化させる兆候はないが、CPU改善の証拠としては弱いため、数値差を性能向上と解釈しない。

V8 allocation samplingの15万Signal create/discardではbaseline 4,230,832 B、candidate 4,232,800 B（+1,968 B、約0.05%）と実質同じで、今回の一時allocation削減を直接検出できなかった。保持heapの差を一時allocation削減と同一視しない。

## 残課題と次の候補

今回明確に示せた利用者効果は、大量のnodeを同時保持する場合の約8 B/nodeのretained heap減少である。CPU改善やcreate/discard時の一時allocation減少は測定から確認できなかった。少数nodeのConsumerでは効果が小さく、性能保証ではない。

この計測により一時`fields` objectとspreadの費用は一部除去できた。Core性能調査を続ける場合も、次はprofileで確認できた異なるhot pathに限定し、WeakMap/protocol identity/brand semanticsやReact semanticsを変える案は別の再現可能な根拠がある場合だけ評価する。
