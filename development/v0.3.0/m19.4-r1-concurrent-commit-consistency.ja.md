# M19.4 — R1 Concurrent Commit Consistency

開始HEAD: `5d12240ba7a12e32123a909f060152b6b59e2bcb`

## 結果

独立レビューのR1（Concurrent Rendering中の一時的なmixed commit）を、各commitを記録するテストで再現し、根本原因を修正した。新機能、公開API、Adapterの全面再設計は追加していない。

| 項目 | 修正前 | 修正後 |
| --- | --- | --- |
| `useSignalTracking` transition mount + yield中write | `[["A0","B1","C1","D1"],["A1"]]` | `[["A1","B1","C1","D1"]]` |
| `useSignalTracking` computed経由のread | `[["A0","B1","C1","D1"],["A1"]]` | `[["A1","B1","C1","D1"]]` |
| `useDeepSignalValue` transition mount + yield中write | `[["A0","B1","C1","D1"],["A1"]]` | `[["A1","B1","C1","D1"]]` |
| 3種のHookを混在させたtree | `[["A0","B1","C1","D1"],["A1"]]` | `[["A1","B1","C1","D1"]]` |
| `useSignalValue`（比較対象） | 混在なし | 混在なし（変化なし） |
| update path（3種とも） | 混在なし | 混在なし（変化なし） |
| `useDeepSignalValue`のActivity reveal | `[0, 5]`（staleを1回commit） | `[5]` |

修正後は、yield中のwriteで不整合になったtransition renderをReactが破棄し、同期的に1回だけやり直す。renderは`A0 B1 C1 D1`（破棄）→`A1 B1 C1 D1`、commitは1回だけになる。

## 根本原因

Reactは非blocking laneのrenderで`useSyncExternalStore`を使ったfiberを記録し、render完了後・commit前に各`getSnapshot`を呼び直して、render時のsnapshotと比べる（store consistency check）。不一致ならblocking laneで同期的に再renderし、混在したtreeをcommitしない。`useSignalValue`は`getSnapshot`がSignalの現在値を返すため、このcheckで捕捉されていた。

- `useSignalTracking`系（`RenderStore`）: `getSnapshot`は`#version`を返し、`#version`は購読通知でしか進まない。購読はlayout commit時に作られるため、mount中のrenderではyield中にreadしたSignalが書き換わっても`#version`は動かず、consistency checkを素通りした。commit後の`settleRenderAttempt`は変化を検出して`#notify`するが、購読が未接続のためReactの購読後checkまで待ち、その間に混在commitが描画された。
- `useDeepSignalValue`（deep selector store）: selector結果のcacheを購読中のeffectだけが更新していたため、未購読（mount前、Activityで非表示中）の`getSnapshot`は古いcacheを返した。

## 修正

- `RenderStore.getSnapshot`は、そのstoreが最後に開始したrender attemptの依存がまだ現在かを確認し、古ければ`~#version`を返す。Reactのconsistency checkはそのrender passの完了時に実行され、commitされるrender passで各componentは1回だけrenderされる（Strict Modeや`use()`のreplayは次へ進む前にやり直す）ため、最新attemptが検査対象になる。commit後の変化は従来どおり購読と`#version`が報告する。関数の同一性はrender間で変わらないので、update renderでReactのstore bookkeepingは増えない。
- render runtimeに副作用のない`isRenderAttemptCurrent(attempt)`を追加した。Sourceのrevisionに加え、computedはrevisionが再評価時にしか進まないため、speculative entryは依存sourceで（既存の`isEntryCurrent`）、cleanでreadしたcomputedはまだcleanかで判定する。等値へ再評価されたcomputedは「変化あり」とみなし、余分なrenderを求めることはあっても変化を隠さない。
- deep selector storeは、未購読の間だけ`getSnapshot`でselectorを再評価し、Object.isで同じprimitiveなら既存の結果を維持する。store生成直後の最初の`getSnapshot`は生成時の結果を再利用する。購読中の挙動は変えていない。

Render中の副作用は追加していない（`getSnapshot`は購読やscheduleを行わない）。render attemptの分離、abandoned renderの扱い、SSRの`getServerSnapshot`は従来どおり。

## 回帰テスト

`tests/react-concurrent-commit-consistency.test.tsx`（14件）を追加した。act環境を無効にしてReactの実Schedulerで動かし、`A`のrender後に8 msのbusy waitでyieldさせ、そのyieldのmicrotaskでSignalへ書き込む。各componentのlayout effectをmicrotaskでcommitごとにまとめて記録し、各commit直後のDOMも記録する。

- mount: `useSignalTracking`、computed経由、`useDeepSignalValue`、3種混在、`useSignalValue`。全commitが単一値、最終DOM`1111`、writeが実際にrender途中で起きたこと（`A0`と`B1`）、render列が`A0 B1 C1 D1 A1 B1 C1 D1`でcommitが1回であることを確認する。
- update: 3種とも全commitが単一値で最終DOMが`1111`。
- writeなしのtransition mount/update: 3種ともrenderが各componentで1回、commitが1回（余分なrenderなし）。
- 購読: consistency checkでやり直した後もSignal更新に追従し、unmount後のwriteでcomputed/selectorが評価されない（3種）。

修正前のsrcでは、このファイルのR1対象6件が失敗し、修正後は14件すべて成功した。同じファイルを連続5回実行して全件成功した。待機は固定時間ではなく条件到達後に50 ms追加で待つため、遅い環境でもcommit記録が欠けにくい。

`tests/react-deep-signal.test.tsx`にActivity revealのテストを追加し（修正前`[0, 5]`で失敗、修正後成功）、selector評価回数のテストを3/3/3/4/4へ更新した。React開発版はmount時に`getSnapshot`をcache確認のため2回呼び、未購読の2回目が再評価するためで、production buildでは従来どおり2回になる。

## 残る制約

- 保証範囲は各componentが追跡したreadに限る。`useSignalTracking()`のwindowはmicrotask（yieldを含む）で閉じるため、自分のtracking callを持たない子孫のreadはyield後に失われうる。これは既存の[Tracking boundary](../../docs/guides/hooks.md#tracking-boundary)の契約どおりで、今回の検証中にも確認した。
- Computedが等値へ再評価された場合はconsistency checkで「変化あり」と扱うため、render途中のwriteがあった場合に限り同期再renderが1回増えうる。
- 実ブラウザーでのtime slicing中のmixed commit観測はjsdom上の実Schedulerテストで代替した。
