# M15.1 — Transform scalability and semantic hardening

開始HEAD: `b5b86b2709880dd52c6f2da3bb646d503c39ec17`  
実装対象: managed transformのstatic `const` object destructuring  
バージョン: `0.3.0`のまま。publish/tag/releaseは行わない。

## 結果

既存のflat destructuringを一つずつ関数再走査・scope crawlする方式を、関数bodyの候補を一括収集してdeclarationごとに展開する方式へ変更した。scope情報の更新はbatch後に行う。単純なnested static object patternも、同じ中間binding方式で安全なsubsetとして対応した。runtimeやHook規約、captureの同期境界は変更していない。

独立した5件とalias依存chainの0/5/20/100/500件を生成する再現可能なbenchmarkを追加した。Node v24.21.0、Windows x64、Ryzen 7 PRO 6850U、warmup 1回・各3サンプルで実行。結果JSONは[baseline](m15.1-transform-baseline.json)と[candidate](m15.1-transform-candidate.json)、実行scriptは[m15.1-transform-scalability.mjs](m15.1-transform-scalability.mjs)。各ケースでcapture数、最終alias、出力サイズも照合した。

100件の独立・chainでは大きな改善を測定した。500件chainは3回の範囲が4.2〜17.3秒と広く、ピークheapも大きいため、性能特性が十分良いとは判定しない。baselineの500件は測定が長時間化したため完走値がなく比較できない。したがって本benchmarkから全入力での線形計算量や500件での改善を主張しない。通常規模の性能問題を示す証拠はないが、極端な巨大render関数は追加調査が必要。

M15時点の比較に対しtransform pluginのdistは126.56 kB raw / 34.21 kB gzipで、nested pattern対応分として約+1.45 kB / +0.38 kB gzip。runtime bundleは変更なし。短い単一マシン計測であるため、サイズ・時間の差は参考値。

## 意味論とReact検証

対象patternは、再代入されない`const` identifier leafと、静的identifier propertyから成る非空のObjectPattern。initializerは一度だけ評価し、propertyは元の順序で一度ずつ読む。追加テストで、前後のdeclarator、getter順、getter副作用・例外、null/undefined例外、TDZ、shadowing、同名aliasの別scope、複数段alias、source/propertyのreplacementとdeep mutation、React DOM更新を確認した。nested patternのSSR/hydration後更新も確認した。React Compiler fixtureも追加した。

Transform focused tests、React実行テスト、React Compiler 28件、typecheck、transform build/package smokeはpass。nested対応に関する変換ではHook数・位置を変更せず、非同期またはescaped callbackへcapture scopeを延長しない。

flat/nested static patternは現在対応する。引き続き未対応: computed key、default initializer、rest、array pattern、空nested object、mutable/reassigned leaf、TypeScript annotation付きbinding。これらは評価順、binding identity、型情報を含めて証明できるまではwarning/従来処理を維持する。

## M16 JSDOM retention再確認

M11のVitest相当条件（root単位の`React.act`、mount batch、root unmount、container remove、microtask後のWeakRef検査、20 cycle × 8 hosts、5 samples、GC待ち）を再構築した。歴史的な症状で最後のvariantのhostが生存する現象を再現した。variantの実行順を逆にすると保持対象もReact controlからRFSGへ入れ替わったため、RFSG固有とは限らないことを確認した。

heap snapshotのretainer pathは`GC roots → Stack roots → JSDOM → Window → DocumentImpl → DOMSelector → Finder → #nodes → HTMLSelectElement`。JSDOM selector cacheがhostを保持していた。RFSGコード変更は行わず、RFSG固有のretentionは未確認としてM16診断を保留する。snapshotはローカル診断後に削除し、巨大heap snapshotはGit管理しない。短い診断scriptとsnapshot path調査scriptのみを保存した。
