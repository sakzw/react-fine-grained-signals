## 呼び出し経路

`useSignalValue(readable)`は`useMemo`でreadableごとの`subscribe`、snapshot cache、`getSnapshot`を安定化し、`useSyncExternalStore`へ渡す。`getSnapshot`はReactがrender時やstore consistency確認時に呼び、`snapshot()`を通じて次を行う。

1. `render.captureRenderSnapshot(readable)`で新しいrender attemptを作り、Signal読取値と依存Mapをcapture。
2. 前回snapshotと依存Mapのsize・revisionを比較する。同じなら以前のprimitive valueを返す。
3. 依存が変わった場合はcacheを更新する。

このためsnapshotのたびにattempt、Map、capture結果が生成され、同値比較時はMap iteratorとspread配列も作られる。`useSyncExternalStore`がsnapshotを複数回要求するため、一回のコンポーネントrenderとcapture回数は一致しない。

M18.11の200行Consumer workloadを`useSignalValue` leafへ置き換えて追試した。snapshot数はproduction Chromiumで直接`captureRenderSnapshot`をwrapして集計。subscriptionは`subscribeReadables`の作成・disposeをwrapして計数した。

## production Chromium Consumer workload

環境はWindows x64、Node `v24.21.0`、React `19.3.0`、Vite `8.3.4`、M18.11と同一ホストのChromium `156.0.8078.4`。200個の独立Signalを持つ200行をproduction modeでbuildし、同じbrowser pageで計測。render counter、MutationObserver、snapshot/subscription wrapperを用いた。mount後3回warm-upし、single-row updateとparent rerenderを交互に25回測定した。プロファイル取得時の時間はDevTools overheadを含むのでwall-clock集計から除外。

| 操作 | snapshot取得 | subscription create/dispose | component render | DOM mutation | 時間（25 samples、中央値 / p25–p75、範囲） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 初回mount | 400 | create 200 | 200 | 初期mount | 未計時 |
| 1 leaf Signal update | 3 | 追加0 / dispose 0 | 1 | 1 text mutation | 1.1 ms / 1.0–1.1 ms（0.8–1.8 ms） |
| parent rerender | 200 | 追加0 / dispose 0 | 200 | 0 | 4.5 ms / 4.3–4.8 ms（3.4–8.2 ms） |
| unmount | — | dispose 200 | — | subtree removal | すべてcleanup |

dev/JSDOM focused instrumentationではStrictModeなしの通常mountでsnapshot 600、version check 400、subscription create 200。単一Signal更新でsnapshot 4、version check 3、render +1。parent rerenderでsnapshot 400、version check 400、render +200。Reactの開発時external-store checkとproduction実行ではsnapshot呼び出し数が異なるため、性能判断にはproduction Chromiumの値を使用した。

Single-row updateは200行中1行だけrenderされ、200 subscriptionsは安定して維持された。親rerenderは全200行を呼び出すConsumer workload自体の処理であり、各rowのsnapshotが200回発生した一方、DOMは変更されなかった。1回のrow render当たりcapture 1回（通常の親render）、Signal更新に伴う対象rowでは計3回（React external-store確認を含む）だった。

## Profile・allocation

Chromium CDP CPU samplingとV8 allocation samplingをwarm-up後のparent rerender 10回に限定して採取した。production minify済みbundleではinternal関数名が短縮され、CPU profileはReact reconciliation、短縮されたruntime関数、GCに分散した。snapshot比較/captureがwall-clockの主要因と断定できるstack比率は得られなかった。allocation samplingの上位もminify済みbundleのframeに集中し、adapter個別のbytes/opをソースへ対応づけられなかった。プロファイラを有効にすると計測時間が大幅に伸びたため、その時間は比較値から除いた。

したがって、一回あたりの確定allocation形状（attempt + dependency Map + capture result、比較時のiterator/spread array）はソース経路から確認したが、実Consumerにおける総allocation量、retained heap差、snapshot由来のCPU比率は**未確定**。ReactとSignalのその他処理から独立して削減可能な量を示せていない。

## 最適化候補と判断

| 候補 | 利点 | リスク・コスト | 判断 |
| --- | --- | --- | --- |
| capture attempt/Mapをcache間で再利用 | 一時allocationを削減できる可能性 | render間・Concurrent/abandoned renderでcapture状態を共有すると、commit済みsnapshotや別renderの依存を破壊する恐れ。allocation/CPU上の効果が未立証 | 不採用 |
| 単一依存Signalのdirect snapshot fast path | よくあるsignal leafでcaptureとMap比較を省ける可能性 | computed/deep/foreign protocol/異なるcopyの依存意味論、revision race、SSR/hydrationとの分岐実装が必要。profileで対象割合と時間が不明 | 不採用。consumer profileで支配性が示されれば別途PoC |
| subscription callbackを別経路へ変更 | 通知経路の処理を変えられる | 既に安定sourceでは更新ごとの作り直しがない。snapshot問題への効果がなく、React lifecycleリスクだけを増す | 不採用 |

候補コードを統合せず、baseline/candidate差分計測は行っていない。採用候補が成立していないためM18.11のstable-subscription最適化を取り消す理由もない。production Chromiumで観測した親rerenderは4.5 ms/200 consumersで、snapshot 200回だけでなくReact component/reconciliation全体を含む。単一leaf更新は1.1 msでrender/DOM更新は局所化済み。現状では利用者に意味のある改善幅を示せない。

## 正確性・サイズ・検証

- Focused計数fixture: `tests/m18.12-temp.test.tsx`、1 test pass。調査専用でcommit前に削除。
- production Vite build: temporary 200-row fixture success（JS 245.82 KB / gzip 76.98 KB。React込みのfixture全体でありRFSG package sizeではない）。
- production Chromium smoke/measurement: mount、Signal update、parent update、unmount成功。console/page errorなし。1-row updateでrender 1、DOM mutation 1、parent rerenderでrender 200、DOM mutation 0。全subscription cleanup確認。
- baseline/candidate比較、StrictMode/Concurrent/SSR専用test、size再計測は製品candidateなしのため実施していない。既存コード・React lifecycleを変更していないので、それらの回帰は発生していない。
- `index-full` gzip budgetはM18.11時点の24,704 Bを変更せず維持。今回bundleを変えていないため再測定なし。

CPU/allocation profileは取得したが、minify済みstackのsamplingだけではAdapter内の実ボトルネックを独立して示せなかった。sampling profilerを使った対象の関数別bytes計測、retained heapの長時間・反復比較も未実施である。数値を推定・一般化しない。

## 残課題・次の判断
