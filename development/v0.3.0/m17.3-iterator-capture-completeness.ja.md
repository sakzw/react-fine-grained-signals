# M17.3 — Iterator captureの網羅

開始基準: `main` / `71f016ae18058d36b2302eb23edefb66bf0e4c49`(M17.2記録時点)

## 結論

M17.2の`for...of`変換(`_signals.iterate(() => source)`)は、sourceの評価、GetIterator、`next()`呼び出しはcaptureしていた。一方で、次のgetterで行われるSignal readがcapture外で実行され、追跡から漏れていた。

- GetIterator時の`next`のlookup
- ループ終了時の`return`のlookup
- ループが各resultに対して行う`done`/`value`の読み取り

再現テストで修正前の失敗を確認してから修正した。nativeの`for...of`と評価順序、this binding、早期終了、IteratorClose、例外伝播が一致することは、変換前後の比較テストで確認している。公開APIの追加はない。

## 修正前の再現

```tsx
const iterable = signal({
  [Symbol.iterator]() {
    let index = 0;
    return {
      get next() {
        const tag = nextTag.value;
        return () => {
          const step = ++index;
          return {
            get done() { return step > doneLimit.value; },
            get value() { return valueTag.value + step + tag; },
          };
        };
      },
      get return() { closedWith = returnTag.value; return () => ({ done: true }); },
    };
  },
});

function App() {
  let out = "";
  for (const item of iterable.value) out += item;
  for (const item of iterable.value) { out += "|" + item; break; }
  return <p>{out + "/" + closedWith}</p>;
}
```

初回表示は`v1n0v2n0|v1n0/r0`。修正前は`nextTag`を変更しても再描画されず、`v1n0v2n0|v1n0/r0`のままだった(期待値`v1n1v2n1|v1n1/r0`)。`doneLimit`、`valueTag`、`returnTag`の変更も同じく反映されなかった。

## 修正

`src/react/react-adapter.mts`の`captureIteration()`を次のように変更した。

- `next`はGetIterator時に1回だけ、capture内で読む。
- `return`は終了時にcapture内でlookupし、呼び出しもcaptureする。`return`が`null`/`undefined`なら呼ばない(native IteratorCloseと同じ)。
- custom iteratorのresultは、`done`/`value`のgetterを持つ遅延wrapperで返す。各getterは、外側の`for...of`が実際にアクセスした時点で元のresultの同名propertyをcapture内で読む。先読みしないため、`done`がtrueなら`value`は読まれない。元のresultのgetterは元のresultをreceiverとして呼ばれ、例外はそのまま伝播する。resultがobjectでなければ、nativeと同じくTypeErrorにする。
- 組み込みの`next`(Array、Map、Set、String iterator、generator、Iterator helpers)と、reactive Map/Set iteratorの`next`は、`done`/`value`がdata propertyの通常objectを返すことが分かっている。この場合はwrapperを作らない。判定は取得済みの`next`関数の同一性比較だけで、外から観測できる操作を追加しない。reactive collection iteratorの`next`は内部の`WeakSet`に登録する。

全件コピーには戻していない。

## 確認

- `react-execution.test.ts`
  - getter追跡テスト: 4種類のgetterでの変更がすべて再描画されることをDOMで確認した。修正前は失敗した。
  - native比較テスト: 同じfixtureを変換あり/なしで実行し、getter呼び出し・`next`のthis・body・closeの順序ログが一致することを確認した。対象は次の9 scenario。
    - complete、break、continue、throw
    - `next`/`done`/`value`/`return` getterの例外
    - `return` getter例外と本体throwの組み合わせ
  - 完了時に`value 4`(`done`がtrueのstepの`value`)を読まないことも確認した。
  - reactive Map/Set、`keys().map()`(Iterator helper)の`for...of`の追跡を確認した。
- `use-signals-managed.test.tsx`: `useSignalCapture().iterate`を直接使い、次を確認した。
  - 組み込みiteratorとcustom getterの追跡
  - iteratorまたはresultがobjectでない場合のTypeError
  - `return`が無いiteratorの`break`
  - `return`が非objectを返した場合のTypeError
- M17.2の`for...of`意味論テスト(早期終了、反復中の変更、shadowing、closing、custom iteratorの追跡)とHook safetyテストは引き続き通過した。

## 性能

render中に1000要素を20回反復した時間の中央値を、`71f016a`と比較した。同一process内でcomponent単位に交互実行し、20 round中の後半16回の中央値をとった。

| source | `71f016a` | M17.3 |
|---|---:|---:|
| 通常配列 | 19.4 ms | 20.6 ms |
| deep proxy配列 | 171.4 ms | 166.7 ms |
| reactive Map | 24.5 ms | 25.2 ms |
| generator | 22.7 ms | 21.8 ms |
| custom iterator | 17.7 ms | 58.3 ms |

組み込み・reactive collection・generatorは計測誤差の範囲だった(±6%)。custom iteratorは1要素ごとに`done`/`value`の読み取りを2回captureするため、約3.3倍(1要素あたり約2µs増)になった。getterによるreadを追跡するために必要なコストとして受け入れる。render scopeの再利用によるcapture自体の高速化は、M17.2と同じく後続候補(分類2)とする。

## 残る制約

- custom iteratorの反復コストは上表のとおり。
- reactive collection iteratorの`next`がユーザーに置き換えられた場合、または別package copyのiteratorの場合は、custom iteratorとして扱う。結果は正しく、wrapperの分だけ遅くなる。
- `for await`、関数呼び出しの結果を直接回す`for (x of gen())`はM17.2と同じく変換対象外。
