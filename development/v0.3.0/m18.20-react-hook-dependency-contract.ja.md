# M18.20 — React Hook Dependency Contract Hardening

## 目的と開始状態

開始HEADは `05eb79c226f4281f83809a4e946d96914217a3bf`。`useComputed`、`useSignalEffect`の依存配列について、Reactのwarningだけで古いclosureが使われ続けるケースを現行HEADで再現し、公開契約と実装を揃えた。

## 再現結果

変更前のテストでは、依存配列長の変更はReactからwarningが出るだけで例外にならなかった。

- `useComputed`: `[a]`から`[a, b]`、逆方向、空配列との切り替えで、computed identityとgetter/setter closureが前のまま残る。getter-onlyとwritableの双方で再現した。
- `useSignalEffect`: 長さ変更後にcleanup/reconnectされず、Signal更新で前のcallback closureが実行される。
- 同じ長さで値を変更する正常系は従来どおり新しいcomputed/effect callbackへ更新する。

再現用のテストは修正後の回帰テストとして残した。

## 実装と契約

- `useComputed`は依存mode（省略／明示）、computed capability（getter-only／writable）、明示依存配列長をrender中に検証する。検証は`useMemo`より前に行うため、不正な呼び出しでcomputedを生成・再利用しない。検証状態は既存refで保持し、新しいHookや依存配列オブジェクトを追加していない。
- `useComputed`は省略modeと明示modeを区別する。明示配列の長さとgetter/setter capabilityはcall siteの生存期間中固定する。mode/length違反はそれぞれ`UseComputedModeChangeError`、`UseComputedDependencyLengthChangeError`。
- `useSignalEffect`では、既存実装が省略と`[]`を同じ空配列としてReactへ渡しているため、その意味論を維持する。省略と`[]`の切り替えは許可し、明示配列の長さ変更は`UseSignalEffectDependencyLengthChangeError`で拒否する。
- `useSignalEffect`は長さ記録用にref Hookを1つ追加する。Hookの呼び出し順は常に一定で、例外時にReactのEffectへ到達しない。

英語・日本語Hook guideとWebsite Hook pageに、mode、長さ固定、cleanup/reconnect、React標準warningとの違いを記載した。

## React lifecycleと互換性

修正はrender中に既存computedやEffectを差し替えない。`useComputed`の検査はmemo生成前に同期的に失敗し、`useSignalEffect`の再接続は従来どおりReact commit後に行う。同長の依存値更新、readonly/writable capability、StrictMode cleanupを維持した。

Fast Refresh専用のブラウザーケースは今回実行していない。Hook内部の呼び出し形状が変わるコード更新ではReact Refreshが対象コンポーネントをremountする可能性があるが、通常のrender間でHook順序が変わることはない。SSR/hydration、Suspense、abandoned render、Compilerは既存focused suiteで確認した。Compilerの30件はHook/runtimeの既存適合性確認であり、Fast Refreshの代替ではない。

## 性能とサイズ

`development/v0.3.0/m18.20-hook-cost.mjs`は再実行可能なproduction React 19 / JSDOM比較。Node 24.21.0、500行、12回のcommit、warmup 2回、交互順序、9 sample。baselineは開始時のHook構成、candidateは修正後APIを使う。これはbrowser性能を代表する値ではなく、Hook guardの相対コストをみる小規模microbenchmark。

| Metric | Baseline median (min–max) | Candidate median (min–max) |
| --- | ---: | ---: |
| Mount | 17.81 ms (13.80–34.80) | 16.04 ms (12.66–22.77) |
| Update per commit | 3.812 ms (2.724–5.891) | 3.766 ms (2.469–4.867) |
| Retained heap, 500 mounted rows | 4,935,384 B (4,887,232–4,988,632) | 5,004,168 B (4,988,336–5,079,728) |

CPUの測定幅は大きく重なり、速度差は確認できない。candidateのretained heap中央値は68,784 B（約138 B/row）増えた。これは`useSignalEffect`の追加ref/React Hook cellを含む。benchmarkは同じ依存値更新ごとにSignal Effectをcleanup/reconnectする負荷で、他のアプリ負荷への外挿はしない。

M18.19 exact size checkの全scenarioを実行。主なgzip値は`signal-only` 6,230 B、`core` 6,284 B、`core+hooks` 10,032 B、`index-full` 24,698 B、Full JSX 13,520 B、Lite JSX 7,149 B。`index-full`は既存24,704 B budget内で6 Bの余裕。M18.19記録の基準24,624 Bから74 B増えた。予算変更はしていない。最初の実装候補は`index-full`を25 B超過したため、エラーチェックを残しつつ診断文を短くしてbudget内へ戻した。

## 残課題

- Fast Refreshを`useComputed` / `useSignalEffect`のConsumerで直接操作する実browser試験は未実施。
- JSDOM microbenchmarkは小さくノイズが大きいため、CPU性能の改善・悪化を結論づけない。retained heapの増分は追加ref Hookの実測コストとして記録する。
- 現行Reactのwarningは依存配列長変更時にstale closureを防がないため、この2 Hookではlibrary guardを維持する。
