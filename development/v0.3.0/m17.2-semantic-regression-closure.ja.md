# M17.2 — managed transformの意味論回帰の解消

開始基準: `main` / `e9165c1f2c0d1f980a5670bc160282616221800e`(M17.1記録時点)
比較基準: tag `v0.2.1` / commit `58f01b9314a1b09b88b162c57912ff736201e790`

## 結論

M17.1で入れた`for...of`の全件コピーは、元のJavaScriptから観測できる動作を変えていた。また、Hook呼び出しがcapture closureへ移動する経路がM17.1以前から残っていた。どちらも再現テストを先に作り、修正前のコードで失敗することを確認してから修正した。あわせて、M17.1に残課題として記録した部分mount失敗時のbinding leakとtransform負荷を修正し、migration guideの未記載事項を追記した。公開APIの追加・削除はない。capture storeへ内部メソッド`iterate`を追加した(生成コードだけが使う)。

## 1. `for...of`の意味論

### 修正前の再現

```tsx
const lazy = ["a", "b", "c"];
Object.defineProperty(lazy, 2, { get() { log.push("read 2"); return "c"; } });
const list = signal(lazy);
const Array = { isArray() { throw new Error("shadowed"); } };

function App() {
  let out = "";
  for (const item of list.value) { if (item === "b") break; out += item; }
  // ...
}
```

M17.1の変換は次のコードを生成した。

```js
for (const item of _signals.capture(() => {
  const _iterable = list.value;
  return Array.isArray(_iterable) || _iterable instanceof Map || _iterable instanceof Set ? [..._iterable] : _iterable;
})) { ... }
```

- `break`しても全件をコピーするため、`read 2`のgetterが実行される。巨大collectionを先頭1件で抜ける場合も全件のコピー時間とメモリを使う。
- ループ中の配列への`push`がループに反映されない。
- module内で`Array`/`Map`/`Set`をshadowすると、生成コードがそれを参照して例外になる。
- generatorやcustom iterableの`next()`はcapture外で実行され、そこで読まれたsignalが追跡されない。

### 修正

`useSignalCapture()`が返すstoreに内部メソッド`iterate(getIterable)`を追加し、変換を次の形にした。

```js
for (const item of _signals.iterate(() => list.value)) { ... }
```

`iterate`はsourceの評価、GetIterator、ループが行う各`next()`と`return()`呼び出しを、その時点で個別にcaptureする。GetIteratorと同じく`next`メソッドは1回だけ読み、`return`は終了時にlookupする。`return`が無いiteratorでは何も呼ばない。外側の`for...of`がstep結果の検査、早期終了時のiterator close、本体の例外の再送出を通常どおり行うため、反復順序、遅延評価、ループ中の変更、iterator closingはnativeの`for...of`と同じになる。`for await`は対象外のまま。

### 確認

- `react-execution.test.ts`
  - `break`後の要素を読まないこと
  - ループ中の`push`が見えること
  - custom iteratorを`break`で抜けたときの`next`/`next`/`return`の呼び出し順
  - shadowされた`Array`を参照しないこと
  - 本体の例外でiteratorが1回だけcloseされること
  - custom iteratorの`next()`内のsignal readが再描画を起こすこと
- 修正前のコードでは、上記のうち意味論と追跡の2件が失敗した。

## 2. Hookをcapture closureへ移動させない

### 修正前の再現

```tsx
import { useContext } from "react";
import { format } from "./format";

function App() {
  const text = format(useContext(Context), count.value);
  return <p>{text}</p>;
}
```

M17.1以前から、import helper呼び出しは丸ごとcaptureされ、`_signals.capture(() => format(useContext(Context), count.value))`となっていた。実行時には無条件に呼ばれるため動作するが、Rules of Hooksのlint形に反し、React Compiler integrationを`off`にした場合の扱いも保証できない。原因は`externalCallMayReadTrackedValue()`経由の分岐にHook判定が無かったことで、M17.1で追加した規則にだけHook除外が入っていた。

### 修正

- call、`new`、tagged template、member read、`in`、spread、`for...of`のどの経路でも、Hook呼び出し(`useX`、`React.useX`、React 19の`use`)を含む式をcapture closureで包まない。
- Hookとtracked readが同じcallにある場合は、callを直接呼び出しのまま残す。引数の`count.value`などは引き続き個別にcaptureする。callee内部でしか行われないread(import helper、局所helper、inline callback)は追跡できないため、source位置付きの警告を出す。
- `useStore().value.name`のようにHookの戻り値に対するreadは、`(_hookResult => _signals.capture(() => _hookResult.value.name))(useStore())`とする。Hookは元の位置で評価し、後続のreadだけをcaptureするため、評価順序は変わらない。それ以外の位置でHookを含むread式は、警告付きでcapture対象外にする。

### 確認

- `react-execution.test.ts`
  - import helper、局所helper、member call、`React.useContext`、custom Hook名、`use()`、inline callback、`useX().value`、template literalの各形について、出力ASTでHookが`.capture(...)`のcallback内に無いことを検査する
  - Hookと同じcallにある`count.value`の追跡を実行時に確認した
  - `useX().value`の追跡を実行時に確認した
  - 警告が出ることを確認した
- 修正前のコードでは、import helperの形で`useContext`がcapture内にあり失敗した。
- `react-compiler.test.ts`
  - Compiler integration `off`(Compilerがmanaged出力をcompileする構成)で、Hookと同じcallにあるread、`useX().value`、`for...of`を含むcomponentが`CompileSuccess`し、signal更新で再描画されることを確認した。

## 3. 残課題の評価と対応

| 項目 | 判断と対応 |
|---|---|
| 部分mount失敗時のbinding cleanup | 確定したleakとして修正。同じnodeの後続bindingがthrowすると、先にmountしたsubscriptionが`#mounted`に残らず、例外を投げたref callbackにはReactもcleanupを返さないため解放されなかった。`#sync`は失敗時に生きているentryをすべて保持し、`attach`が破棄してから再送出する。radio source競合と`title` signalの組み合わせで、修正前はsignalにsubscriberが残ることを再現した |
| 同期helperを多数呼び出す場合のtransform負荷 | 修正。主因は、生成したcapture callbackごとに上位の`Function` visitorが`decideTransform`を実行し、helperを呼び出し位置の数だけ再解析していたこと。生成callbackを判定対象から外した。あわせて、helper解析で`visited`を先に確認し、helperごとの解析結果をcacheする。200 read helperを400回呼ぶfixtureで、`e9165c1`の約5.0秒から約0.12秒になった(同一process内で交互実行し、5回の中央値)。200 componentとread 2000件の単一関数では差は誤差範囲(569→543ms、1324→1280ms) |
| migration guideに未記載のbreaking change | 英日に追記した。フォームcontrol以外への`value={signal}`、`bindValue`が受け付けないinput type、保存時にthrowするcollection(subclass、別realm、凍結collection、凍結object entry)、collection readのproxy identity。いずれも実行時の挙動を確認してから記載した |
| cancelされたclickと同期的なSignal書き込みの競合 | 仕様上の制約としてmigration guideに記載した。`preventDefault()`したhandlerが、ユーザーがclickした値と同じ値を同期的に書くと、binding自身の書き込みと区別できないため、その書き込みも戻される。確認後など、event後の書き込みは保持される |

## 4. M17.1修正の維持

次の項目の既存回帰テストは、すべて引き続き通過している。

- opaque値の高速read
- Map/SetのO(1) identity lookup
- collection key metadataの解放
- Iterator helpers
- checkbox/radioのReact event順序
- `preventDefault()`後の整合性
- inline callback、spread、`in`、call内部のmanaged tracking

M17.1の`for...of`テストは、コピーを前提にしていたため、この修正で意味論を検査するテストへ置き換えた。

## 性能

- transform: 上記のとおり、helperを多数呼ぶ場合は大幅に短縮した。他の構成で遅くなったものは無かった。
- runtime: `for...of`は要素ごとに`next()`をcaptureするため、M17.1の全件コピーより1要素あたりのコストが高い。render attempt内で1000要素の通常配列を20回反復した計測(同一process内で交互実行、中央値)は次のとおり。
  - 通常配列: コピー0.9ms、`iterate` 17ms(1要素あたり約0.8µs)
  - deep proxy配列の要素propertyも読む場合: 239ms、288ms
- 差分は主にcaptureごとのrender scope作成コストである。`for...of`の意味論を保つための必要コストとして受け入れる。render scopeの再利用によるcapture全般の高速化は、Runtimeの共通経路を変えるため今回は行わず、後続候補とする(分類2)。
