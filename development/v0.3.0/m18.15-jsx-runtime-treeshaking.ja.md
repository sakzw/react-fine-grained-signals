# M18.15 — JSX Runtime Tree-Shaking Audit

## 結果

- 開始HEAD: `d7d95ab0dbbc6ab7e80f2d6f7acb89f1a6b4211c`
- 判定: **製品コード変更は採用しない。** `jsx-runtime`を使うと、signal childrenだけのConsumerにもform bindingのruntime分岐が含まれる。一方、全form bindingを使うfixtureとの差はsignal-child fixture比でgzip 88 Bだった。これを除くためにruntime variant、entry point、またはbuild transformの追加を正当化できるほどのConsumerサイズ削減は今回の測定で確認できない。
- 公開API、実装、依存、version、既存bundle budgetは変更していない。release freezeも行わない。

## 測定方法

5つの独立Consumerを、同じproduction Vite buildで作成した。環境はWindows x64、Node `v24.21.0`、Vite `8.3.4`、`@vitejs/plugin-react` `6.1.2`、React `19.3.0`、esbuild minifier。RFSGは開始HEADの`pnpm build:runtime`で作成した`dist/`をaliasし、Reactとalien-signalsを含むdependenciesをbundleへ取り込んだ。各fixtureは1つのproduction JS assetを出力し、external dependencyはない。

React標準JSXとRFSG plain JSXは同じ`App` markupを使用する。全fixtureで`App`をglobalへ公開し、tree shakingによりConsumer本体が消えないようにした。5番目はtext/number/range input、textarea、single/multiple select、radio、checkbox group、`bindChecked`をすべて含む。

サイズはJS assetのraw bytes、Node `gzipSync(level: 9)`、`brotliCompressSync(quality: 11)`で測定した。計測fixtureとsummaryは[m18.15-measure.mjs](m18.15-measure.mjs)と[m18.15-consumer-bundles.json](m18.15-consumer-bundles.json)に保存した。圧縮結果は同一ホスト内の比較であり、CDN転送やHTTP cacheを含む実サイトのLCP計測ではない。

## Consumer bundleサイズ

| Consumer | raw | gzip | brotli | form-binding markers |
|---|---:|---:|---:|---|
| React標準JSXのみ | 560 B | 368 B | 314 B | なし |
| RFSG JSX runtime、binding未使用 | 39,189 B | 13,337 B | 12,112 B | あり |
| Signal childrenのみ | 39,252 B | 13,362 B | 12,179 B | あり |
| Signal children + signal attribute | 39,278 B | 13,380 B | 12,169 B | あり |
| 全form binding | 39,677 B | 13,450 B | 12,223 B | あり |

form-binding markerは`Invalid select bindValue`、text inputの許容tag/type検証、checkbox-groupの型チェック、`bindChecked`の型チェック、radio group、form resetなどの実装文字列。シンボル名はminifyで変更されるため、関数名の有無では判定していない。

- RFSG JSXを使うだけのbundleはReact標準JSX fixtureよりgzipで`+12,969 B`。signal childを加える増加はRFSG plain JSX比`+25 B`。
- signal attributeを加える増加はsignal-child fixture比gzip`+18 B`。
- 全form binding fixtureはsignal-child fixture比raw`+425 B`、gzip`+88 B`、brotli`+44 B`。
- 重要な観測として、form bindingを1つも記述しないRFSG JSX bundleにもbinding markerが存在する。現在の`createJsxWrapper`が任意のhost propsを実行時に調べ、`findHostBindings`、`resolveBindingKind`、mount/subscribe経路へdispatchするため、通常のtree shakingは個々のpropsに対応する分岐を除去できない。

この比較は、form binding処理全体がわずか88 Bという意味ではない。runtime dispatcherが全fixtureに既に含まれるため、マークアップ上でbindingを追加したときの差分として測れる値である。BindingのないConsumerにformコードが混入する、という点は肯定できた。

## 改善候補と判断

| 候補 | 見込み | コスト / リスク | 判断 |
|---|---|---|---|
| 現行dispatcher内の小さなsource file分割 | import参照を切らない限りbundlerはbinding実装を残す | file構成だけ増え、bundle差が出ない | 不採用 |
| form binding専用entry/runtime variant | form handler importを切ればsignal-only consumerから除外可能 | 別runtimeの意味論・SSR/hydration・Fast Refresh・Compiler・型・文書の維持が必要。現行APIからの切替方法も必要になる | 今回不採用。実サイズ削減を測るPoCへ進む条件が不足 |
| Managed Transformが使用機能ごとにfactoryを選択 | build時にbinding利用を判定できる可能性 | pluginなしのJSX import sourceとの一貫性、JSX spread/変数経由propsの解析、安全なfallback、複数bundler対応が必要 | 不採用 |
| runtime props dispatchの維持 | 既存APIと任意のprops変化を維持 | form dispatchはnon-form consumerにも残る | 現時点で維持 |

別entryまたはcompiler設定を追加すれば、コードを静的に分離できる可能性はある。しかし今回の計測が示すのは混入の存在までで、分離後に除けるform実装のgzip/brotli量を示していない。通常のruntimeはSignal children、属性binding、form bindingを同時に扱う既存契約がある。サイズ削減の定量効果が分からない段階で別entryやtransform設定を導入すると、利用者の選択・保守負荷に先行するためPoCは作らなかった。

M18.9のpackage-entry bundle測定とM10のfactory-call性能測定とは異なり、今回はproduction Vite app-graphで`jsxImportSource`から出るconsumer outputとbinding codeの残存を調べた。M18.9が確認した既存`jsx-runtime` entryのgzip budgetとも測定対象が異なる。

## 検証と残課題

- `pnpm build:runtime`: pass。開始HEADのsourceから全entryをbuildした。
- 5つすべてのproduction Vite fixture build: pass。1 bundleずつ出力し、サイズとmarkerを記録した。
- root package、lockfile、runtime、公開APIの変更なし。新しい依存も追加していない。
- 手元のVite app output測定であり、Chromium network waterfallや実際の公開サイトを通したtransfer測定ではない。

今後、RFSG JSXを採用した実アプリで初回転送量が問題になり、form系runtimeの分離による具体的な削減値が期待できる場合は、独立したruntime variantを一案だけ隔離PoCし、同じfixtureの5 consumerとReact/SSR/Compiler/refresh契約で比較する。今回の結果だけでは、公開API分割やManaged Transform統合を進めない。
