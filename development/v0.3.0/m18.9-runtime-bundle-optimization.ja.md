# M18.9 Runtime & Bundle Optimization

## 結果

- 開始HEAD: `98cbbc246bd5663d5caab6c35d5dddeb83296657`
- 判定: **Core-only と Deep/JSX Consumerのbundle・retained heapを削減できたため、Render Adapterの遅延初期化を採用**。
- 公開API、package entry、version、size budgetは変更していない。
- Reactを使う全API bundleは小幅に増えた。`index-full`は既存gzip budgetの近くにあるため、以降の変更でもsize checkを維持する。

## 調査した構成と過去の判断

`coreRuntime`は`src/core/core-runtime.ts`でmodule評価時に生成される。開始HEADの`src/core/reactive-runtime.ts`は`render-runtime.mjs`を静的importし、`createReactiveRuntime()`内でGraphとRender Adapterの両方を生成していた。Reactのrender trackingを使わないConsumerでも、Coreのimport graphにRender Adapterが入り、Core Runtimeごとにその状態を保持する。

開始HEADのsignal-only bundleには`renderAdapter`、`renderRevision`、`hasActiveSubscriber`などのRender由来コードが残っていた。これは実際のConsumer bundleで確認した。`useSyncExternalStore`やDeep Signalのmarkerはsignal-only/coreから除去されており、既存Tree Shakingは機能していた。

M9の記録では、Core専用のsubpath/packageを増やす案を、既存bundlerのTree Shakingで大半のReactコードを除けること、package/API面の保守負荷を理由に不採用としている。今回は新entryを追加せず、残っていたRender Adapterの静的依存だけを切る。M14のinterop protocol lazy materialization、M18.4の`For`/`Index`候補と同じく、測定できないruntime最適化は採用しない方針を維持した。

## 実装

- `src/core/reactive-runtime.ts`はGraphだけを生成し、Render Adapterを初期状態で保持しない。
- 内部Runtimeに`initializeRenderAdapter(factory)`を追加し、最初の呼び出しで現在のGraphに対するadapterを一度だけ生成する。
- `src/react/use-signals.ts`がReact Adapterを作る際にRender Adapterを同期初期化する。ReactのHook呼び出し中やConcurrent render中に状態を差し替えない。
- Render Adapter未初期化のRuntimeでは`isSpeculative()`は`false`を返し、`markSpeculativeDeepRead()`はno-opとなる。React tracking経路は引き続きadapterを初期化してから利用する。
- Render Adapterを直接使う内部テストとcross-copy smokeは、内部Runtimeの明示的初期化を行うよう更新した。root packageのexportや利用者向けAPIは変更していない。

単純なlazy getterだけを置く最初のPoCはbundleを縮めず、gzipで約22 bytes増えたため破棄した。今回の候補はRender Runtimeの静的依存をReact接続module側へ移す構成である。

## Consumer bundle比較

各行は開始HEADと候補を同じNode/Vite環境で3回ずつ交互に測った値。raw/gzip/brotliはbytes。gzip比は各runを順序対応させたcandidate/baseline比の中央値。開始HEADは`98cbbc2`のsourceからbuildしたdist、候補は変更後sourceからbuildしたdistを使用した。`scripts/size-budget.json`は変更していない。

| Scenario | Baseline raw / gzip / br | Candidate raw / gzip / br | gzip差分 | paired gzip比 |
|---|---:|---:|---:|---:|
| signal-only | 27,356 / 7,514 / 6,783 | 21,968 / 6,240 / 5,634 | -1,274 B (-17.0%) | 0.830 |
| core | 27,580 / 7,576 / 6,837 | 22,193 / 6,294 / 5,681 | -1,282 B (-16.9%) | 0.831 |
| core+hooks | 35,986 / 9,923 / 8,938 | 36,195 / 9,996 / 9,002 | +73 B (+0.7%) | 1.007 |
| deep | 63,265 / 15,649 / 13,946 | 58,580 / 14,562 / 12,979 | -1,087 B (-6.9%) | 0.931 |
| index-full | 95,062 / 24,479 / 21,603 | 95,277 / 24,692 / 21,691 | +213 B (+0.9%) | 1.009 |
| jsx-runtime | 52,879 / 14,794 / 13,234 | 47,473 / 13,537 / 12,098 | -1,257 B (-8.5%) | 0.915 |
| utils | 34,957 / 9,633 / 8,697 | 35,167 / 9,693 / 8,763 | +60 B (+0.6%) | 1.006 |

gzipのrun-to-run範囲はbaselineで最大2 bytes、候補で最大4 bytes。rawは全scenarioで一定。brotliのばらつきはscenarioあたり最大18 bytesだった。圧縮差が小さいcore+hooks/utilsの増加はこの作業の狙いに対して許容できるが、`index-full`はbudget 24,704 bytesに対して測定上24,690〜24,693 bytesまで達し、残り11〜14 bytesと小さい。budgetの引き上げは行わない。

実bundleのabsence/presence checkと既存budgetはすべて通過した。core-only bundleからReact `useSyncExternalStore`とDeep Signal markerが除去され、Core APIが残ることを確認した。集計前の7 scenario全runは[paired size log](m18.9-size-paired.txt)に記録した。

## Runtime速度とretained heap

### Core hot path

`benchmarks/core.mjs`をNode `v24.21.0`、Windows x64、AMD Ryzen 7 PRO 6850U、各100,000 operation、3 warmup、9 sampleで実行した。開始HEADと候補を3 round交互に実行。各roundの中央値同士のpaired throughput比(candidate/baseline)を比較した。

| Case | Baseline median ops/s | Candidate median ops/s | paired ratio median (3 round range) |
|---|---:|---:|---:|
| signal/read | 14.91M | 14.95M | 0.972 (0.969–1.061) |
| signal/write | 14.55M | 16.10M | 1.102 (1.049–1.539) |
| observed write | 3.13M | 3.05M | 0.897 (0.873–1.208) |
| computed/create | 6.51M | 6.66M | 1.023 (1.021–1.513) |
| computed/read | 20.02M | 15.39M | 0.883 (0.612–1.006) |
| computed/update-and-read | 2.86M | 3.21M | 1.125 (0.508–1.516) |
| batch/two-observed-writes | 0.95M | 0.86M | 0.901 (0.898–1.377) |

ばらつきとoutlierが大きく、Core操作速度の改善・悪化はいずれも結論できない。今回の採用理由はConsumer bundleとruntime objectの保持量であり、signal hot pathが速くなったとは主張しない。各sampleのp25/p75と実測値は[baseline JSONL](m18.9-core-baseline.jsonl)、[paired JSONL](m18.9-core-paired.jsonl)を参照。

### retained heap

同一プロセスで、Render Adapter未初期化Runtimeと初期化済みRuntimeを5,000個ずつ作成し、`--expose-gc`によるGC後の`heapUsed`を5回、順序を交互にして比較した。後者は開始HEADのeager adapter保持を近似する対照。初期化済みとの差は中央値7,761,944 bytes、約1,552 bytes/Runtime。paired差は約7.67〜7.77 MB/5,000 Runtimeだった。これは複数Runtimeを直接生成する内部測定であり、一般的なアプリ全体のheap削減量を示すものではない。

raw measurementsは[retained heap JSONL](m18.9-retained-heap.jsonl)。

## 採否と残課題

Render Adapterの同期lazy initializationを採用する。signal-only/coreで約1.27 KB gzip、deepで約1.09 KB、jsx-runtimeで約1.26 KB削減し、5,000 Runtime比較でも保持heap削減が得られた。一方、React利用scenarioのbundleは約60〜213 bytes増える。全scenarioは既存budget内だが、`index-full`のheadroomは非常に小さいため、次のbundle変更時もこの値を注意して確認する。

内部モジュールから`createReactiveRuntime()`を直接使う場合、`renderAdapter`を読む前に`initializeRenderAdapter()`を呼ぶ必要がある。この内部factoryはpackage exportではない。利用者向け公開APIには影響しないが、将来internal test/toolingを追加する際はこの初期化契約を維持する。

Core benchmarkの測定ばらつきが大きく、次に性能最適化を行う場合はCore hot pathのprofileやReact app計測を別の測定機会に実施する。M18.9ではこれ以上Core/JSX runtimeの変更を追加しない。
