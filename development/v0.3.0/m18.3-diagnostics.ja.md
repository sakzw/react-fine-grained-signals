## 1. 現行警告の分類

`src/internal/transform.ts` の `reportWarning()` に集約されている非致命の警告は、本文として11種類ある。このうち、原因と対処が同じものを統合し、9カテゴリにした。

| 旧警告（本文の先頭） | 発生箇所 | 新ID |
| --- | --- | --- |
| This JSX callback prop reads a signal ... | `warnUntrackedRenderPropRead` | RFGS003 |
| This JSX children callback reads a signal ... | `warnUntrackedChildrenCallbackRead` | RFGS003 |
| A .value read remains in a function parameter initializer ... | `warnUncapturedParameterRead` | RFGS004 |
| This useSignalTracking() call cannot be verified ... barrel ... | `warnUnverifiableBarrelSignalTracking` | RFGS005 |
| This @signalTracking annotation is ignored ... | `warnUnnamedSignalTrackingAnnotation` | RFGS006 |
| This anonymous default export is left untransformed ... | `warnUnnamedDefaultExport` | RFGS007 |
| X is called as a plain function (X()) and also rendered ... | `warnPlainCalledComponentAlsoMounted` | RFGS008 |
| This component is left untransformed because ... "use server" ... | `warnServerDirectiveComponent` | RFGS009 |
| A Hook call shares this call with signal reads ... | `HOOK_IN_CAPTURED_CALL_WARNING`（2箇所） | RFGS001 |
| A Hook call is nested inside this signal read expression ... | `HOOK_IN_CAPTURED_READ_WARNING`（6箇所） | RFGS001 |
| This call runs a function that both calls a Hook and reads signals ... | `HOOK_CALLING_HELPER_WARNING` | RFGS002 |

統合の判断:

- **RFGS001**: 「Hookが読み取りを含む式の中にある」と「Hookを含む呼び出しが、呼び出し自身だけが行う読み取りを共有する」は、Hookをcapture closureに入れないという同じ理由で同じ対処（Hookを独立した文で呼ぶ）になるため1IDにした。
- **RFGS003**: JSXの属性callbackと `children` callbackは、受け取り側がいつ呼ぶかを証明できないという同じ理由で、同じ対処（tracked componentへ移す）になるため1IDにした。

診断の対象外（警告ではないもの、または警告の経路が別のもの）:

- `could not parse ...` の例外（Babelの構文エラーの付加情報）と、`transform.ts` の `throw path.buildCodeFrameError(...)`（不正な async/generator）は、警告ではなくエラーなので対象外。
- `unplugin.ts` の source map パッチ未適用の通知（`reportLoaderPatchSkipped`）と、`loader.ts` の `console.warn` 直接出力は、Managed Transformの診断ではなくbuild設定の通知なので対象外。

既存の検出条件は一切変更していない。既存の診断の出現数は、このリポジトリ内の310ファイル・3組のoption（後述の検証）で、RFGS005が234件、RFGS003が6件だった。他のIDは既存のテストfixtureで発火を確認した。

## 2. 導入した診断ID

| ID | カテゴリ | 内容 |
| --- | --- | --- |
| RFGS001 | Hook inside a tracked read | Hookが読み取り式の中にある、または読み取りだけを行う呼び出しと同じ呼び出しを共有している。対処: Hookを独立した文で呼ぶ。 |
| RFGS002 | Hook-calling helper read | 呼び出された関数がHookを呼び、render内でsignalを読んでいる。対処: componentとして描画する、またはcustom Hookにする。 |
| RFGS003 | Untracked callback read | JSX render propまたは `children` callbackがsignalを読み、所有者を証明できない。 |
| RFGS004 | Uncaptured parameter read | 関数の引数初期化子に `.value` の読み取りが残る（移動を見送った場合）。 |
| RFGS005 | Unverifiable barrel | `useSignalTracking()` がbarrel/re-export経由でしか解決できない。 |
| RFGS006 | Ignored annotation | `@signalTracking` の付いた関数に、boundaryを付けるidentityがない。 |
| RFGS007 | Unnamed default export | 無名の `export default` 関数で、module名からidentityを導けない。 |
| RFGS008 | Plain-called and mounted | componentが通常関数として呼ばれ、かつ `<Component />` としても描画されている。 |
| RFGS009 | Server-directive component | 先頭の `"use server"` directiveを持つmoduleのcomponentが変換されない。 |

IDの扱い:

- IDは `src/internal/diagnostics.ts` の `DIAGNOSTIC_IDS` に一度だけ定義し、各発生箇所は `reportWarning(options, "RFGSxxx", path, text)` で渡す。本文は ID に依存しない。
- 本文は `[react-fine-grained-signals] RFGSxxx: ...` の形にする。ID の文字列を本文に含めることで、端末やbundlerの表示だけを見ても識別できる。
- `reportWarning` は重複抑止の後で診断を生成する。重複した訪問では生成コストを払わない。

## 3. 追加した公開API

```ts
signals({
  diagnostics: { errorOn: ["RFGS001", "RFGS003"] },
});
```

- `ReactFineGrainedSignalsOptions.diagnostics?: ReactFineGrainedSignalsDiagnosticsOptions`
- `ReactFineGrainedSignalsDiagnosticsOptions.errorOn?: readonly ReactFineGrainedSignalsDiagnosticId[]`
- 型 `ReactFineGrainedSignalsDiagnosticId`（`"RFGS001"` ... `"RFGS009"`）
- 定数 `REACT_FINE_GRAINED_SIGNALS_DIAGNOSTIC_IDS`（機械的な列挙用）
- bundlerへ渡す警告に `diagnosticId` プロパティを追加。`code` は従来どおり `"RFGS"`。

設計判断:

- 依頼の形 `diagnostics: { errorOn }` を採用した。既存のオプションはすべてフラットだが、診断の設定を名前空間にまとめておくと、今後の診断オプションを既存のトップレベルと衝突させずに追加できる。
- 未知のIDは、plugin作成時に `TypeError` を投げる。黙って無視すると、typoした診断が警告のまま残り、利用者が気づけないため。
- `errorOn` に `"all"` のような全指定は設けない（必要な診断だけを昇格させるという要件に合わせた）。

## 4. 各Bundlerでの動作

昇格（`errorOn`）は transform の内部ではなく adapter 層（`src/unplugin.ts`）で行う。transform は従来どおり警告を出し、adapter がIDで振り分ける。昇格した診断は、Babel の実行が終わってから報告する。Babel の `try` が実行中に投げられた例外を「parse失敗」に包み直してしまうため、実行中には投げない。

| Bundler | 警告（既定） | `errorOn` で昇格した場合 | 検証 |
| --- | --- | --- | --- |
| Vite | `this.warn` で `code: "RFGS"`、`diagnosticId`、`loc`、code frame付きの警告 | `this.error` が投げ、build が失敗する。1 module につき最初の昇格診断で止まる。 | 実際の `vite.build()` |
| Rollup | Vite と同じ経路（`this.warn`） | `this.error` が投げる。1 module につき最初の昇格診断で止まる。 | adapter の契約レベル（実際のRollup buildは未実行） |
| esbuild | `onLoad` の `warnings` 配列（location付き） | `errors` 配列に入る。昇格した診断はすべて報告され、build が失敗する。 | 実際の `esbuild.build()` |
| webpack / rspack | loader の `emitWarning`（`code`、`loc`、`diagnosticId` を保持） | loader の callback に error を返す。1 module につき最初の昇格診断で止まる。 | loader の単体テスト（実際のwebpack/rspack buildは未実行） |

昇格しなかった診断は、すべての bundler で従来どおり警告になる。

## 8. 未解決事項

1. **1 module につき最初の昇格診断で止まる**（Vite、Rollup、webpack、rspack）: esbuild はすべて報告する。他の bundler でも全件を報告するには、昇格した診断を1つの error にまとめる必要がある。今回は、bundler の error 契約を単純に保つため見送った。
2. **実際の Rollup build 未検証**: webpack/rspack はM18.3レビュー修正後、source map付きの実buildで strict 診断が code frame を保った build error になることを確認した。Rollup はadapter契約レベルの検証に留まる。
3. **Babel 層での strict policy は実装していない**: 変換本体で投げると、transform の `try` が parse 失敗に包み直すため、要件（誤った診断にしない）を満たせない。adapter 層での昇格で足りると判断した。
4. **全件指定や path ごとの重大度は未対応**: 必要になった時点で、別途検討する。
5. **RFGS004〜009 は実リポジトリでの出現が少ない**: 検証は専用の fixture で行った。実プロジェクトでの出現頻度は未計測。
6. **ロードマップ統合**: M18.3の完了状態、実装・検証内容、Rollup実buildの残課題を [v0.3.0 roadmap](README.ja.md) に記録した。

## 10. M18.3レビュー残課題の修正

### webpack/Rspack loader

source map付きtransformの失敗を常にsource mapなしで再実行していたため、diagnostics.errorOnが意図的に投げた診断エラーまで再試行され、同じmoduleの他warningが二重に出る可能性があった。loaderはdiagnosticIdを持つ失敗を昇格診断としてそのままcallbackへ返す。診断IDのない失敗は従来どおりsource mapなしで再試行する。

診断エラーのErrorオブジェクトをそのまま返すため、message/code frame、loc、code、diagnosticIdを維持する。直接loaderテストはsource mapあり・なし両方で、昇格診断、RFGS007 warningが1回だけであること、locationとcode frameを確認する。別のsource map処理エラーを模したloaderテストでは、mapなし再試行と成功が維持されることを確認する。
