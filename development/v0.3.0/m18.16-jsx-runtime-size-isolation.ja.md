# M18.16 — JSX Runtime Size Isolation PoC

## 結果

- 開始HEAD: `7a2bca097b459895c6e46addb7d1a0888be2d908`
- 判定: **明示的なformless JSX Runtimeは約3.1 KB gzipを削減できる。** 効果は定量化できたが、今回は製品コード・公開APIを変更しない。自動Runtime選択はdynamic propsやspreadを見落とす可能性があり不採用。次は、明示lite entryの追加が約3.1 KBの効果に見合う保守負荷かを、React互換性込みで判断する。
- npm依存、package exports、既定`jsxImportSource`、version、bundle budgetは変更していない。release freezeも行わない。

## 測定方法

再実行は`pnpm build:runtime`の後に`node development/v0.3.0/m18.16-measure.mjs`を実行する。スクリプトは一時ディレクトリに`src/runtime/jsx.ts`から実験派生版を生成し、production Vite buildを8回行う。依存環境はWindows x64、Node `v24.21.0`、Vite `8.3.4`、`@vitejs/plugin-react` `6.1.2`、React `19.3.0`、esbuild minifier。各fixtureは同じReactDOM mount scaffoldを持ち、React標準JSX baseline、Core-onlyは各構成の寄与を見るための補助比較である。すべての出力は1つのJS assetで、gzipはlevel 9、Brotliはquality 11。

PoCのformless runtimeは、フォーム専用validation、binding kind、host-prop処理、subscription dispatchを一時ソースから除去し、Signal childrenと通常のsignal属性binding (`title`)を残した。children-only版は直接bindingをすべて除去し、Signal childrenの正規化だけを実装した。ライブラリのsourceや公開entryは変更・コピーしていない。source由来の実験派生ファイルを一時フォルダでViteがcompileし、現在のCore/React adapterをpackage `dist`にaliasしている。

## Consumerサイズ

| Fixture | raw | gzip | Brotli | 含める機能 |
|---|---:|---:|---:|---|
| React標準JSX static baseline | 220,653 B | 68,632 B | 59,076 B | ReactDOM + static React component |
| Core-only | 16,774 B | 5,626 B | 5,143 B | signal生成・更新。Reactなし |
| React JSX + `useSignalValue` | 239,185 B | 74,747 B | 64,661 B | Signal children相当のHooks実装 |
| Full JSX Runtime / Signal child | 258,440 B | 81,261 B | 70,275 B | 現行Runtime、フォーム未使用 |
| Formless Runtime / Signal child | 248,159 B | 78,143 B | 67,662 B | Signal children + 非フォーム属性binding |
| Children-only Runtime / Signal child | 239,802 B | 74,992 B | 64,878 B | Signal childrenのみ |
| Full JSX Runtime / attribute | 258,500 B | 81,286 B | 70,406 B | Signal child + `title` Signal binding |
| Formless Runtime / attribute | 248,219 B | 78,154 B | 67,598 B | 同じConsumer機能、form実装なし |

Formless Runtimeの差分は、比較するConsumerコードを揃えた次の値である。

| 比較 | raw削減 | gzip削減 | Brotli削減 |
|---|---:|---:|---:|
| Full child → formless child | 10,281 B | 3,118 B | 2,613 B |
| Full child → children-only | 18,638 B | 6,269 B | 5,397 B |
| Formless child → children-only | 8,357 B | 3,151 B | 2,784 B |
| Full attribute → formless attribute | 10,281 B | 3,132 B | 2,808 B |

formless bundleでは`Invalid select bindValue`、text/range validation、checkbox-group validationの各markerが消え、signal childが更新された。Chromium smokeではformlessのSignal `title`属性もSignal更新でDOMへ反映され、Console errorとpage errorはなかった。children-only版でもSignal child更新を確認した。

## サイズの読み方と内訳

- Full child bundleはReact標準static appよりgzipで12,629 B大きい。ただしConsumer機能とRFSG Core/React integrationを含む差であり、JSX Runtime単独の費用ではない。
- React標準JSXから`useSignalValue`版への増加はgzip 6,115 B。Core-only fixtureはgzip 5,626 Bだが、Reactなしの別entryなので単純加算・厳密なCore寄与とはみなさない。tree shakingと共通コードの圧縮があるため、Core・React adapter・JSX Runtimeのサイズは独立した加算値にならない。
- `useSignalValue` consumerからFull child consumerへの増加はgzip 6,514 B。これはCore/React統合を共有する代替構成との実測差で、direct JSX pathの総追加差として読む。
- form実装を除去した実測差は3,118 B gzip / 2,613 B Brotli。M18.15の「form markupを追加した差分」と異なり、今回の比較ではform実装コードそのものを派生Runtimeから取り除いた。full fixtureにはform固有markerがあり、formlessにはない。
- Full childとchildren-onlyの差にはform bindingに加えて通常の属性bindingも含まれる。差分6,269 Bをform実装単体の削減量とは解釈しない。

## 実現方法の評価

| 案 | 効果と負担 | 判断 |
|---|---|---|
| 現行Runtimeを維持 | 設定不要で全機能を使える。form未使用でもform実装が残る | 今回は既定を維持 |
| 明示的なlite JSX Runtime entry | Formless PoCで約3.1 KB gzip削減。`jsxImportSource`をlite entryへ指定するか、別runtime specifierを選ぶ必要がある。公開entry、開発用runtime、型、classic JSX fallback、SSR、React Compiler、Fast Refreshの二重保守と試験が必要。フォームpropが動的に到達した場合の明確な診断も必要 | 有望な次段階候補。サイズ効果は確認したが、公開API化は今回行わない |
| Transformによる自動選択 | 自動importを選べれば利用者設定は少ない | 不採用。spread、条件付きprop、変数を経由したpropsを完全に静的判定できる保証がなく、誤選択は実行時互換性を壊す。安全なfallbackを加えると削減効果を薄める |

分割はファイルを移すだけでは削減にならない。PoCではRuntimeからフォーム機能への参照を取り除いた結果、tree shakingでform handlerとvalidationが消えた。製品化するなら、fullとliteの両entryでSignal children、属性binding、SSR、development JSX、型定義の契約を保ち、lite entryでフォームbindingを検出したときに意図が伝わるエラーを出す設計が必要になる。

## 検証と限界

- 8つのproduction Vite fixtureを同じ環境でbuildし、raw/gzip/Brotliを保存した。
- Chromium localhost smoke: Full/formless/children-onlyのSignal child更新、Full/formlessの属性更新、page error/console errorを確認。
- 実験派生版は小さなConsumerでのtree shaking効果を測るPoCであり、SSR/hydration、Concurrent Rendering、StrictMode、React Compiler、Fast Refresh、production app全体での互換性試験ではない。
- 結果JSONと再実行スクリプト: [m18.16-consumer-bundles.json](m18.16-consumer-bundles.json)、[m18.16-measure.mjs](m18.16-measure.mjs)。
- 製品コード・公開API・package/lockfileに変更なし。M18.15と同じく、転送サイズ以外のLCPやHTTP cachingは測っていない。

## 推奨する次の作業

明示的なlite entryの最小実装PoCを独立branchで行い、既存React/Compiler/SSR/Fast Refresh matrixをfull entryとlite entryの双方で確認する。フォームbindingを混ぜたConsumerがlite entryを使った場合の診断、型分離、`jsxImportSource`切り替え時のDXも評価する。約3.1 KB gzipの削減を保ったまま既存契約を維持でき、設定・保守負荷が妥当なら公開候補に進める。今回の計測のみを根拠に既定Runtimeを変更したり、自動選択を行ったりしない。
