# M18.4 — List Rendering Improvement

## 結論

- 作業開始HEADは `e4fd02836fb64c5366d00cb05bacdcf536e0d567`。比較基準はM18でfreezeした `4c15349ce54fad96e73b18dccce13ea9184dca27`。
- `Index`の直接key付与をPoCで測定したが、製品への採用は見送った。初回PoCでは大きな差が出たものの、同じ製品実装を再計測すると効果が再現しなかった。
- `For`も変更しない。Fragmentを取り除く同じ案はcallback数を減らさず、10,000行でmount・prepend・delete・move・unmountが遅くなる計測結果があった。
- 公開API、依存、version、Transform、Collection契約は変更していない。

## 現行実装と更新コスト

`For`はSignal化されたcollectionを親境界で読み、`by(item, index)`をkeyに各callbackの結果をkey付きFragmentで囲む。配列を置換、追加、削除、並べ替えすると親が全itemsをmapし、`by`とchildren callbackをそれぞれの行について呼ぶ。Reactはkeyで行identityとstateを保つが、Fragmentを含む全行をreconcileする。

`Index`は位置をkeyにし、childrenへ現在値を読み直すaccessorを渡す。保存されたaccessorも現在のcollectionを読み、immutable replacementで位置の値が変われば、その行のpropsを更新するためcallbackを再実行する。この契約は維持した。

行オブジェクトのDeep Signalを1か所変更するケースはcollection自体を置換しない。既存の行内`useSignalTracking()`やJSX direct bindingがleafを購読し、`For`親の行callbackは再実行しない。これは`tests/control-flow.test.tsx`のdeep-signal leaf更新とkey呼び出し回数で確認済み。immutableなcollection replacementの全callbackを省くには、行ごとのcacheとdependency boundaryが必要になる。

## 比較した方式と判断

| 方式 | 評価 | 判断 |
|---|---|---|
| row-local Signal購読 / JSX direct binding | 行データのDeep Signal変更では既に局所更新される。immutable replacementでchildrenが読む値の再評価を省くものではない | 現行機能として利用。新しい仕組みは追加しない |
| stable keyed row component / `React.memo` | M10で実装・計測済み。単一更新はcallbackを減らすが、mountとheap、prepend/move/replace/unmountに負担が出た | M10の不採用判断を維持。再実装しない |
| keyed elementへ直接keyを付ける | row componentを増やさずFragment Fiberを省く。callback数は同じ。`For`と`Index`の双方を隔離harnessと製品buildで比較 | 不採用。`Index`の初回PoC結果を製品buildで再現できず、一般的な最適化として根拠不足 |
| callback実行を行ごとに追跡・cacheする | signal依存の再実行を局所化できる可能性があるが、render-time reads、動的依存、Concurrent/abandoned render、cleanup、key変更を管理する新しい境界が必要 | PoC/製品実装は見送り。現在の測定だけでは複雑性を正当化できない |

## 性能測定

比較は同じNode processとfixtureで行い、Node v24.21.0、React 19.3.0、jsdomを使用した。各測定は同じ行component、同じoperation、同じDOM出力で、3 timed samplesの中央値を記録。100/1,000行は1 warmup、10,000行はwarmupなし。GC有効のrunではmount heap差とunmount後のretained heapも測った。実行ホストのCPU/OS詳細は記録していないため、ms値はこの環境での比較値である。

### `Index` — 初回isolated PoC

| 操作 | 1,000行 baseline → 候補 | 10,000行 baseline → 候補 |
|---|---:|---:|
| mount | 502 → 277 ms (-45%) | 3,371 → 1,881 ms (-44%) |
| mount heap差 | 5.88 → 4.59 MB (-22%) | 42.64 → 37.38 MB (-12%) |
| 単一行置換 | 303 → 218 ms (-28%) | 3,006 → 1,278 ms (-58%) |
| append | 243 → 259 ms (+7%) | 966 → 633 ms (-34%) |
| prepend | 409 → 480 ms (+17%) | 1,516 → 1,327 ms (-12%) |
| 中央削除 | 595 → 396 ms (-33%) | 1,958 → 1,211 ms (-38%) |
| move | 438 → 261 ms (-40%) | 1,569 → 1,781 ms (+14%) |
| 全件置換 | 404 → 280 ms (-31%) | 1,425 → 1,813 ms (+27%) |
| unmount | 40 → 32 ms (-20%) | 181 → 181 ms (同等) |

この初回PoCではmount時間・mount heapと複数operationに改善が見られたため、候補を一時的に`Index`製品実装へ適用し、build後の同じharnessで再計測した。この改善幅は再現しなかったため、下記の再測定を採用判断の根拠とする。

### `Index` — 一時実装buildの再測定

| 操作 | 1,000行 baseline → 候補 | 10,000行 baseline → 候補 |
|---|---:|---:|
| mount | 354 → 389 ms (+10%) | 1,551 → 1,715 ms (+11%) |
| mount heap差 | 5.99 → 4.64 MB (-23%) | 42.51 → 37.37 MB (-12%) |
| 単一行置換 | 343 → 455 ms (+33%) | 1,873 → 1,475 ms (-21%) |
| append | 440 → 307 ms (-30%) | 1,505 → 1,749 ms (+16%) |
| prepend | 431 → 321 ms (-26%) | 1,911 → 1,825 ms (-5%) |
| 中央削除 | 327 → 316 ms (-3%) | 1,660 → 1,657 ms (同等) |
| move | 424 → 255 ms (-40%) | 2,681 → 2,214 ms (-17%) |
| 全件置換 | 222 → 281 ms (+26%) | 1,637 → 1,754 ms (+7%) |
| unmount | 30 → 21 ms (-29%) | 289 → 226 ms (-22%) |

これはbuild済みの候補実装とbaselineを同じprocessで比較した3 samplesの中央値。1,000行はmountと単一更新が悪化。10,000行は単一更新/moveが改善したが、mount・append・全件置換は悪化。p25–p75もoperationにより重なりがあり、初回PoCのmount -44%や単一更新 -58%は再現しなかった。方向が不一致な結果を製品改善の根拠とはできない。

PoCの更新callback数は従来実装と候補で同じ。10,000行の単一更新ではcallbackとRow renderが10,000回、appendは10,001回である。Fragment Fiberを減らすだけでは再実行コストを消さない。

unmount後heapはbaseline/候補とも中央値約0.1–0.3 MBだったが、各3 sampleのうち1 sampleに約18–28 MBの外れ値が出た。retained heapの値は採否根拠に使わず、mount heap差のみを参考にする。

### `For` — 同じ直接key付与候補

10,000行GC有効runでは、mountは1,773 → 2,175 ms (+23%)、mount heap差は42.40 → 37.15 MB (-12%)、単一置換は1,740 → 1,394 ms (-20%)、appendは1,667 → 1,477 ms (-11%)だった。しかしprependは2,283 → 4,524 ms (+98%)、中央削除は1,981 → 2,533 ms (+28%)、moveは1,938 → 2,268 ms (+17%)、全件置換は2,328 → 2,387 ms (+3%)、unmountは168 → 203 ms (+21%)。操作全体としてのトレードオフが強く、`For`へは採用しない。

## 製品変更と互換性

PoCでは子callbackを一度実行し、結果がReact elementなら`cloneElement(child, { key: index })`を返し、それ以外は従来どおりFragmentを使った。一時実装のfocused testで返却elementのrefも維持されたが、性能効果が不安定なため`src/utils.tsx`は元のFragment実装へ戻した。最終的な製品runtime/APIは作業開始時の状態を維持する。

最終製品ソースではReact 19上のposition stateとaccessor、StrictMode、Deep Signal更新、`For` key identityに関する既存control-flow testsを実行した。SSRテストでは出力とhydrationに問題がないことを確認し、Concurrent suiteも通過した。一時実装には追加ref保持testも適用した。製品runtime変更が残らないためFast Refresh専用suiteは再実行していない。

最終baselineのライブラリ全体buildとsize checkが成功した。utils import graphはgzip 9.36 kBでbudget 9.69 kB以内。一時候補buildは9.40 kBで、候補による増分は約0.04 kBだった。API・依存・version・package lockは不変。Production browser benchmarkは今回の判断材料に含めず、jsdom測定に基づく数値を実ブラウザ性能保証として扱わない。

M18.3で保留されていたRollup単体buildもfocused smokeを追加して確認した。`diagnostics.errorOn: ["RFGS007"]`で匿名default export fixtureを処理するとRollup buildが失敗し、Rollupの`PLUGIN_ERROR`と元の`pluginCode: "RFGS"`、`diagnosticId`、locationが保持された。その他の診断をwarningとして誤出力しない。diagnostics suiteは43 tests passed。

## 次の実装計画

1. M18.5で`Index`の直接key付与を実ブラウザDOM benchmarkでも測り、Chrome/Firefox/WebKit間の結果、Fast Refresh、React Compiler有効時をqualificationする。move/全件置換が多いUIで採用判断が変わるか確認する。
2. `For`/`Index`の実アプリdogfoodingから、immutable collection replacement時の行callback回数が実測上のボトルネックか記録する。必要性が確認できるまでrow-local callback cacheや新APIを実装しない。
3. M18.6以降で必要なら、keyed row boundary方式を新設計から比較する。abandoned render、依存の入れ替え、cleanup、memoryを含む計測を先に用意し、M10のmemo Row案をそのまま再利用しない。

今回の範囲でv0.3.0へ新しく取り込むruntime最適化はない。`Index`案は実ブラウザで改善が再現できるまで保留し、`For`案・新しい公開API・SVG・Managed Transform redesign・リリース作業も行っていない。
