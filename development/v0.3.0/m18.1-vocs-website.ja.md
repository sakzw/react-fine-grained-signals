- 開始HEAD: `4544ba2176cffe770565e3b1623f5d9f5166bc8a`(M18 exploration記録)

- 主な依存: Vocs 2.10.3、Waku 1.0.0-rc.3、Vite 8.3.4、React 19.3.1、TypeScript 5.9.3

## 結論

`website/`に、ライブラリとは依存管理とbuildが独立したVocsのドキュメントサイトを作った。

- 英語の9ページと、RFSG自身を使う7つのライブデモを持つ。
- 静的生成(`full-static`)とGitHub Pagesのproject path(`/react-fine-grained-signals`)に対応した。
- 現在のライブラリソースを`pnpm pack`したtarballで動かしている(ドッグフーディング)。

ブラウザ検証の結果は次のとおり。

- 静的buildをGitHub Pagesと同じ規則で配信した状態と、Vite dev serverの両方で確認した。
- 全ページの直接アクセス、basePath配下のCSS・JS・icon、7デモのSignal更新が動いた。
- managed transformとJSX runtimeはVocs/Waku(RSC)環境で共存した。
- Consoleにhydration不一致、Hook違反、error、warningは出なかった。
- Vocs 2.10.3がbasePathを付けないskip linkは、静的出力後の小さな補正scriptで直し、Chromium smokeに全ページのskip link検査を加えた。

ライブラリの不具合は見つからなかった。dev serverで見つかったhydration不一致は自作デモの不純なrenderが原因で、デモ側を直した(後述)。

ルートへの変更は3点だけである。

### Vocs CLIを使わない理由

`vocs dev`/`vocs build`は`vite.createServer({ configFile: false, plugins: [react(), vocs()] })`でViteを起動する。そのため、ユーザーのVite plugin(RFSGのtransform)を追加する方法がない。サイトは`vocs/vite`がexportする`vocs()`を使い、CLIと同じplugin構成に`signals()`を加えた`vite.config.ts`で、Viteを直接実行する。

`vocs preview`も使わない。これは`dist/serve-node.js`のNodeサーバーを起動するもので、静的ホスティングとは異なる。代わりに`dist/public`をGitHub Pagesと同じ規則で配信する`serve-static.mjs`を使う。

## ローカルRFSGと公開版の切り替え

### Repository development mode(現在)

1. `node scripts/pack-local-rfsg.mjs`で親リポジトリのルートと`packages/unplugin-react-fine-grained-signals`を`pnpm pack`し、固定名で`website/vendor/*.tgz`に置く。`vendor/`はgitignoreする。
2. `package.json`は`file:./vendor/react-fine-grained-signals.tgz`などで参照する。

この方式の性質:

- `pnpm pack`はprepack buildを実行し、`workspace:`の範囲を書き換える。そのため、`pnpm publish`と同じ中身がinstallされる。ソースはコピーしない。
- Reactはサイトの1コピー(19.3.1)だけに解決された(`node_modules/.pnpm`で確認)。
- 同じソースから作ったtarballはbyte単位で一致した(sha256で確認)。ライブラリが変わるとlockfileのintegrityも変わるため、packした後は`--frozen-lockfile`なしでinstallし、lockfileを更新する。
- 親の位置に依存するのは`pack-local-rfsg.mjs`の既定値だけで、引数か`RFSG_REPO`で変更できる。

### Standalone mode(v0.3.0の公開後)

`pnpm add react-fine-grained-signals@^0.3.0`と`pnpm add -D unplugin-react-fine-grained-signals@^0.3.0`で2行を置き換え、`vendor/`を消す。ほかのファイルは変更しない。

npmには0.2.1までしかないため、standalone modeの実際のinstallとbuildは未確認である。代わりに、`website/`だけをリポジトリ外のディレクトリへコピーし、親workspaceなしで次がすべて成功することを確認した: `pnpm install --frozen-lockfile`、`pnpm typecheck`、`pnpm build`、`pnpm smoke`。

## ページとデモ

ページ: Introduction(`/`)、Installation、Getting Started、Core Signals、React Hooks、Managed Transform、JSX Direct Binding、Deep Signal & Collections、Interactive Examples。

| デモ | 内容 | 使う機能 |
|---|---|---|
| Counter | `useSignal`。`useSignalTracking()`を書かない | managed transform |
| Computed | `useComputed`の連鎖、React controlled input | managed transform |
| Deep Signal | todoの配列とproperty、reactive `Map` | `useDeepSignal`、managed transform |
| Form Binding | text、radio group、checkbox group、単独checkbox、signal childのsummary | JSX runtime(`bindValue`/`bindChecked`) |
| For / Index | 追加、回転、削除 | `react-fine-grained-signals/utils` |
| JSX Direct Binding | signal child、`title`、`hidden`、signal値の`style` entry。component自身が再renderしないことを`peek()`の値で示す | JSX runtime |
| Managed Transform | module-levelのsignal、helper経由のread、computed。`@noSignalTracking`で外した対照が更新されないことを示す | managed transform |

RSCの扱い:

- MDXページとVocsのlayoutはServer Componentである。デモは`'use client'`のファイルだけに置いた。
- transformの`include`は`src/components/**/*.tsx`に限定した。そのため、Server Componentにclient専用のcapture Hookは入らない。
- JSX runtimeはデモのファイルごとにpragmaで有効化した。

内容の管理: `docs/`(日英)を完全なリファレンスとして残す。サイトのページは英語の要約版で、各ページから`docs/`の該当ガイドへリンクする。正本をサイトへ移すかは、サイトの公開時に判断する。

### ドッグフーディングで見つかったこと

- **自作デモのhydration不一致(修正済み)。** 最初のJSX Direct Bindingデモは、render中に`useRef`のカウンタを増やして再render回数を表示していた。
  - dev serverではStrictModeでrenderが2回走るため、server(1)とclient(2)の表示が食い違い、hydrationが失敗した。
  - 静的buildではStrictModeがないため現れなかった。
  - 修正: 最後のrenderが見た値を`clicks.peek()`で表示する純粋なrenderに変えた。ライブラリの問題ではない。
- **faviconのbasePath。** `iconUrl`はbasePathを自動で付けないため、設定でbasePathを前置した。iconを設定しない場合も、ブラウザがoriginの`/favicon.ico`を取りに行き404になる。
- ライブラリ(runtime、JSX runtime、managed transform)の不具合は見つからなかった。

### Windowsでの追加確認

2026-10-17、Node v24.21.0 / pnpm 12.8.1 / Windows x64で追加確認した。`node scripts/pack-local-rfsg.mjs`は2回連続で実行し、Windowsからpnpm起動と同じ固定名tarballの置き換えに成功した。`pnpm install --no-frozen-lockfile`後、再packした状態で`pnpm install --frozen-lockfile`、`pnpm run typecheck`、`pnpm run build`、static previewの直接route(HTTP 200)、`pnpm run smoke`(74項目)、`pnpm run dev`に対する`pnpm run smoke --url http://localhost:5173`(55項目)が成功した。初回dev routeはCold cacheではRSC/SSR/client optimizeとMDX compileのため30秒を超えたが、SMOKE_NAVIGATION_TIMEOUTを180秒にして初回compile後に全件通過した。

## 残課題と制約

- Standalone modeの最終確認は、v0.3.0のnpm公開後にしかできない。
- Vocs 2.10.3の「Skip to content」リンク(`SkipToContent`)はbasePathを付けずに`/<page>#vocs-content`を出力する。`fix-base-path-links.mjs`で静的HTMLを補正し、smokeで各routeのhrefとhydration後のConsoleを確認する。
- GitHub Pagesへの実際のデプロイは行っていない。workflowはテンプレート(`website/deploy/github-pages.yml`)で、actionのSHA固定とPagesの設定が有効化の前提である。
- Waku 1.0.0-rc.3はpre-releaseである。Vocs 2.10.3のpeer要件(`waku >=1.0.0-rc.1`)に従っている。
- browser検証はChromiumだけで行った。Fast Refreshはdev serverで個別に確認していない。
- サイトの出力が14MBと大きい。Vocsが同梱するplayground、検索、言語ハイライトのassetによる。
- `docs/`とサイトのページは内容が重複する。移行方針は上記のとおりである。
- 実行環境はNode 22で、ルートの`devEngines`(Node 24.21.0)とは異なる。
