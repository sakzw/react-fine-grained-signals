# M15.2 — Benchmark validity & transform stress audit

開始main HEAD: `3718387cc97d465726ba4df5597f74a51f3d413e`  
対象: M15.1のstatic destructuring transform、benchmark fixture、React correctness test  
package version: `0.3.0`のまま

## 修正した問題

旧dependent-chain fixtureは初期データが1段の`child`しかなく、2段目から`undefined`をdestructureしていた。したがって、旧M15.1記録のalias-chain時間、capture数、heap列は正しいchain workloadの結果ではなく、比較・性能主張に使えない。M15.1記録のchain行はこの理由で無効とする。

fixtureを件数分の深さを持つ木に修正した。木は深いJSON literalではなく、小さなループで実行時に作る。これにより500件時にparserのnesting制限へ先に当たる状態も避け、destructuring transformそのものを測れる。0/5/20/100/500件について、変換後コードを実行し、初期`Ada`値を検査する。対応する各fixtureではdeep propertyを`Bea`へ書き換え、読み出しが変わることも同じプロセス内で確認する。独立読みでは共有leafの更新後、全aliasの表示値が変わることを照合する。

実際のReact描画については、8段alias chainのmount、leaf deep write、root replacementを検証する回帰testを追加した。React componentの表示は`Ada`→`Bea`→`Cleo`と更新される。

## 計測条件

- Node `v24.21.0`、Windows x64、AMD Ryzen 7 PRO 6850U
- M15 baseline: `696a16ac41c47a245075fe0dfacc2a8f4fd7dc45`のpluginを別worktreeでbuild
- Candidate: 開始main HEADにあるM15.1 pluginを同じ依存runtimeでbuild
- それぞれ新規Node processで1 sample、warmupなし。3-roundケースはround間でbaseline/candidateの順を交互にした
- Transform timerはplugin transform hookだけを計測。Oxc JSX lowering、Babelでのfixture linking、初期値/deep update実行は別の`correctnessValidationMs`
- 500件のchain/independent baselineは1回ずつ試し、60秒で打ち切り。candidate 500件は3プロセスで採取した
- 100件chainは3 roundを採取。小規模と100件のindependent/chain/nestedはそれぞれ3 round
- CPU profileはcandidate 500件chainのtransform区間に限定して取得。profile中はinstrumentation overheadがあるため、profile実行の時間をbenchmark tableに混ぜていない

| independent | 5 | 275 ms | 292 ms | 1,271 | initial + deep update |

| independent | 100 | 2,682 ms | 406 ms | 16,924 | initial + deep update |
| independent | 500 | >60 s timeout | 5,844 ms (3,069–15,051) | 84,522 | initial + deep update |
| alias chain | 5 | 250 ms | 260 ms | 1,003 | initial + deep update |
| alias chain | 20 | 691 ms | 342 ms | 2,452 | initial + deep update |

M15 baselineにはnested static destructuringのdeep trackingがない。baseline nestedは初期値とtransform時間だけを確認し、deep update成功とは記録していない。baseline chain/independent 500のtimeoutは正しいfixtureでの結果であり、完走性能値の代用ではない。M15.1 candidateの500件すべては正しいinitial/deep updateを通過した。

候補500件での`heapUsedDeltaAfterTransformMiB`はchainが約23.45 MiB、independentが約43.68 MiB、nestedが約15.77 MiB（3 sampleの中央値）。これはtransform直後に観測した`heapUsed`の差であって、peak heapでも総allocationでもない。直後にGCした後のheap差も短時間・ノイズを含む観測であり、retentionやleakの証明に使わない。heap snapshotやallocation profileの代わりとして解釈しない。

## 500件chainのprofile

Inspector CPU profileはtransform区間のみ、約8.68秒・3,382 sample。self sampleの上位は以下。

- Babel visitorの展開(`@babel/traverse` `explode$1`): 約1.39秒 (16%)
- `hasTrackedSource`: 約0.81秒 (9%)
- Babel path/traverse処理 (`get`, parent/key/scope setupなど): 複数functionに分散し、各約0.3–0.5秒
- `getStaticConstDestructuredBindings`: 約52 ms
- Scope `crawl`: 約6 ms
- Babel generatorのprint/generate: 約25 ms

このprofileで見える主費用はalias chainのdiagnostic source追跡とBabel visitor/AST traversalの経路管理である。alias fixpoint、visitor展開、scope crawlを完全な総時間へ分離する関数単位のinclusive計測ではないため、これ以上細かい配分は断定しない。少なくともこのprofileではscope crawlとcodegenは主要hotspotではなかった。

M15.1が既に一括destructuring expansionを行うため、scope crawlはこのfixtureで約6 msだった。scope再構築をさらに削る案は測定上の効果が見込めず、製品transformには追加変更をしない。500件candidateは中央値で約5.8秒かかり、round間の幅も広い。巨大な単一render関数のstress制約として扱い、通常規模のbuild保証へ一般化しない。

## 制約と結論

主要なchain benchmark欠陥はfixtureが実行不能な深さになる点だった。修正後、candidateで最大500件の初期値とdeep updateが正しいことを確認した。500件baselineのchain/independentは60秒以内に完了しなかったため、比較倍率は主張しない。100件chainではbaseline 6.56秒、candidate 2.98秒の中央値だが、観測幅は大きい。

M15.1の製品コードは維持した。profileはM15.1のbatch expansionがscope crawl/codegenの反復コストを抑えていることと整合し、追加最適化を支える再現性の高い根拠を示さなかった。M15.1記録中の過去chain値とpeak heap表記は無効/誤解を招くため、現行のbenchmark結果として使わない。新しいJSX/runtime/API契約、package bundle、versionは変更していない。
