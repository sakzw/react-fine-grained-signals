# M10.2 Event Compatibility Closure

## 基準と再現

- 開始基準: `main` / `80c5fc554f7eecbf215d4d208c91533ec82a1299`
- 対象: Writable computedを使ったtext bindingで、React 19のsynthetic `onChange` / `onInput`がnative `input`と共存すること
- package versionは`0.3.0`のまま

JSDOMでは、Reactのprogrammatic value trackerを迂回するnative value setterで値を書き、ユーザー操作に相当するbubble `InputEvent`を一度だけdispatchするfocused regressionを追加した。修正前はsetterが入力を拒否または正規化するケースで、target上のbinding listenerが同期的にDOMを書き戻すため、Reactの委譲`onChange`が発火しないことを再現した。通常の受理、同じgetter値への正規化、異なる値への正規化、textarea、`onInput`との共存も個別に確認する。

最初の実装ではDOM補正を`queueMicrotask()`へ遅延した。Chromium/WebKitのPlaywrightで実際のキーボード入力を行うと、microtask checkpointがtarget listenerとReact委譲listenerの間に発生し得るため、拒否された入力でReact `onChange`が失われることを確認した。JSDOMとFirefoxだけではこの差を検出できなかった。

## 修正

入力setterは引き続きnative `input` listener内で同期的に呼ぶ。補正処理だけを`setTimeout(..., 0)`で次のtaskへ遅らせ、Reactの全委譲handlerにユーザー入力を観測させてからgetterを読み直す。入力ごとのversionと現在のDOM値を確認し、より新しい入力またはReact handlerがDOMを変えている場合は古い補正を破棄する。受理済みの値がgetterと等しい場合は従来の同値判定によりDOM書き込みを行わない。IME composition中は既存どおり`compositionend`まで補正を保留する。

ブラウザE2Eは`fill()`によるprogrammatic value設定を使わず、実際のキー入力で拒否された一文字と受理された一文字を順に入力する。Chromium、Firefox、WebKitすべてで各入力につきReact `onInput`と`onChange`が1回発火し、拒否入力後はDOMがcomputed getter値へ戻ることを確認した。

英語・日本語ガイドの重複していたWritable computed同期説明を各1箇所にまとめ、補正が次のtaskで行われる理由と、`onChange`が拒否処理ではないことを明記した。
