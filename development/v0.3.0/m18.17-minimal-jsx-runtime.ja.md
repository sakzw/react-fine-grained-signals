# M18.17 — Minimal JSX Runtime Qualification

開始HEAD: `c2704bc69b10a46fbc264355c08f9a9112e6a74e`

## 結論

Signal子要素だけを使うConsumer向けに、明示opt-inのLite JSX Runtimeを追加した。Full Runtimeは既定のまま維持する。実際のpackage entryから作った同一Consumerのproduction bundleでFullよりgzip 6,029 bytes、Brotli 5,309 bytes小さく、M18.16で計測した約6.3 KB gzipの差がほぼ維持された。サイズ差と境界の明確さが追加保守コストに見合うため、Full/Liteの2構成を製品APIとして採用する。

## 実装

- `react-fine-grained-signals/lite`、`/lite/jsx-runtime`、`/lite/jsx-dev-runtime`をpackage exportsに追加した。既定の`jsxImportSource`、Full Runtime、binding APIは変更していない。
- Signal子要素・ネストした配列の正規化を小さな`jsx-children`共有moduleへ分離し、FullとLiteが利用する。LiteからFullのbinding dispatcherをimportしない。
- Liteは通常のReact JSX、host element/Fragment、React component、Signal children、配列内Signal、classic `createElement` fallback、development `jsxDEV`をサポートする。SignalをReact component props/childrenへ渡しても自動unwrapしない。
- Liteのintrinsic JSX型はSignal-valued props、`bindValue`、`bindChecked`、Signal style entryを許可しない。JavaScriptやspreadで渡されたフォームbinding・Signal host propは、誤ったDOM状態に進まず明確な`TypeError`を出す。
- `jsxImportSource: "react-fine-grained-signals/lite"`を英語・日本語ガイドとWebsiteへ記載した。Runtimeのソース書き換えやchunk hash/minified export名への依存はない。

## Package Consumerの測定

Node 24.21.0、Vite 8.3.4、`@vitejs/plugin-react` 6.1.2、React/React DOM 19.3.0、esbuild minifyを使い、同じSignal counter Consumerを実package `dist`からproduction buildした。gzipはlevel 9、Brotliはquality 11。JS output fileの合計を計測した。

| 構成 | Raw bytes | gzip bytes | Brotli bytes |
| --- | ---: | ---: | ---: |
| Full JSX Runtime | 258,411 | 81,240 | 70,412 |
| Lite JSX Runtime | 240,537 | 75,211 | 65,103 |
| React JSX + `useSignalValue` | 239,156 | 74,734 | 64,636 |
| tarball install後のLite Consumer | 240,537 | 75,211 | 65,103 |

FullからLiteへの差はraw 17,874 bytes、gzip **6,029 bytes**、Brotli **5,309 bytes**。LiteはReact JSX + `useSignalValue`よりgzip 477 bytes大きい。 tarballを独立Consumerへinstallした場合もpackage distを直接使う場合と同じ出力サイズとなった。

出力のbinding markerを確認した。Fullはform validation markerを含む。Liteはform binding validation、checkbox group validation、select validationを含まず、Lite固有のform/Signal属性拒否診断は含む。従ってLiteへform dispatcher自体は戻っていない。Vite production outputをChromiumで操作し、Full、Lite、Hooks、tarball-installed Liteすべてでボタン操作によりSignalが`0`から`1`へ更新し、browser console/page errorがないことを確認した。Packed ConsumerのTypeScript検査も通過した。

再現スクリプトは[`m18.17-measure.mjs`](./m18.17-measure.mjs)、数値は[`m18.17-consumer-bundles.json`](./m18.17-consumer-bundles.json)に保存した。通常sandbox権限での再実行は、Windows上でpnpm child process/store lockが`EPERM`となり失敗した。M18.18で許可済みの子プロセス実行として再試行したところ、tarball pack/install、packed Consumer typecheck、4構成のVite buildとChromium smokeが成功し、同じexact bytesを再現した。原因はmeasurement scriptやpnpm lockfileでなく、実行環境の子プロセス権限だった。

## 正確性・互換性

- Lite focused testはSignal更新時に親renderが増えないこと、StrictMode、ネストした配列、Fragment、React component passthrough、非対応binding診断、classic fallback、`jsxDEV`、SSR/hydration、Suspense retry、Full Runtimeとの同一tree共存を確認する。
- 対象focused React suiteは5 files / 132 tests passed。React CompilerのLite Signal child caseを含むsuiteは1 file / 30 tests passed。
- `pnpm typecheck:runtime`、`pnpm build:runtime`、`pnpm size`が成功し、既存`index-full` gzip budget 24,704 Bを変更せず通過した。`tests/lite-jsx-types.tsx`はSignal childrenと配列を許可し、Signal host props/form binding/style entryを型で拒否する。
- React 19、Vite production build、React Compiler、SSR/hydration、StrictMode、Suspense、classic/dev JSX entry、同一treeのFull/Lite共存を確認した。共有`useSignalValue`経路はcross-copy interopに対応し、既存cross-copy suiteがその基盤を検査するが、Lite entryを跨ぐ専用の2 package-copyテストは未追加。
- Vite HMR/Fast RefreshについてLiteのdev serverで編集を伴う実ブラウザー検証は未実施。`jsxDEV` entryの動作はunitで確認済みだが、これをFast Refresh qualificationとは扱わない。対応 bundlerのうち実ビルドを今回実施したのはVite。Webpack/RspackのLite fixtureは未確認。

## 採否と残課題

Liteは実測で約6.0 KB gzip削減し、React JSX + Hook実装に近いサイズを保ちながらSignal childを親renderなしで更新する。設定は既存の`jsxImportSource`選択だけで、Full defaultを変えず、追加variantも増やさない。型・runtime guardは限定的でform dispatcherをLiteへ含めず、公開APIの保守コストも小さいため採用した。

残課題はLite固有のFast Refresh実ブラウザー検証、Webpack/Rspack package Consumer build、duplicate package copyを跨ぐLite-specific interop確認。これらは明示opt-in APIの追加確認として残し、既定Full Runtimeの互換性を変える変更はしない。サイズ計測では`index-full`予算を引き上げていない。npm publish、version/tag、GitHub Release、Pages deploy、release freezeは実施していない。
