# M17.7 — Ownership & call resolution qualification

- 開始基準: `main` / `d9df0c84da801c434672ad02995c556bbf2d050a`(M17.6.3終了時点。作業開始時のmain HEADと一致)
- 作業ブランチ: `claude/gracious-darwin-vo10zj`
- 中間commit: `c69aee6`(規則の置き換え)。その後の独立reviewの指摘を同じマイルストーン内で修正した
- 終了HEAD: 本記録をcommitした時点のHEAD(報告に記載)
- 比較対象: 変更前のmanaged transform(`d9df0c8`)、v0.2.1と同じambient方式(v0.3の`transform: "inject"`)、仕様に基づく期待値

## 結論

Managed transformが「この呼び出しはcaptureしなくてよい」と判断する規則に、構造的な穴が2つあった。

1. **calleeのrootの形で判定していた。** `unresolvedCallMayRead()`は、組み込み名の判定で除外できなかったcallを、call chainのrootが識別子・`this`・配列/objectリテラルのどれかで振り分け、それ以外(条件式、論理式、sequence、IIFE、別のcall)は無条件に「読まない」としていた。rootがプリミティブだけのリテラルや、グローバル(`Object`、`Array`、`Reflect`)の場合も除外していた。rootはcalleeの実体を何も証明しないため、`(flag ? extStore : other).total()`のような組み込みと無関係な名前でもstale renderになった。
2. **証明していない値を「所有するdata」として扱っていた。** すべての関数parameterをDeep(props相当)とみなしていたため、組み込み配列methodのcallback、`reduce`の累積値、IIFEやhelperの引数に入った外部objectの`map`/`toString`がcaptureされなかった。組み込みが呼び返す関数(`items.map(extFn)`)、再代入された関数・object、`push`で外部値を入れた配列も同様だった。

さらに、helper関数の本体は`.value`の直接readしか調べておらず、`function total() { return cart.total(); }`のように未解決callだけでSignalを読むhelperを`{total()}`で呼ぶとcaptureされなかった。

これらを個別のホワイトリスト追加ではなく、判定規則の置き換えで修正した。

- calleeは「証明できたもの」だけを除外する。到達方法(rootの形)は判定に使わない。
- 組み込みが呼び返す関数も証明の対象にする。
- parameterをDeepとするのは、componentのpropsと、Deepな配列の要素を受け取るcallbackと、module内でDeepな値だけを渡して呼ばれるhelperに限る。
- 所有する配列へ外部の値を書き込むと、その配列の信頼を下げる。

規則を置き換えた後、別のagentが独立に敵対的reviewを行い、置き換えで新たに入った回帰3件(うち1件は変換時間の指数的増加)と、変更前から存在した漏れ7件を再現した。いずれも修正した(B.2)。

差分実行プローブ(自作732ケースとreviewの約100ケース、各`auto`/`all`)で再現した追跡漏れは、仕様上の制約として記録したもの(暗黙のuser code、`auto`の関数選択)を除いてすべて解消した。性能面では、propsへの組み込みcallのcapture数は変わらない。分割代入したprops(`const { items } = props`)はDeepとして扱えるようになり、captureは401件から1件に減った。examplesのcapture数は`auto` 7件・`all` 9件のまま変わらない。

公開判断は **CONDITIONAL GO**(末尾参照)。

## A. 判定規則

### A.1 callee resolution(`unresolvedCallMayRead`)

同期callは、calleeが次のいずれかだと証明できる場合だけcaptureしない。それ以外は、calleeがどのような式で得られたかに関係なくcaptureする。

| calleeの種類 | 保証の根拠 | 備考 |
|---|---|---|
| Hook・component形の名前(条件式・論理式・sequenceのどの枝でも) | 規約。Hookをclosureへ移さないため常に直接呼ぶ | `(flag ? useA : useB)()`も直接呼ぶ |
| 再代入されない局所・module関数、その場で呼ぶ関数式 | 本体を解析して判定する(`targetFunctionMayReadTrackedValue`) | 本体の未解決callも判定に含める(今回追加) |
| 標準グローバルの関数・静的member(`Math.max`、`JSON.stringify`、`String`、`Object.keys`など。`standardGlobals`) | engine組み込み | 一覧にない自由変数(`window.store`、`globalThis.x`)はcaptureする。`.call`/`.apply`/`.bind`は除外しない |
| 標準classの新しいinstanceのmethod(`new Intl.NumberFormat().format()`、再代入・method差し替えのない局所変数を含む) | 新しいinstanceはprototypeのmethodだけを持つ | |
| libraryまたはReactからのimport(名前付き・namespace) | 自パッケージとReact | |
| 組み込み名のmethod(`pureMethodNames`)で、receiverが所有するdata(A.2のBuiltin以上) | receiverの出所の証明 | 名前だけでは判定しない |

`new C(...)`とtagged template(`` tag`x` ``)も同じ考え方で扱う。標準のconstructor・tag(`new Date()`、`String.raw`)だけを証明済みとし、`new Promise(executor)`はexecutorの証明も必要とする。`new Object(x)`は`x`自体を返すため、標準instanceとはみなさない。その場で呼ぶ`async`関数は、最初の`await`までがcall中に実行されるためcaptureする。

関数やobjectを解決できるのは、名前が再代入されず、moduleがそのmemberを差し替えない場合に限る。差し替えには、`o.total = ...`、`Object.assign(o, ...)`・`Object.defineProperty(o, ...)`、分割代入やloop headによる書き込み、`const a = o`の別名を経由した書き込みを含む。

さらに、組み込みが呼び返す関数(`map`/`filter`/`reduce`/`sort`などの第1引数、`replace`/`replaceAll`の第2引数、`Array.from`/`JSON.stringify`/`JSON.parse`/`Object.groupBy`の第2引数)は、inline関数、再代入されない局所関数、標準グローバル、`null`/`undefined`のどれかでなければcaptureする。

### A.2 Ownership(値の出所)

| 分類 | 保証すること | 該当する値 |
|---|---|---|
| Deep | 値そのものと、そこから読む値がすべて信頼できる | primitive値の式(literal、template、算術・比較、単項演算)、Deepな値だけのliteral(配列・data propertyだけのobject)、componentのprops、`useState`等のstate、それらのmemberと分割代入した部分(defaultもDeepの場合)、Deepな配列の要素を受け取るcallbackのparameter(`reduce`の累積値を除く)、moduleがDeepな値だけを渡して直接呼ぶhelperのparameter、要素を保つ・返す組み込みmethodをDeepに適用した結果、primitiveを返す組み込みmethodの結果 |
| Builtin | 値そのものは組み込み(配列)で、methodは組み込み。要素は信頼しない | Deepでない要素を含む配列literal、`map`/`flatMap`/`concat`の結果、外部の値を`push`等で書き込まれた配列 |
| Unknown | 何も証明しない | 上記以外。import、module-levelの値、`this`、custom Hookの結果、`reduce`/`reduceRight`の結果、上記以外の関数のparameter(IIFE、Hook、export・escapeしたhelper、ほかの関数が呼ぶcallback)、名前付きmemberへ非primitiveを代入されたobject、再代入される変数 |

合成規則:
- 条件式・論理式は弱い方の枝。sequenceは最後の式。`=`代入は右辺。
- memberは、objectがDeepのときだけDeep。
- 再代入されない局所変数は初期化式の分類。ただし、その変数への書き込み(`mutationLimit`)で上限を下げる。要素への代入と`push`/`unshift`/`splice`/`fill`/`set`/`add`でDeepでない値を入れるとBuiltinまで、名前付きmemberへprimitive以外を代入するか、`Object.assign`等で書き込むとUnknownまで下がる。
- 書き込みは`const`の別名(`const a = list`、`const { part } = list`、`copy = list`のような`let`への代入)を経由しても数える。名前で追えない場所(`holder.list = list`)へ格納した値はUnknownにする。
- 再代入されるparameterはUnknown。
- 判定は式nodeごとに1回だけ行い、結果を保存する。判定中のnodeを再び尋ねるとUnknownを返す。その仮の答えに依存した結果は保存しない。このため、自分の引数を自分へ渡す再帰helperのparameterはUnknownになる(安全側)。深さ上限(16)を超えた場合もUnknownになる。
- helper本体の判定(`cachedTargetMayRead`)も同様に、相互再帰の途中で仮に「読まない」とした答えに依存した結果は保存しない。

### A.3 推測として扱うもの(証明ではない)

型情報がないため、次の2点は証明ではなく規約として扱う。どちらも公開ドキュメントに明記した。

1. **componentのprops、React state、そこから読む値は、組み込みと同名の独自methodを持たないplain data。** `function App({ store }) { return store.map() }`で`store`が独自の`map`を持ちSignalを読む場合は追跡しない。
2. **組み込みや演算子が暗黙に実行するuser codeは追跡しない。** tracked alias以外の値に対する`String(x)`、`` `${x}` ``、`"" + x`、`join`での要素の`toString`、getter、`toJSON`、iterator、`Symbol.species`、Proxy trapが対象。明示的に書かれたcall(`x.toString()`)は追跡する。

2.は既存の振る舞い(M17.6 T8でtracked operandのToPrimitiveだけを対象にした)を規則として明文化したもの。暗黙の呼び出しをすべて安全側に倒すと、未証明の値を含む演算と組み込みcallのほとんどがcaptureされる。

## B. 発見した不具合

再現はすべてReact 19 + jsdomの実行で行った。期待結果は「Signal更新後にDOMが更新される」こと(明示的なtracking boundaryと同じ結果)。v0.2.1と同じambient方式(`transform: "inject"`)では、B1〜B9の全ケースが正しく更新された。したがって全件がv0.2.1からの回帰である。

### 修正内容

- `unresolvedCallMayRead`をA.1の規則に置き換え、`callChainRoot`と`literalHoldsValues`を削除した(B1、B2、B8)。
- `standardGlobals`(標準グローバルのallowlist)、`calledBackIsKnown`(callback引数の証明)、`isStandardInstance`を追加した(B2、B4、B8)。
- `ownership`を整理した。primitive値の式をDeepにし、`parameterOwnership`(B5、B9)、`elementCallbackOwnership`、`helperArgumentOwnership`、`mutationLimit`(B7)を追加した。分割代入したpropsもDeepとして扱う。
- `targetFunctionMayReadTrackedValue`で本体の未解決callも判定する(B3)。再帰helperのため、判定中はcacheにfalseを置く。
- `resolveReferencedFunction`は再代入される名前を解決しない。`resolveKeyedFunction`は、再代入されるroot、またはmodule内で再代入されるliteralのslotを解決しない(B6)。
- `callNameIsHook`は条件式・論理式・sequenceのcalleeの各枝を調べる。B1の修正で条件式のcalleeをcaptureするようになったため、Hookを選ぶ式をclosureへ移さないよう先に塞いだ。
- B.2: ownershipのmemo化(`memoizedOwnership`)、`freshInstanceConstructor`、別名と分割代入・loop headの書き込みを追う`mutationLimit`/`memberWrite`/`referenceAlias`、`objectMayBeRewritten`、`constructorMayRead`、`templateTagMayRead`、async IIFEの判定、`cachedTargetMayRead`の循環対策。

## C. 既知の制約

### 仕様上の制約(追跡漏れを許容する)

| 制約 | 理由 | 影響 |
|---|---|---|
| props・stateを組み込みと同名の独自methodを持たないdataとして信頼する | 型情報がない。安全側に倒すと、propsへの組み込みcallのcaptureが1件から601件に、出力が23.6kBから38.0kBになり、renderは約1.5〜3.5倍になった(D.2) | `<List items={extStore} />`のように、Signalを読む独自methodを持つobjectをpropsで渡すと追跡しない。`useSignalTracking()`を置けば追跡できる |
| 暗黙のuser code(ToPrimitive、getter、`toJSON`、iterator、`Symbol.species`、Proxy trap)は、tracked alias以外の値では追跡しない | 安全側に倒すと、未証明の値を含む演算と組み込みcallのほとんどをcaptureすることになる | `` `${extStore}` ``、`String(extStore)`、`[extStore].join()`、importしたobjectのgetterは追跡しない。v0.2.1方式(`inject`)では追跡される |
| `auto`は`.value`のreadなど静的に認識できるreadを持つ関数だけを選ぶ | 既存の選択規則 | 未解決callだけでSignalを読むcustom Hook(`function useIt(v) { return v.total(); }`)は変換されない。`@signalTracking`か`useSignalTracking()`で指定する |
| module外へ渡した値が、見えないコードで書き換えられることは追わない | 1ファイル単位の変換 | `const list = items.slice(); fill(list); list.pop().map()`で`fill`が外部の値を入れる場合 |
| 深さ上限(16)を超える出所の連鎖、自分へ引数を渡す再帰helperのparameterはUnknown | 変換時間の上限と循環の扱い | 100段のhelper chainでcaptureが1件増えた(安全側) |
| 代入が呼ぶsetter(`ks.x = extStore`)はtracked aliasでなければ追跡しない | 暗黙のuser codeと同じ扱い | setterの中でSignalを読む場合 |
| `[...gen()]`のspreadによるgeneratorの反復 | M17.6から既知。`for...of`と`Array.from(gen())`はcaptureする | generatorの中のread |
| 条件式などのどちらかの枝がHook名のcall(`(cond ? extFn : useX)()`)は直接呼ぶ | Hookをclosureへ移さないため | Hookを条件で選ぶ時点でRules of Hooks違反 |
| moduleが書き換えた標準global(`Math.total = fn`) | allowlistは名前で判定する | 標準globalへの代入 |
