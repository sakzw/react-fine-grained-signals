# Phase 9 M1.3 — Targeted hot-path validation

## Scope and result

M1.3 started from accepted `main` at `b4fc12a48b25266dcdd62ef0fb171e760a7d98ed` (`perf: reduce readable representation overhead`). It used read-only path audits followed by isolated, one-change paired ablations. The accepted implementation changes only the private speculative-computed cache promotion path; it keeps public APIs, runtime semantics, and the `alien-signals/system` boundary unchanged.

The supported optimization is narrow: when a computed has already been checked as promotable, its dependency validation no longer checks `speculativeCachePromotable` a second time. The original check remains on all other dependency-validation callers. The change passed the full runtime and transform suites.

M1.3's final full matrix completed all 958 planned tasks with no failures. It shows a repeatable paired improvement against unchanged-current in `computed/dirty-read`, while that case remains slower than v0.1.1. Effect fan-out at 16/64, source access, and computed equality suppression also remain below v0.1.1 parity. M1.3 is complete; this report does not start M2 or set a new release gate.

## Causal audits and candidate selection

Three read-only audits mapped effect fan-out, computed dirty-read, source-read, and managed React paths. The fan-out measurement includes synchronous write propagation, Alien edge traversal, RFSG queue scheduling, callback execution, scopes, tracking, and cleanup. Its current measurements cannot allocate the gap to any one edge or scope. The computed dirty-read workload has one source and one lazy computed; on each read it checks the pending dependency, recomputes, and relinks/settles the dependency. Source-read's ordinary unobserved path still passes through collector/interop checks and core settlement, but the earlier guarded read bypass was slower. Managed React includes React `act`, scheduling and commit time in addition to RFSG tracking, so its result does not isolate hook or watcher overhead.

Candidate C's immediate source-read diagnostic was neutral (`1.004×` candidate/control, IQR `0.959–1.013`, 3/4 faster). Therefore the final M1.2 source-read ratio movement from M1b cannot be attributed to Candidate C. Similarly, final current/v0.1.1 ratios describe the full runtime relative to the released artifact; they do not isolate the M1.3 code change.

The accepted helper change preserves the clean initialized-node return, rejects non-promotable caches before dependency-map validation, and performs the same dependency revision checks for promotable caches. The large spread in several fan-out and equality diagnostics is retained in the raw records; those results are not presented as causal shares or combined into a score. The tested zero-depth fast path did not help effect fan-out, so no speculative/render isolation scope was removed.

Raw records are indexed in [`benchmarks/phase9/attribution/README.md`](../../../benchmarks/phase9/attribution/README.md). Source/read, fan-out, and managed React remain open investigation areas where the audits did not establish a safe, repeatably beneficial change. In particular, bypassing the graph-backed React render watcher with direct notification was not accepted: batching, dirty settlement, duplicate-copy reads, render/commit races, and abandoned renders all need preservation.
