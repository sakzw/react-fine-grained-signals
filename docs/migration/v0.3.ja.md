# v0.3への移行

## `deepSignal`のリアクティブcollection

v0.3では、同一realmの`Map`、`Set`、`WeakMap`、`WeakSet`がnested collectionを含め既定でリアクティブになります。`collections` optionと旧read-only Map/Set viewは削除されました。既存の呼び出しは第2引数を削除すれば型checkできますが、collectionの変更が例外になることを前提にしたコードは確認してください。`.value`経由の変更はcollectionを更新し、readerへ通知します。

旧opt-in引数を削除します。

```ts
const state = deepSignal(new Map<string, { count: number }>());
```

collection rootと、plain objectまたは配列にnestedされたcollectionに対応します。dependencyの追跡と通知には`state.value`経由で読み書きしてください。元のcollectionや`.peek()`から変更すると通知は発生しません。同一realmの標準collectionのみ対応し、クラスインスタンスなど他の不透明な値はProxy化しません。

Weak collectionは列挙できません。method呼び出し時にkeyを正規化します。Symbol keyの可否はnative runtimeのWeakMap/WeakSet key規則に従います。dependencyとidentityの詳細は[Core primitives](../guides/core-primitives.ja.md#reactive-collections)を参照してください。

## JSXフォームbinding

RFSG JSX runtimeでの `value={signal}` と `checked={signal}` は、暗黙のdirect DOM bindingではなくなりました。通常の `value` / `checked` propsはReactのcontrolled inputとして動作します。この方式では `signal.value` を渡して `onChange` からsignalを更新してください。DOMをsignalへ直接同期する場合は、書き込み可能なsignalを明示propsへ渡します。

```tsx
<input bindValue={name} />
<textarea bindValue={name} />
<input type="checkbox" bindChecked={enabled} />
<select bindValue={selected}>
  <option value="a">A</option>
  <option value="b">B</option>
</select>
<select multiple bindValue={selectedMany}>
  <option value="a">A</option>
  <option value="b">B</option>
</select>
```

`bindValue`は単一selectに`FormBindableSignal<string>`、multiple selectに`FormBindableSignal<string[]>`を使います。text系inputとtextareaも`bindValue`、個別checkboxは`FormBindableSignal<boolean>`を使う`bindChecked`でbindingできます。同じform ownerと`name`を持つradio groupは各radioのstring `value`と共有`FormBindableSignal<string>`、checkbox groupは各checkboxのstring `value`と共有`FormBindableSignal<string[]>`を使います。`signal()`、`useSignal()`、書き込み可能な`computed({ get, set })`と`useComputed({ get, set })`はこのcapabilityを持ちます。汎用フォームコンポーネントではbinding propを`FormBindableSignal<T>`として宣言してください。`Signal<T>`へ型を広げるとJSXで使えるbinding capabilityが失われます。読み取り専用computedは引き続き拒否されます。このcapabilityはTypeScript専用のbrandで、実行時プロパティを追加しません。runtimeはパッケージ内部のprivate brandと書き込み可能性を検査します。multiple selectの変更値は`selectedOptions`のoption順に取得し、後からのoption追加・削除後もsignal値を再適用します。radio／checkbox groupはnative clickで共有signalを更新し、Reactのdelegated event処理後に必要な補正を行います。旧形式のsignal-valued `value` / `checked` はruntimeでmigration errorとなり、RFSGのJSX型もbuild時に拒否します。`bindValue`と`value`/`defaultValue`、または`bindChecked`と`checked`/`defaultChecked`は併用できません。bindingがDOM stateを所有するため、競合propsは拒否します。これらのbinding propsを認識するのは `jsxImportSource: "react-fine-grained-signals"` の場合だけです。標準のReact JSX runtimeでは認識されません。

text bindingはnative `input`、checkboxとselect bindingはnative `change` eventでsignalを更新し、Reactの `onChange` / `onInput` はそのまま呼ばれます。direct listenerがReactのbubble handlerより先にsignalを更新するため、値を正規化するhandlerは正規化後の値をsignalへ書き戻せます。handlerが編集を無視しても入力は拒否されません。IME変換中はcomposition終了まで外部text DOM更新を遅らせ、input typeが対応する場合はfocused fieldの選択範囲を維持します。form resetはsignalの最新値へ戻り、resetがcancelされた場合はDOMとsignalを変更しません。SSRではserver/clientの初期signal値を一致させてください。hydration前の編集はbinding attach時に上書きされる場合があります。完全な契約は[JSX bindings](../guides/jsx-bindings.ja.md#form-binding)を参照してください。

## managed tracking transform

v0.3ではmanaged transformの追跡境界が変わりました。v0.2.1は関数本体全体を `try` / `finally` scopeで囲んでいたため、destructuring、helper、関数が戻る前に呼ばれるcallbackなど、同じ同期call stack上で実行されたreadを収集しました。v0.3はtop-levelで `useSignalCapture()` を呼び、同期的だと静的に証明できるsignal readを個別にwrapします。ユーザーが書いたHookを通常どおりtop-levelに保ちますが、captureされる式の範囲は狭くなります。

upgrade前に、destructuring、aliasやdynamic key、importしたhelper、JSX render prop、`children` callbackにreadが隠れていないか確認してください。pluginは1 moduleずつ解析するため、callbackがいつ実行されるかを決めつけられません。対応patternは[plugin guideの追跡契約とdiagnostics](../../packages/unplugin-react-fine-grained-signals/README.ja.md#managed-tracking契約)を参照してください。`mode: "all"`で関数を多く選んでも、不透明なhelperや遅延callback内のreadをmanaged transformが捕捉できるようになるわけではありません。

| read pattern | v0.3 managedの動作 | 移行方法 |
| --- | --- | --- |
| 選択済み関数内の`state.value.user.name` | 同期read式としてcaptureします。 | 完全なreadをcomponentまたはcustom Hook内に見える形で置きます。 |
| `const { user } = state.value; user.name` | `.value`の後にproxy propertyを読むため、そのproperty readはcapture範囲外になり、更新を逃す可能性があります。このdestructuringにはdiagnosticが出ます。 | `state.value.user.name`と直接読むか、ambient deep-proxy tracking用に明示的な`useSignalTracking()`を残します。 |
| `const alias = signal; alias.value` | 単純なlocal aliasを解決できる場合、直接の`.value` accessは追跡されます。 | aliasをlocalに保ち、選択された関数内で`.value` accessを見える形にします。 |
| `const { value } = signal` | signal accessorのdestructuringは追跡対象ではなく、captureを迂回することがあります。 | 選択された関数内で`signal.value`と直接読みます。 |
| `const profile = state.value.profile; const { name } = profile` | 最初の`.value`式はcaptureされますが、後からdestructuringで隠したproperty readを検出できない場合があります。 | `state.value.profile.name`と直接読むか、ambient deep-proxy tracking用に明示的な`useSignalTracking()`を使います。 |
| 同一module内の同期helper | `auto`でreadを静的に追跡し、同期呼び出し位置でcaptureできます。 | 同期呼び出しを維持し、更新を確認します。 |
| import helper | `auto`でhelper本体を解析して呼び出し側を選ぶことはできませんが、呼び出し側が選択済みなら同期call位置でcaptureできる場合があります。 | 他の静的readまたは明示opt-inで呼び出し側を選び、確認します。readが隠れたままなら呼び出し側へ移すか、明示ambient trackingを残します。 |
| JSX render prop / `children` callback | 選択済み関数がcapture中に同期呼び出しする場合はreadをcaptureできます。別componentがproducer関数から戻った後に呼ぶ場合、ownershipはcallbackへ引き継がれません。静的に見えるfunction-valued propにはwarningが出る場合があります。 | 実際に呼び出すcomponent内にreadを置くか、同期実行とambient ownershipを検証したruntime boundaryを使います。 |
| `signal[key]`のようなruntime key | 他の対応readで関数が選択されればcaptureできますが、このreadだけでは`auto`選択されません。 | 静的readで選択するか、明示的opt-in/ambient trackingを使います。 |

先頭文に直接importした明示的な`useSignalTracking()`は、`transform: "managed"`でもruntimeのambient boundaryとして残ります。pluginはこれを`useSignalCapture()`へ置換しません。`.value`式のない`task.done`のようなdeep proxy readはper-read captureだけでは見えないためです。これは明示tracking利用者のstale-render回帰を直します。`mode: "manual"`は明示callまたは`@signalTracking`を認識し、`"auto"`は静的に検出したreadから選択し、`"all"`は対象JSX componentを広く選びます。選択modeは、選んだ関数のcapture意味を変えません。

移行時は次の順に確認してください。

1. 可能ならsignal readをcomponentまたはcustom Hook自身の実行位置に置き、その関数内で見える形にします。
2. helperやcallback自身にreadを所有させる必要がある場合は、ReactがcomponentまたはHookとして呼び出す関数へreadを移すか、同期ambient collectionが必要な関数には明示的な`useSignalTracking()`を残します。`transform: "inject"` は選択関数に同じbest-effortのambient boundaryを挿入します。[React hooks](../guides/hooks.ja.md#追跡境界)の注意点を確認してください。
3. 静的に検出したreadで関数を選ぶには `mode: "auto"`、`useSignalTracking()` または `@signalTracking` でopt-inするには `"manual"`、条件を満たす関数をすべて選ぶには `"all"` を選びます。`mode` は選択方法、`transform` は選択した関数でのreadの捕捉方法を制御します。
4. build diagnosticsを確認し、対象signalを書き換えて各componentの更新を検証します。stale renderingは許容する制約ではなく、移行時に解消する不具合です。

明示的なlexical boundaryが必要な場合は、runtimeの `useManagedSignals()` と `try` / `finally` を引き続き使えます。このscope内で同期的に実行される読み取りは、同期的に呼ぶhelper内も含めて追跡されます。pluginのmanaged出力によるper-read captureとは同等ではありません。[React hooks](../guides/hooks.ja.md#pluginを使わずに厳密な境界を作る)を参照してください。

`useDeepSignalValue`はprimitive専用のままです。plain object／array snapshotのprototypeを評価しましたが、更新ごとのコストが選択subtree全体に比例し、retained heapの計測も安定したメモリ保証を示すにはばらつきが大きいため採用していません。deep objectではprimitive fieldを選択するか、追跡境界内で読む方法を使ってください。
