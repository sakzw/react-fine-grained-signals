# Migrating to v0.3

## Reactive collections in `deepSignal`

In v0.3, `deepSignal` makes same-realm `Map`, `Set`, `WeakMap`, and `WeakSet` values reactive by default, including nested collections, and the read-only Map/Set views v0.2.1 returned for them are gone. Review code that relied on collection mutations throwing: mutations through `.value` now update the collection and notify readers.

A collection can also be the root:

```ts
const state = deepSignal(new Map<string, { count: number }>());
```

Collection roots and collections nested in plain objects or arrays are supported. Read and write through `state.value` so dependencies are tracked and notified. Mutating the original collection or a collection obtained through `.peek()` bypasses notifications. Only same-realm standard collections are supported; class instances and other opaque objects remain unproxied.

Weak collections cannot be enumerated; their keys are normalized on method calls, and Symbol keys follow the native runtime's WeakMap/WeakSet key rules. See [Core primitives](../guides/core-primitives.md#reactive-collections) for dependency and identity details.

Values that v0.2.1 stored as opaque collections are now validated as reactive state, so review these cases before upgrading:

- A `Map`/`Set` subclass, a collection from another realm (for example `vm` or an iframe), a frozen `Map`/`Set`, or a collection with own properties throws when it is stored. Convert it to a plain same-realm `Map`/`Set` first, or keep it outside `deepSignal`.
- Objects or arrays used as `Map` keys or values, or as `Set` members, are now proxied like any other nested plain object, so the same rules apply to them: frozen, sealed, or otherwise non-extensible objects and objects with accessor properties throw when stored, including in the initial `deepSignal(...)` value. Looking up a key never validates it: `has`/`get`/`delete` with an absent frozen or opaque key returns `false`/`undefined`.
- Reads through the collection return reactive proxies, so `state.value.map.get(key) === rawObject` and comparisons against raw Set members are now `false`. A `WeakMap`/`WeakSet` stored in state is also returned as a proxy (`state.value.weakMap !== rawWeakMap`). Compare through `state.value`, or use stable ids.

## JSX form bindings

`value={signal}` and `checked={signal}` no longer create implicit direct DOM bindings in the RFSG JSX runtime. Ordinary `value` and `checked` props now keep React's controlled-input behavior. Pass `signal.value` and update the signal from `onChange` for that model. For direct DOM synchronization, use the explicit writable-signal props:

```tsx
<input bindValue={name} />
<textarea bindValue={name} />
<input type="checkbox" bindChecked={enabled} />
<select bindValue={selected}>
  <option value="a">A</option>
  <option value="b">B</option>
</select>
<select multiple bindValue={selectedMany}>
  <option value="a">A</option>
  <option value="b">B</option>
</select>
```

`bindValue` supports text-like, number, and range inputs with `FormBindableSignal<string>`, textareas, single selects with `FormBindableSignal<string>`, and `multiple` selects with `FormBindableSignal<string[]>`; `bindChecked` supports individual checkboxes with `FormBindableSignal<boolean>`. Number and range bindings preserve the DOM string and do not convert through `valueAsNumber`; range min/max/step normalization follows native browser semantics. Radio groups sharing a form owner and `name` use one `FormBindableSignal<string>` with a string `value` on each radio. Checkbox groups sharing a form owner and `name` use one `FormBindableSignal<string[]>`. `signal()`, `useSignal()`, writable `computed({ get, set })`, and writable `useComputed({ get, set })` values retain this capability. If a reusable component accepts a binding, type its prop as `FormBindableSignal<T>`; widening it to `Signal<T>` erases the compile-time capability, while readonly computed values remain rejected. The capability is a TypeScript-only brand and adds no runtime property; the runtime checks the package's private signal brand and writability. Multiple-select changes read `selectedOptions` in option order, and option insertion/removal re-applies the current signal value. Radio and checkbox groups update the shared signal from the native click and defer corrective group writes until React's delegated event handling completes. A signal-valued legacy `value` or `checked` prop throws a migration error at runtime, and the RFSG JSX types reject it at build time. Do not combine `bindValue` with `value`/`defaultValue` (except the string `value` each radio or checkbox-group option requires) or `bindChecked` with `checked`/`defaultChecked`: the binding owns that DOM state and conflicting props are rejected. A binding prop or a conflicting prop explicitly set to `undefined` counts as absent. These props work only with `jsxImportSource: "react-fine-grained-signals"`; the regular React JSX runtime does not interpret them.

Two v0.2.1 patterns have no direct replacement:

- `value={signal}` on elements other than form controls (`<option>`, `<li>`, `<meter>`, `<progress>`, `<data>`) was a one-way attribute binding in v0.2.1 and now throws the same migration error. Pass `signal.value` and let the owning component re-render, or move the read into a small component.
- `bindValue` accepts `text`, `search`, `tel`, `url`, `password`, `email`, `number`, and `range` inputs, textareas, and selects. `date`, `color`, `hidden`, and other unsupported input types that v0.2.1 bound through `value={signal}` throw `bindValue: text-like, number, or range input/textarea/select only.` Use React's controlled `value={signal.value}` with an `onChange` handler for unsupported types.

A click handler that calls `preventDefault()` cancels the edit: the binding restores the previous signal value after the event unless something wrote a different value meanwhile. A handler that cancels the click and synchronously writes the same value the user clicked to cannot be told apart from the binding's own write, so that write is reverted too; write it after the event instead (for example after a confirmation).

Text bindings update on native `input`, select bindings on native `change`, and checkbox and radio bindings on the target's native `click`, before React synthesizes `onChange` from that click. React `onChange`/`onInput` handlers still run. If a click handler calls `preventDefault()`, the binding restores the previous signal value once the event has finished, unless a handler wrote another value in the meantime. The direct listener writes the user edit into the signal before React's bubbled handler, so a handler that needs to normalize an edit can write the normalized value back; ignoring the edit does not reject it. IME composition defers external text DOM writes until composition ends, and changed values preserve the focused selection range where the input type supports it. Form reset restores the latest signal value; canceling reset leaves the current DOM and signal untouched. For SSR, server and client initial signal values must match; an edit made before hydration can be overwritten when the binding attaches. See [JSX bindings](../guides/jsx-bindings.md#form-bindings) for the full contract.

## JSX runtime choices

The Full runtime selected by `jsxImportSource: "react-fine-grained-signals"` remains opt-in and retains the supported Signal-child, host-attribute, style, and explicit form-binding contract. v0.3 also adds an optional Lite runtime at `react-fine-grained-signals/lite` for ordinary React JSX plus Signal children. Lite does not support Signal-valued host attributes, style bindings, `bindValue`, or `bindChecked`. Choosing Lite is not required when upgrading from v0.2.1. It can reduce a bundle only when Full is absent from the same eagerly loaded chunk; package size varies by consumer and bundler.

## TypeScript changes

- `signal()`, `useSignal()`, and writable `computed({ get, set })` / `useComputed({ get, set })` return `FormBindableSignal<T>`, a subtype of `Signal<T>`. Passing them where `Signal<T>` is expected still works, but a variable inferred from `signal(0)` no longer accepts a plain `Signal<number>`: annotate it as `let count: Signal<number> = signal(0)`.
- `computed` and `useComputed` gained a writable overload. Utility types that read the last overload, such as `Parameters<typeof computed<number>>[0]`, now resolve to `WritableComputedOptions<number>`; spell the getter type out (`() => number`) instead.
- `FormBindableSignal<T>` is checked contravariantly for bindings that can write any string: `<input bindValue>` and `<textarea bindValue>` reject a signal typed as a narrower union such as `signal<"a" | "b">`. Radio, select, and checkbox-group bindings, which only write rendered option values, still accept it.

## React Hook dependency contracts

`useComputed` keeps the first getter closure when dependencies are omitted, so this mode is for getters that read Signals only. When a getter captures props, React state, or another non-Signal value, pass every such value in an explicit dependency array. At one Hook call site, do not switch between omitted and explicit dependencies, change the explicit array length, or change between getter-only and writable computed capability; these invalid changes now throw instead of allowing an old computed closure to remain in use. Keep explicit dependency positions stable.

`useSignalEffect` treats omitted dependencies and `[]` as equivalent and allows switching between those two forms. Both keep the initial callback across ordinary React renders. If the callback captures non-Signal values, list them; keep an explicit array's length and positions fixed. A length or omitted/explicit-nonempty mode change throws.

`useDeepSignalValue` may omit dependencies for a selector that reads only deep Signal state; it retains its initial selector closure. Pass `[]` for explicit empty dependencies, or list captured props/state such as `[prefix]`. Its omitted/explicit mode and explicit array length must remain stable. None of these APIs automatically tracks props or React state. See the [Hooks guide](../guides/hooks.md#usecomputed) for examples.

## Managed tracking transform

The managed transform changed its tracking boundary in v0.3. The v0.2.1 transform wrapped the function body in a `try` / `finally` scope, so synchronous reads made anywhere on that call stack—including destructuring, helpers, and callbacks invoked before the function returned—were collected. The v0.3 transform instead calls `useSignalCapture()` at the top level and wraps individual signal reads when the transform can prove that the read is synchronous. This keeps authored Hooks at their normal top-level positions and avoids the old generated `try` / `finally` shape, but narrows which expressions are captured.

The selection and capture phases are distinct. In `mode: "auto"`, a function needs a statically recognized read or explicit opt-in to be selected. The plugin analyzes one module at a time and does not inspect an imported helper's body to select its caller. A synchronous imported-helper call may be captured at its call site only after the caller already has a managed boundary. A hand-written `useSignalTracking()` call and `transform: "inject"` provide a best-effort ambient boundary, not exact lexical ownership. For an explicit lexical scope, use `useManagedSignals()` with `try` / `finally`; see the [Hooks guide](../guides/hooks.md#exact-boundary-without-the-plugin).

Before upgrading, audit code that hides reads behind dynamic aliases or keys, imported helpers, JSX render props, and `children` callbacks. Destructuring from a tracked value is captured by managed mode: static `const` object patterns are expanded into ordered reads, and other patterns (defaults, rest, computed keys, arrays, `let`, assignments, and for-of loop heads) are evaluated as authored inside one capture. The plugin analyzes one module at a time and cannot assume when a callback is invoked. Follow the [plugin guide's tracking contract and diagnostics](../../packages/unplugin-react-fine-grained-signals/README.md#managed-tracking-contract) for the supported subset. `mode` only selects functions; `mode: "all"` does not make an opaque helper or deferred callback visible to managed capture.

| Read pattern | v0.3 managed behavior | Migration action |
| --- | --- | --- |
| `state.value.user.name` directly in a selected function | Captures the `.value` expression. Deep proxy property reads performed within that expression remain part of the captured synchronous evaluation. | Keep the complete read visible in the component or custom Hook. |
| `const { user: { profile } } = state.value; profile.name` | Supported for nonempty `const` object patterns made only of static identifier keys, identifier bindings, and nested object patterns, with no TypeScript annotations or reassignment. The source and intermediate properties are evaluated once in order; later reads such as `profile.name` are captured too. | Other patterns (defaults, rest, computed keys, array patterns, annotations, `let`, destructuring assignments, and destructuring loop heads) are captured as one evaluation of the authored pattern, and their bindings are tracked as aliases. A pattern whose initializer calls a Hook is left uncaptured with a warning. |
| `const alias = signal; alias.value` | A direct `.value` access through a simple local alias is tracked when the transform can resolve the alias. | Keep the alias local and the `.value` access visible in the selected function. |
| `const { value } = signal` | Destructuring a signal accessor is not a supported read and can bypass capture. | Use `signal.value` directly in the selected function. |
| `const profile = state.value.profile; const { name } = profile` | Supported when the alias is statically tracked and the destructuring meets the same `const` subset, including static nested object patterns. | No change needed for other pattern shapes either; they are captured as authored. |
| Same-module synchronous helper | Reads can be statically followed in `auto` mode and captured at the synchronous call site, including calls made inside inline callbacks, IIFEs, and local getters, and helper results used as aliases. Calls with an unresolvable callee (imported or module-level objects, `useCallback` results) are captured as a precaution; Hook calls never are. | Keep the call synchronous and verify updates. |
| Callback, argument, `in`, spread, or `for...of` over a tracked value | `items.filter((item) => item.done.value)`, `JSON.stringify(state.value.profile)`, `"key" in state.value.profile`, `{ ...state.value.profile }`, and `for (const task of state.value.tasks)` are captured as whole synchronous expressions. `for...of` captures each iterator step lazily, preserving early exit and iterator closing; `for...in` runs the native loop and captures each step the same way. Hook calls are never moved into a capture; a Hook that shares a call with a tracked read keeps the call direct, and reads inside that callee are reported with a warning. | No change needed; keep the expression synchronous and call Hooks in their own statements. |
| Imported helper | Its body is not inspected to select a caller in `auto`; a synchronous call can still be captured at its call site when the caller is selected. | Select the caller through another visible read or opt-in, then verify. For an otherwise hidden read, move it into the caller or preserve explicit ambient tracking. |
| JSX render prop or `children` callback | Reads can be captured when the selected function invokes the callback synchronously inside its capture. If another component invokes it after the producer returned, ownership does not travel with the callback. A statically visible function-valued prop read can produce a warning. | Put the read in the component that actually invokes it, or use an explicit runtime boundary only when invocation is synchronous and its ambient ownership is verified. |
| Runtime key such as `signal[key]` | Captured when another supported read selects the function; a dynamic-key read alone does not select it in `auto`. | Add a static read/explicit opt-in, or use explicit ambient tracking. |

An explicit first-statement `useSignalTracking()` remains an ambient runtime boundary even when `transform: "managed"` is enabled. The plugin preserves that call instead of replacing it with `useSignalCapture()`, because capture scopes cannot see deep proxy property reads that have no `.value` expression. This repairs the stale-render regression for explicit tracking users. `mode: "manual"` recognizes the explicit call or `@signalTracking`; `mode: "auto"` selects from statically detected reads; `mode: "all"` selects eligible JSX components. These selection modes do not change the capture semantics of a selected function.

For a migration:

1. Keep reactive reads at the component or custom-hook execution site when possible, with the signal read visible in that function.
2. For a helper or callback that must own a read, move the read into a component/custom Hook that React actually invokes as a Hook or component, or keep an explicit `useSignalTracking()` call when synchronous ambient collection is intended. `transform: "inject"` inserts the same best-effort ambient boundary for automatically selected functions; it retains the ambient-boundary caveats in [React hooks](../guides/hooks.md#tracking-boundary).
3. Choose `mode: "auto"` to select functions from statically detected reads, `"manual"` to opt in with `useSignalTracking()` or `@signalTracking`, or `"all"` to select eligible JSX components. `mode` controls selection; `transform` controls how selected functions capture reads.
4. Check build diagnostics and verify each migrated component by changing the signal it reads. A stale render is a migration failure, not an acceptable limitation.

The runtime `useManagedSignals()` plus `try` / `finally` form remains available when an explicit lexical boundary is needed. It tracks synchronous reads executed inside that boundary, including reads made by synchronously called helpers. It is not equivalent to the plugin's per-read managed output; see [React hooks](../guides/hooks.md#exact-boundary-without-the-plugin).

`useDeepSignalValue` remains primitive-only. A plain-object/array snapshot prototype was evaluated, but its per-update cost scaled with the whole selected subtree and retained-heap measurements were too noisy to support a stable memory claim. Select a primitive field or keep the component inside a tracked read boundary for deep objects.
