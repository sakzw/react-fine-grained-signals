# Migrating to v0.2

This guide covers the public API and dependency changes when upgrading from v0.1.1 to v0.2.

## Render tracking hooks

v0.1.1 exposed two different hooks with the same name. Their import paths identify two different tracking contracts; migrate them separately.

### Root API: bare, best-effort tracking

The root `useSignals()` became the root `useSignalTracking()`:

```tsx
// v0.1.1
import { useSignals } from "react-fine-grained-signals";
```

```tsx
// v0.2
import { useSignalTracking } from "react-fine-grained-signals";

function Counter() {
  useSignalTracking();
  // Read signals during render.
}
```

This is the small, best-effort tracking boundary.

### `/runtime` API: managed, exact tracking

The separate `/runtime` `useSignals()` alias became `/runtime` `useManagedSignals()`:

```tsx
// v0.1.1
import { useSignals } from "react-fine-grained-signals/runtime";
```

```tsx
// v0.2
import { useManagedSignals } from "react-fine-grained-signals/runtime";

function Counter() {
  const scope = useManagedSignals();
  try {
    return <output>{count.value}</output>;
  } finally {
    scope.finish();
  }
}
```

This is the managed, exact render-tracking boundary. When the transform plugin is available, its default `transform: "managed"` mode is the recommended exact boundary and inserts this `try/finally` scope automatically. Manual `useManagedSignals()` is the plugin-free alternative. The advanced `transform: "inject"` mode inserts the root best-effort `useSignalTracking()` boundary instead.

## Managed scope method

`ManagedSignalsStore.f()` has been removed. Replace `scope.f()` with `scope.finish()`.

## Transform plugin

### Upgrade the plugin together with the runtime

Upgrade `unplugin-react-fine-grained-signals` to v0.2 in the same change as `react-fine-grained-signals`. The v0.1.1 plugin emits code against v0.1.1 runtime contracts that v0.2 removed: its default managed mode imports `useSignals` from `react-fine-grained-signals/runtime` and closes each scope with `store.f()`, and its inject mode imports the root `useSignals`. With the v0.2 runtime, that output fails to build or throws at render. The v0.1.1 plugin's peer range (`^0.1.1`) does not include v0.2, so your package manager reports the mismatch.

### Annotation comments were renamed

The plugin's opt-in and opt-out comments were renamed. The v0.2 plugin does not recognize the old names and does not warn about them, so update every occurrence:

| v0.1.1 | v0.2 |
| --- | --- |
| `@useSignals` | `@signalTracking` |
| `@noUseSignals` | `@noSignalTracking` |

- With `mode: "manual"`, a component opted in with `@useSignals` is no longer transformed and stops re-rendering on signal writes until it is changed to `@signalTracking`.
- A function opted out with `@noUseSignals` is transformed again in `auto` or `all` mode until it is changed to `@noSignalTracking`. Check opt-outs that keep the transform away from code that must not get a hook boundary, such as React Server Components.

### File extensions are matched case-insensitively

The plugin now matches source file extensions without regard to case, so `App.TSX`, `App.JSX`, and similar files are transformed like `App.tsx`. v0.1.1 skipped them. `.cjs`/`.cts` files are still excluded.

### Custom `importSource` wrappers

If the plugin's `importSource` points at your own package that re-exports RFSG, update that wrapper with the runtime. The v0.2 plugin imports `useSignalTracking` from the wrapper's root (inject mode) and `useManagedSignals` from its `/runtime` entry (managed mode, the default), and calls `finish()` on the managed scope. A wrapper that still re-exports only `useSignals` breaks the generated code.

## Alien Signals dependency

`alien-signals` changed from a peer dependency to a normal dependency of RFSG, pinned to an exact version (`3.2.1`) because RFSG builds on its low-level `alien-signals/system` module. If your application installed it only to satisfy RFSG v0.1.1's peer dependency, you can remove that direct dependency. Keep it in your own dependencies if your application imports Alien Signals directly; your copy and RFSG's do not need to be the same version.

## Mixing v0.1.x and v0.2

Mixing v0.1.x and v0.2 is not supported; upgrade every package that bundles or depends on RFSG together. v0.2 signals use a new identity brand, so a v0.1.x copy does not recognize them as signals and v0.2 does not recognize v0.1.x signals. What happens to a signal from the other generation depends on where it is used:

- As a JSX child, it fails loudly: React reports an object child.
- As a host prop, it is not recognized as a binding and is passed through as an ordinary prop value. The DOM gets the signal object itself, not its value, and never updates: `className` or `value` renders as `"[object Object]"`, and a boolean attribute such as `disabled` or `hidden` is set even when the signal holds `false`.
- In control-flow utilities such as `Show` and `Match`, it is not recognized either, so the signal object itself is the condition and is always truthy.
- Through effects or hooks, reads are not reactive.

Several copies of v0.2 on one page still interoperate.

## Effects

Nested effects keep v0.1.1's behavior: an effect created while another effect runs is disposed when that effect re-runs or is disposed. `untracked()` now also suppresses tracking by another installed copy of RFSG.

## deepSignal tracking

- Array mutation methods no longer subscribe the code that calls them. An effect that pushes to an array no longer re-runs on every later push to that array.
- `Object.keys`, `for...in`, `Object.hasOwn`, and `hasOwnProperty.call` re-run when keys are added or removed, not when a property's value changes. A value read only through `Object.getOwnPropertyDescriptor(...).value` is no longer tracked; read the property itself.
- Keys inherited from `Object.prototype` (`constructor`, `toString`, ...) are reactive in dictionary-style objects.
- Writing through an object that inherits from a deep proxy (`Object.create(state.value).x = 1`) defines the property on that object, as an ordinary assignment does, and leaves the deep state unchanged.
- `includes`, `indexOf`, and `lastIndexOf` on a deep array now find the original object you stored, not only the proxy it reads as. In v0.1.1, `items.indexOf(a)` returned `-1` for a stored object `a`, so `items.splice(items.indexOf(a), 1)` removed the last element instead.

## JSX and hooks

- A host prop can switch between a plain value and a signal without remounting the element or its children. Bound host elements are no longer wrapped in an internal component; bindings attach through a ref on the element, and your own `ref` is still called with the element.
- Bound `value`/`checked` survive a form reset: `form.reset()` and React 19's reset after a `<form action>` restore the signal's current value. Write the signal to clear a field.
- `useSignalValue()`, signal children, and bound host props no longer accept a `deepSignal` in TypeScript, because they follow root replacement only. Use `useDeepSignalValue()` or read deep state in a tracked component.
- The package root now exports `createElement`, the classic factory compilers fall back to for `<div {...props} key="k" />` under `jsxImportSource`. It is not meant to be called directly.
- A signal placed inside an array child (`[a, sig]`) now renders with a key derived from its position in that array.
- A bare `useSignalTracking()` window now closes when React starts committing, so descendants' layout effects and ref callbacks are no longer attributed to it.
