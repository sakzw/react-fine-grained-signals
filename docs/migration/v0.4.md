# Migrating to v0.4

v0.4 is a breaking release that removes the parts kept only for compatibility and narrows the public API. Upgrade the runtime and the build plugin together (`0.4.x` with `0.4.x`), and read each section below that touches code you have.

| Area | v0.3 | v0.4 |
| --- | --- | --- |
| Loaded copies of the package | Copies interoperated | Install one copy; a mix throws |
| Classic `createElement` | `react-fine-grained-signals` | `react-fine-grained-signals/jsx` |
| JSX import source | `react-fine-grained-signals` | `react-fine-grained-signals/jsx` |
| Lite import source | `react-fine-grained-signals/lite` | `react-fine-grained-signals/jsx/lite` |
| Generated-code entry | `react-fine-grained-signals/runtime` | `react-fine-grained-signals/internal` (not public API) |
| Hand-written strict boundary | `useManagedSignals()` | Removed; use the plugin, a leaf hook, or `useSignalTracking()` |
| Omitted vs `[]` dependencies | Different modes in `useComputed` and `useDeepSignalValue` | Same everywhere |
| Writable computed Hook | `useComputed({ get, set })` | `useWritableComputed({ get, set })` |
| React | `>=19.0.0` | `>=19.3.0` |
| `Show` / `Match` callback value | `NonNullable<T>` | `Truthy<T>` |
| Writable signal type | `FormBindableSignal<T>` | `Signal<T>` |
| `deepSignal(...).peek()` | `T` | `DeepReadonly<T>` |
| `Map` / `Set` in `deepSignal` | Reactive | Untracked; use `deepCollectionSignal` |
| Plugin `reactCompiler` default | `"auto"` | `"opt-out"` |

## Install one copy of the package

v0.3 let several loaded copies of `react-fine-grained-signals` exchange reactive reads through a shared protocol. v0.4 removes that protocol, which makes every signal read cheaper and the core smaller (`signal` alone is about 1.6 kB gzip smaller).

Each copy now keeps its own graph, so a second copy is an error rather than a silently stale value:

- Reading another copy's signal from inside an `effect`, a `computed`, or a tracked component throws `Multiple copies of react-fine-grained-signals are loaded; install a single copy`.
- `isSignal` throws for a signal that another copy created.
- A plain read made outside any `effect`, `computed`, or tracked component cannot be detected: it returns the current value and updates nothing.

Remove the duplicate from the install. Run your package manager's dedupe (`pnpm dedupe`, `npm dedupe`), or make the bundler resolve one copy (Vite: `resolve.dedupe: ["react-fine-grained-signals"]`; Rollup: the `dedupe` option of `@rollup/plugin-node-resolve`). A package that ships its own stores should declare the library as a peer dependency. A v0.1.x copy next to v0.4 is not detected and stays unsupported, as before. Mixing v0.3 and v0.4 copies is not supported and is not specially handled.

## Entry points

The root no longer exports `createElement`, and the JSX runtimes moved under `/jsx`. The old entries are removed without aliases, so a stale import fails to resolve.

| Before | After |
| --- | --- |
| `react-fine-grained-signals` (`createElement`) | `react-fine-grained-signals/jsx` |
| `react-fine-grained-signals/jsx-runtime` | `react-fine-grained-signals/jsx/jsx-runtime` |
| `react-fine-grained-signals/jsx-dev-runtime` | `react-fine-grained-signals/jsx/jsx-dev-runtime` |
| `react-fine-grained-signals/lite` | `react-fine-grained-signals/jsx/lite` |
| `react-fine-grained-signals/lite/jsx-runtime` | `react-fine-grained-signals/jsx/lite/jsx-runtime` |
| `react-fine-grained-signals/lite/jsx-dev-runtime` | `react-fine-grained-signals/jsx/lite/jsx-dev-runtime` |
| `react-fine-grained-signals/runtime` | `react-fine-grained-signals/internal` |

`/utils` is unchanged. In practice you change the JSX import source wherever you set it:

```json
{ "compilerOptions": { "jsx": "react-jsx", "jsxImportSource": "react-fine-grained-signals/jsx" } }
```

```tsx
/** @jsxImportSource react-fine-grained-signals/jsx */
```

Use `react-fine-grained-signals/jsx/lite` for the Lite runtime. The same applies to the Vite `react({ jsxImportSource })` option and to bundler aliases. Both JSX entries now export `createElement`, `Fragment`, the `JSX` namespace, and the `SignalChild` type.

`/internal` holds what the build plugin's generated code imports (`useSignalCapture`). It is not public API and is outside semver. If you pass a custom `importSource` wrapper to the plugin, it must re-export `useSignalCapture` from its `/internal` entry (it used to be `/runtime`). Use the plugin at the same release line as the runtime.

## `useManagedSignals` is removed

`useSignalTracking()` is now the only tracking boundary you write yourself. `useManagedSignals` and `ManagedSignalsStore` are gone from the package entries, and the plugin no longer recognizes a hand-written `useManagedSignals()` boundary. Replace a `try` / `finally` boundary with one of:

- the build plugin with `transform: "managed"` (the default), which captures statically proven synchronous reads;
- the leaf hooks `useSignalValue` and `useComputed`;
- `useSignalTracking()`, with the best-effort limits in the [hooks guide](../guides/hooks.md#tracking-boundary). With React Compiler in the build, a hand-written `useSignalTracking()` component needs `"use no memo"`.

## Hook dependency arrays

Omitting `dependencies` now means `[]` in `useComputed`, `useDeepSignalValue` and `useSignalEffect` alike. Switching between omitted and `[]` is no longer an error. A length change still throws, and switching between omitted (or `[]`) and a non-empty array is now reported as a length change. The `UseComputedModeChangeError` and `UseDeepSignalValueModeChangeError` errors are gone.

`useComputed({ get, set })` moves to `useWritableComputed({ get, set }, deps?)`. `useComputed` accepts a getter only in its types, so the runtime read-only/writable capability check (`UseComputedCapabilityChangeError`) is no longer needed and was removed; plain JavaScript that still passes `{ get, set }` gets a writable computed without an error. A fixed-length violation of `useWritableComputed` throws `UseWritableComputedDependencyLengthChangeError`. The primitive `computed({ get, set })` is unchanged.

## Plugin option `reactCompiler: "auto"` is renamed

The value that adds `"use no memo"` to every transformed function is now `"opt-out"`. The behavior is the same; the old name suggested the plugin detected React Compiler, which it never did. It is still the default, so only a config that spelled out `reactCompiler: "auto"` changes: write `"opt-out"` or drop the option. Any value other than `"opt-out"` or `"off"` now throws when the plugin is created, with a message that names the rename for `"auto"`.

## React 19.3

The peer dependency is `react >=19.3.0`. React 19.3 fixed `useSyncExternalStore` missing store changes made while an `<Activity>` is hidden, and the library's tests assume that behavior. React 19.0 to 19.2 are no longer supported.

## TypeScript changes

- **`Signal` and `ReadonlySignal` are nominal.** An object with only `value` and `peek()` is not a `ReadonlySignal`, matching `isSignal`. A structural readable passed to `useSignalValue` needs a cast. `ReadonlySignal<T>` stays covariant in `T`.
- **`Signal<T>` is invariant in `T`.** A `Signal<"a" | "b">` cannot be passed where `Signal<string>` is expected. Option-based bindings (radio, select, checkbox group) still accept a literal-union signal.
- **`FormBindableSignal` is removed** without an alias. Replace it with `Signal`. `signal()`, `useSignal()`, `useWritableComputed()` and `computed({ get, set })` return `Signal<T>`, so annotating a variable as `Signal<T>` no longer erases the binding capability.
- **`Show` and `Match`** pass `Truthy<T>` to a function child. `Truthy<T>` removes `null`, `undefined`, `false`, `0`, `""` and `0n` from `T` (it is exported from `/utils`). The exported `MatchProps` type is removed (it was a props type for `Match`, which `Match`'s overloads already describe); type a `Match` element through `Match` itself.
- **`deepSignal(...).peek()` returns `DeepReadonly<T>`.** Object properties are `readonly`, arrays are `ReadonlyArray`, `Map` and `Set` become `ReadonlyMap` and `ReadonlySet`, and `WeakMap` and `WeakSet` lose `set`, `add` and `delete`. Writing through `peek()` is a compile error; change state through `.value`. At runtime `peek()` still returns the raw object.
- **`DeepSignal<T>` is never a `Signal<T>`.** Code that passed one where a `Signal<T>` was expected (a binding, a writable parameter) needs to read and write through `.value`. For reading it still counts as a `ReadonlySignal<T>` when `T` has no arrays or collections to make `DeepReadonly<T>` differ from `T`; the `For`, `Index`, `Show` and `computed` inputs keep working.

## Collections moved to `deepCollectionSignal`

`deepSignal` now tracks plain objects and arrays only, so an app that never stores a `Map` or `Set` no longer loads the collection support (`deepSignal` and its hooks go from 14.59 to 9.95 kB gzip together with the interop removal). If you store `Map`, `Set`, `WeakMap` or `WeakSet` values in a deep signal, switch to `deepCollectionSignal` (and `useDeepCollectionSignal`):

```ts
import { deepCollectionSignal } from "react-fine-grained-signals";

const state = deepCollectionSignal({ tags: new Set<string>(), counts: new Map<string, number>() });
state.value.tags.add("react");
```

What changes in `deepSignal`:

- A `Map`, `Set`, `WeakMap` or `WeakSet` root is a type error and throws a `TypeError` that points to `deepCollectionSignal`.
- A nested collection is an untracked value, like a `Date`. It keeps its identity, and the signal notifies only when the property holding it is assigned a different value. `state.value.tags.add(x)` is **not** notified, and its type still allows the call, so search for these mutations when you upgrade.
- A plain object or array cannot be shared between a `deepSignal` and a `deepCollectionSignal`: wrapping the same raw object with both, or assigning a proxy from one into the other, throws.

`useDeepSignalValue` accepts either kind. `DeepCollectionSignal<T>` and `DeepSignal<T>` are separate types.

## Checklist

1. Install one copy of the library; run your package manager's dedupe.
2. Update every `jsxImportSource`, pragma, and bundler alias to the `/jsx` entries.
3. Replace `useManagedSignals` boundaries; replace `useComputed({ get, set })` with `useWritableComputed`.
4. Move `Map` / `Set` state to `deepCollectionSignal`, and look for mutations of nested collections inside `deepSignal`.
5. Replace `FormBindableSignal` with `Signal`, and fix `Signal<T>` assignments that relied on covariance.
6. Raise React to 19.3 or newer.
7. Upgrade the plugin to the same `0.4.x`, and change `reactCompiler: "auto"` to `"opt-out"` if you set it.
