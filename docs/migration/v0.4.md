# Migrating to v0.4

v0.4 is a breaking release that removes the parts kept only for compatibility and narrows the public API. Upgrade the runtime and the build plugin together (`0.4.x` with `0.4.x`), and read each section below that touches code you have.

| Area | v0.3 | v0.4 |
| --- | --- | --- |
| Loaded copies of the package | Copies interoperated | Install one copy; a mix throws |
| Classic `createElement` | `react-fine-grained-signals` | `react-fine-grained-signals/jsx` |
| JSX import source | `react-fine-grained-signals` | `react-fine-grained-signals/jsx` |
| Lite import source | `react-fine-grained-signals/lite` | `react-fine-grained-signals/jsx/lite` |
| Generated-code entry | `react-fine-grained-signals/runtime` | `react-fine-grained-signals/internal` (not public API) |
| Hand-written strict boundary | `useManagedSignals()` | Removed; use the plugin, a leaf hook, or `useSignalTracking()` |
| Omitted vs `[]` dependencies | Different modes in `useComputed` and `useDeepSignalValue` | Same everywhere |
| Writable computed Hook | `useComputed({ get, set })` | `useWritableComputed({ get, set })` |
| React | `>=19.0.0` | `>=19.3.0` |
| `Show` / `Match` callback value | `NonNullable<T>` | `Truthy<T>` |
| Writable signal type | `FormBindableSignal<T>` | `Signal<T>` |
| `deepSignal(...).peek()` | `T` | `DeepReadonly<T>` |
| `Map` / `Set` in `deepSignal` | Reactive | Untracked; use `deepCollectionSignal` |
| Plugin `reactCompiler` default | `"auto"` | `"opt-out"` |
| Non-signal passed to `useSignalValue` | Subscribed through an effect | Throws a `TypeError` |
| Plugin exports | Included internal helpers (`pluginName`, `canTransform`, ...) | The documented API only |
| Plugin `include` / `exclude` | A predicate | A predicate, a `RegExp`, or an array of them |

## Install one copy of the package

v0.3 let several loaded copies of `react-fine-grained-signals` exchange reactive reads through a shared protocol. v0.4 removes that protocol, which makes every signal read cheaper and the core smaller (`signal` alone is about 1.7 kB gzip smaller).

Each copy now keeps its own graph, so a second copy is an error rather than a silently stale value:

- Reading another copy's signal from inside an `effect`, a `computed`, or a tracked component throws `Multiple copies of react-fine-grained-signals are loaded; install a single copy`.
- `isSignal` throws for a signal that another copy created.
- A plain read made outside any `effect`, `computed`, or tracked component cannot be detected: it returns the current value and updates nothing.

Remove the duplicate from the install. Run your package manager's dedupe (`pnpm dedupe`, `npm dedupe`), or make the bundler resolve one copy (Vite: `resolve.dedupe: ["react-fine-grained-signals"]`; Rollup: the `dedupe` option of `@rollup/plugin-node-resolve`). A package that ships its own stores should declare the library as a peer dependency. Detection covers v0.4 and later copies only: v0.4 changed the brand and shared-context keys, so a v0.1 to v0.3 copy next to v0.4 is not detected and stays unsupported.

## Entry points

The root no longer exports `createElement`, and the JSX runtimes moved under `/jsx`. The old entries are removed without aliases, so a stale import fails to resolve.

| Before | After |
| --- | --- |
| `react-fine-grained-signals` (`createElement`) | `react-fine-grained-signals/jsx` |
| `react-fine-grained-signals/jsx-runtime` | `react-fine-grained-signals/jsx/jsx-runtime` |
| `react-fine-grained-signals/jsx-dev-runtime` | `react-fine-grained-signals/jsx/jsx-dev-runtime` |
| `react-fine-grained-signals/lite` | `react-fine-grained-signals/jsx/lite` |
| `react-fine-grained-signals/lite/jsx-runtime` | `react-fine-grained-signals/jsx/lite/jsx-runtime` |
| `react-fine-grained-signals/lite/jsx-dev-runtime` | `react-fine-grained-signals/jsx/lite/jsx-dev-runtime` |
| `react-fine-grained-signals/runtime` | `react-fine-grained-signals/internal` |

`/utils` is unchanged. In practice you change the JSX import source wherever you set it:

```json
{ "compilerOptions": { "jsx": "react-jsx", "jsxImportSource": "react-fine-grained-signals/jsx" } }
```

```tsx
/** @jsxImportSource react-fine-grained-signals/jsx */
```

Use `react-fine-grained-signals/jsx/lite` for the Lite runtime. The same applies to the Vite `react({ jsxImportSource })` option and to bundler aliases. Both JSX entries now export `createElement`, `Fragment`, the `JSX` namespace, and the `SignalChild` type.

`/internal` holds what the build plugin's generated code imports (`useSignalCapture`). It is not public API and is outside semver. If you pass a custom `importSource` wrapper to the plugin, it must re-export `useSignalCapture` from its `/internal` entry (it used to be `/runtime`). Use the plugin at the same release line as the runtime.

## `useManagedSignals` is removed

`useSignalTracking()` is now the only tracking boundary you write yourself. `useManagedSignals` and `ManagedSignalsStore` are gone from the package entries, and the plugin no longer recognizes a hand-written `useManagedSignals()` boundary. Replace a `try` / `finally` boundary with one of:

- the build plugin with `transform: "managed"` (the default), which captures statically proven synchronous reads;
- the leaf hooks `useSignalValue` and `useComputed`;
- `useSignalTracking()`, with the best-effort limits in the [hooks guide](../guides/hooks.md#tracking-boundary). With React Compiler in the build, a hand-written `useSignalTracking()` component needs `"use no memo"`.

## Hook dependency arrays

Omitting `dependencies` now means `[]` in `useComputed`, `useDeepSignalValue` and `useSignalEffect` alike. Switching between omitted and `[]` is no longer an error. A length change still throws, and switching between omitted (or `[]`) and a non-empty array is now reported as a length change. The `UseComputedModeChangeError` and `UseDeepSignalValueModeChangeError` errors are gone.

`useComputed({ get, set })` moves to `useWritableComputed({ get, set }, deps?)`. `useComputed` accepts a getter only in its types, so the runtime read-only/writable capability check (`UseComputedCapabilityChangeError`) is no longer needed and was removed; plain JavaScript that still passes `{ get, set }` gets a writable computed without an error. A fixed-length violation of `useWritableComputed` throws `UseWritableComputedDependencyLengthChangeError`. The primitive `computed({ get, set })` is unchanged.

All four Hooks (`useComputed`, `useWritableComputed`, `useDeepSignalValue`, `useSignalEffect`) now report a length change with the same message, `<hook>: dependencies length changed from N to M; keep the array the same length on every render.` The `error.name` of each is unchanged; update a test that matched the old message text.

## `useSignalValue` accepts this package's signals only

`useSignalValue` used to subscribe to any object with a `value` property through an effect. It now throws a `TypeError` during render for anything that is not a signal or computed created by this package (a plain `{ value, peek }` object, a primitive, `null`). The types already rejected these values, so only plain JavaScript or code with a cast is affected. Wrap such a value in `computed(() => source.value)` if it is backed by signals, or read it with React state. The JSX bindings dropped the same fallback.

## Plugin option `reactCompiler: "auto"` is renamed

The value that adds `"use no memo"` to every transformed function is now `"opt-out"`. The behavior is the same; the old name suggested the plugin detected React Compiler, which it never did. It is still the default, so only a config that spelled out `reactCompiler: "auto"` changes: write `"opt-out"` or drop the option. Any value other than `"opt-out"` or `"off"` now throws when the plugin is created, with a message that names the rename for `"auto"`.

## Plugin exports and filters

Every plugin entry (the root, `/vite`, `/rollup`, `/webpack`, `/rspack`, `/esbuild`) now exports only the documented API: the default plugin factory, `reactFineGrainedSignals`, `REACT_FINE_GRAINED_SIGNALS_DIAGNOSTIC_IDS`, the option types, and the entry's own plugin type (for example `VitePlugin`). `pluginName`, `canTransform`, `resolveEsbuildLoader`, `createBundlerPlugin`, `EsbuildLoaderName` and `BundlerTransformOutput` were internal and are no longer exported; if you used `pluginName`, write the string `"unplugin-react-fine-grained-signals"`.

`include` and `exclude` now also accept a `RegExp` or an array of predicates and `RegExp`s (an array matches when any element matches); the new `ReactFineGrainedSignalsFilterPattern` type describes them. A predicate works as before. Strings and globs are not supported and throw when the plugin is created; use a `RegExp`. An empty `include: []` matches no module, unlike Rollup's `createFilter`, where it means no restriction.

## React 19.3

The peer dependency is `react >=19.3.0`. React 19.3 fixed `useSyncExternalStore` missing store changes made while an `<Activity>` is hidden, and the library's tests assume that behavior. React 19.0 to 19.2 are no longer supported.

## TypeScript changes

- **`Signal` and `ReadonlySignal` are nominal.** An object with only `value` and `peek()` is not a `ReadonlySignal`, matching `isSignal`. A structural readable is also rejected by `useSignalValue` at runtime (see above). `ReadonlySignal<T>` stays covariant in `T`.
- **`Signal<T>` is invariant in `T`.** A `Signal<"a" | "b">` cannot be passed where `Signal<string>` is expected. Option-based bindings (radio, select, checkbox group) still accept a literal-union signal.
- **`FormBindableSignal` is removed** without an alias. Replace it with `Signal`. `signal()`, `useSignal()`, `useWritableComputed()` and `computed({ get, set })` return `Signal<T>`, so annotating a variable as `Signal<T>` no longer erases the binding capability.
- **`Show` and `Match`** pass `Truthy<T>` to a function child. `Truthy<T>` removes `null`, `undefined`, `false`, `0`, `""` and `0n` from `T` (it is exported from `/utils`). The exported `MatchProps` type is removed (it was a props type for `Match`, which `Match`'s overloads already describe); type a `Match` element through `Match` itself.
- **`deepSignal(...).peek()` returns `DeepReadonly<T>`.** Object properties are `readonly`, arrays are `ReadonlyArray`, `Map` and `Set` become `ReadonlyMap` and `ReadonlySet`, and `WeakMap` and `WeakSet` lose `set`, `add` and `delete`. Writing through `peek()` is a compile error; change state through `.value`. At runtime `peek()` still returns the raw object.
- **`DeepSignal<T>` is never a `Signal<T>`.** Code that passed one where a `Signal<T>` was expected (a binding, a writable parameter) needs to read and write through `.value`. For reading it still counts as a `ReadonlySignal<T>` when `T` has no arrays or collections to make `DeepReadonly<T>` differ from `T`. The `For`, `Index`, `Show` and `Match` inputs accept a deep signal directly and type the item by its `.value` type, so a row can write `item.done = true`.

## Collections moved to `deepCollectionSignal`

`deepSignal` now tracks plain objects and arrays only, so an app that never stores a `Map` or `Set` no longer loads the collection support (`deepSignal` and its hooks go from 14.59 to 10.33 kB gzip together with the interop removal). If you store `Map`, `Set`, `WeakMap` or `WeakSet` values in a deep signal, switch to `deepCollectionSignal` (and `useDeepCollectionSignal`):

```ts
import { deepCollectionSignal } from "react-fine-grained-signals";

const state = deepCollectionSignal({ tags: new Set<string>(), counts: new Map<string, number>() });
state.value.tags.add("react");
```

What changes in `deepSignal`:

- A `Map`, `Set`, `WeakMap` or `WeakSet` root is a type error and throws a `TypeError` that points to `deepCollectionSignal`.
- A nested collection is an untracked value, like a `Date`. It keeps its identity, and the signal notifies only when the property holding it is assigned a different value. `state.value.tags.add(x)` is **not** notified, and its type still allows the call, so search for these mutations when you upgrade.
- A plain object or array cannot be shared between a `deepSignal` and a `deepCollectionSignal`: wrapping the same raw object with both, or assigning a proxy from one into the other, throws.

`useDeepSignalValue` accepts either kind. `DeepCollectionSignal<T>` and `DeepSignal<T>` are separate types.

## Consistency fixes before the release

Several functions did the same job by slightly different rules. Each now shares one implementation, and the shared rule is the one below.

**JSX runtimes**

- Full and Lite apply one Signal-prop rule. On a custom element (a tag name containing `-`), a Signal passed to a prop outside the direct-binding list reaches the element unchanged, `value` and `checked` included. Before, Full threw for those two and Lite threw for every Signal prop. Lite still throws where Full binds: `title`, `id`, `className`, `hidden`, `disabled`, `style`, `aria-*`, `data-*`, and Signal entries of a style object.
- Lite treats `bindValue={undefined}` and `bindChecked={undefined}` as absent and keeps them off the DOM, as Full does. Its error messages now name the tag.

**Hooks and deep state**

- `useDeepSignalValue` checks its source like `useSignalValue`: anything that is not a `deepSignal` or `deepCollectionSignal` throws a `TypeError` during render, a plain `signal()` or `computed()` holding an object included (it would follow root replacement only; the types already rejected it). Its selector no longer subscribes an effect that renders synchronously, for example through `flushSync` inside `useSignalEffect`.
- Errors from `deepCollectionSignal` state start with `deepCollectionSignal()`, plain objects inside it included; they used to say `deepSignal()`. Update a test that matched the full text.
- In `deepSignal`, a deep proxy inside a collection from another realm is now rejected, as one inside a local `Map` already was. Do not store a collection whose prototype was replaced. Set to `null` or `Object.prototype`, it counts as a plain object (its entries are not visible); set to another object, it counts as an opaque value whose entries are not checked. Detecting these would slow down storing every empty `Object.create(null)` dictionary, Date and class instance.
- `includes`, `indexOf` and `lastIndexOf` on a deep array find a stored object that holds a deep proxy (`{ inner: state.value.inner }`), as `Set.has` already did.
- A throwing listener of a `useSignalTracking()` component's store is reported as a listener failure and no longer stops the listeners after it.

**Plugin**

- Every option is validated when the plugin is created (for webpack and rspack, at `apply()`): an unknown `mode` or `transform` value, an `importSource` or `reactImportSource` that is not a non-empty string, and a `diagnostics.errorOn` that is not an array throw a `TypeError`. `mode` is case-sensitive; `"Auto"` names `"auto"` in the message.
- Diagnostics start with `[unplugin-react-fine-grained-signals] RFGSxxx:` (was `[react-fine-grained-signals]`), and parse and analysis failures with `[unplugin-react-fine-grained-signals] could not ...`.
- In `mode: "auto"` and `"all"`, a component or custom Hook whose only `.value` read is inside a function passed to a Hook (`useSignalEffect`, `useComputed`, `useSyncExternalStore`, `use`, any `useX`) is no longer transformed. Before, that applied to five React Hooks only. With `transform: "inject"`, a custom Hook that calls such a callback synchronously during render loses the boundary the plugin added; read through `useSignalValue` or add `useSignalTracking()`.
- RFGS003 follows the runtime: a `Match` inside a `Switch` through a fragment, an array or a condition no longer warns; an orphan `Match` passed as `children=` now warns; callbacks wrapped in a TypeScript assertion are checked; an async or generator callback warns only when it reads a signal, so a React 19 `<form action={async () => ...}>` no longer warns.
- RFGS004 no longer warns for `ref.current.value` or `event.target.value` in a parameter default.
- Reads inside an async function never become render dependencies, those before the first `await` included, whether the function is inline, named, an IIFE or a render callback, and running one no longer makes the call that runs it captured. Before, the plugin chose a component by one rule and captured by the other. Read the value synchronously in render, or with `useSignalValue`, if the component must re-render.
- Auto mode selects a component or custom Hook exactly when the managed pass would capture one of its render reads. No longer selected: one whose only reads are in a local function or method it never calls, a handler kept in a variable, a generator it never iterates, a returned closure, a Hook's callback, `untracked(...)`, or a timer or Promise callback (`setTimeout`, `queueMicrotask`, `requestAnimationFrame`, `then`, ...). In managed mode this only drops a `useSignalCapture()` and `"use no memo"` that captured nothing; with `transform: "inject"` the added `useSignalTracking()` disappears too, so read such values with `useSignalValue` or add `useSignalTracking()` yourself. Newly followed, so now selected: `.call`/`.apply`, local template tags, a named `new Promise(executor)`, `for...of` over a local generator, and closures called through an array index, a key, a condition or an object passed to a call. `.peek()` on a library signal and `untracked(...)` are no longer captured.
- More reads are captured, so some components that showed stale values now re-render: an optional chain is captured as a whole (`props.todos?.filter(...).length` no longer throws when `todos` is missing); a JSX member tag (`<theme.value.Icon />`); the object written to in `st.value.a = 2`; names bound by a destructuring assignment (`({ user } = state.value)`) or an assignment-form loop head (`for ({ row } of list.value)`); and property reads on a conditional, logical, array or object expression that holds a deep-signal value (`(flag ? user : fallback).name`). Instance field initializers of a class declared in a component are no longer counted as render reads, since they run only on `new`.
- The plugin treats a name as a Hook by React's rule, `use` followed by an uppercase letter or a digit (`use3D`), and never moves a Hook into a capture: one in a destructuring default, a `new` argument, a spread or an `in`/coercion operand is reported as RFGS001 instead. RFGS009 is reported for components only (not for lowercase server actions), and each diagnostic is reported once per source location.
- A parameter default that may read a signal through a call (a same-module helper, an inline callback, an imported function) is now moved into the body like a direct `.value` read, so it is captured; the parameter is renamed `_param` in the output. RFGS004 reports such a default only when moving it would change its meaning, and its message now says "a .value read, or a call that may make one".
- `.mjsx` and `.mtsx` files are no longer transformed: no tool gives these extensions a meaning, and esbuild had no loader for them. The claimed extensions are `.js .mjs .jsx .ts .mts .tsx`.
- React imports by string name (`import { "memo" as m }`, `"Fragment"`) are recognized.
- A custom `importSource` wrapper must also provide `${importSource}/utils` (re-exporting `Show`, `Switch`, `Match`, `For` and `Index`); otherwise their callbacks get RFGS003.
- Output fixes: with `reactImportSource` set, calls to functions imported directly from `"react"` are no longer wrapped in `capture()`; `(s.value satisfies T) = v` no longer produces invalid code; a wrapped `++` or `+=` is captured with valid parentheses; a helper that calls `use()` is no longer wrapped in `capture()`.

## Checklist

1. Install one copy of the library; run your package manager's dedupe.
2. Update every `jsxImportSource`, pragma, and bundler alias to the `/jsx` entries.
3. Replace `useManagedSignals` boundaries; replace `useComputed({ get, set })` with `useWritableComputed`.
4. Move `Map` / `Set` state to `deepCollectionSignal`, and look for mutations of nested collections inside `deepSignal`.
5. Replace `FormBindableSignal` with `Signal`, and fix `Signal<T>` assignments that relied on covariance.
6. Raise React to 19.3 or newer.
7. Upgrade the plugin to the same `0.4.x`, and change `reactCompiler: "auto"` to `"opt-out"` if you set it. Replace imports of `pluginName` or other internal plugin helpers.
8. Check that every `useSignalValue` and `useDeepSignalValue` call receives a signal from this package.
9. Check the plugin options against their documented values, and update tests that match diagnostic or deep-state message text.
