# Transform toolchain alternatives: oxc and swc

[English](transform-toolchain-alternatives.md) | [日本語](transform-toolchain-alternatives.ja.md)

Status: design investigation; no API or implementation decision has been made.

## Context

The `useSignals()` auto-injection transform lives in `packages/unplugin-react-fine-grained-signals/src/internal/transform.ts` as a Babel plugin. It is not wired up as a bundler-specific Babel plugin config entry: `transformReactFineGrainedSignals(code, id, options)` is a standalone Node function that calls `@babel/core`'s `transformSync()` directly on an arbitrary source string and returns `{ code, map }` (or `null` when nothing in the file needed transforming). The `unplugin` wrapper (`src/unplugin.ts`) exposes this same function uniformly to Vite, Rollup, Webpack, Rspack, and esbuild through thin adapters (`src/vite.ts`, `src/rollup.ts`, `src/webpack.ts`, `src/rspack.ts`, `src/esbuild.ts`) — including the esbuild adapter, which calls this Node function from inside unplugin's own `onLoad`/`transform` hook rather than through any plugin mechanism native to esbuild's Go pipeline. This bundler-agnostic design works because Babel exposes a synchronous "parse a string, run my plugin, print the string back with a source map" API that this project calls from plain Node code, decoupled from any specific bundler's plugin host; that is a property of how this project uses Babel, not something only Babel's plugin model could provide, and any alternative toolchain has to be evaluated against whether it can preserve that same property, not only against raw transform speed.

The plugin logic itself is non-trivial and leans on several Babel-specific capabilities: parsing TS/TSX/JS/JSX with legacy decorators; custom traversal control flow that walks every `Function` node and selectively calls `path.skip()` to stop descending into nested components or hooks that own their own subscription while still traversing into ordinary callbacks such as `.map()` render props (`isNestedTrackingBoundary`, `inspectFunction`); real scope and binding resolution via `functionPath.scope.getBinding(name)` to confirm a called `useSignals` identifier actually resolves to an import specifier rather than a shadowed local, including through renamed (`import { useSignals as x }`) and namespace (`import * as X; X.useSignals()`) imports (`isNamedUseSignalsImport`, `isNamespaceUseSignalsImport`); leading-comment matching (`@useSignals`, `@noUseSignals`) that walks up through `export const Foo = ...` wrappers to find comments attached to the export declaration rather than only the function (`hasOwnedLeadingComment`); AST mutation that inserts deduplicated import specifiers with a collision-safe generated local name (`scope.generateUidIdentifier`), wraps bodies in `try { ... } finally { store.f() }`, and calls `path.scope.crawl()` mid-pass to keep scope information valid for the rest of that visitor run; and source map emission alongside the transformed code.

`oxc` and `swc` are both marketed as substantially faster than Babel for parsing, transforming, and printing JavaScript and TypeScript. This document investigates whether either could replace Babel here. An existing micro-benchmark harness at `packages/unplugin-react-fine-grained-signals/benchmarks/transform.mjs` (invoked via `pnpm bench:transform`) already measures per-file transform latency across small and large source variants, comparing transform-candidate against non-candidate sources; non-candidate sources are measured under `transform: "inject"` only, while candidate sources are measured under both `transform: "inject"` and `transform: "managed"`. Any future toolchain comparison should extend this harness rather than inventing a new methodology.

## Prior art

Vite 8, which this repository depends on (`^8.2.2`), replaced esbuild and Rollup internals with Rolldown, whose Rust toolchain is oxc-based rather than swc-based. SWC is therefore not implicitly present anywhere in this project's current toolchain; if anything, oxc is the more "already adjacent" of the two, and the project also already depends on `oxlint`, oxc's linter, for `pnpm lint`. Neither adjacency implies a usable transform-authoring path, which is the subject of the two findings below.

`@preact/signals-react-transform` is the closest analog to this project's plugin: a scope-aware, comment-influenced Babel transform that wraps opted-in components in a `try`/`finally` store boundary. No official swc or oxc equivalent exists from the Preact team; Babel remains canonical there. A community effort, `@preact-signals/safe-react`, has pursued a Rust SWC plugin for the equivalent transform since December 2023 (tracked from issue #43) and has a multi-year history that includes SWC-path-specific correctness bugs being reported and fixed along the way — for example, a hooks-misbehavior report (issue #184) closed as completed in September 2024; the repository currently has no open issues tagged `swc`. Valtio ships a community SWC plugin, but for a materially simpler transform with no scope-aware component detection. styled-components, emotion, and Relay do have official SWC plugins; Next.js's own tracking explicitly frames this work as porting (for example, "Port babel-plugin-styled-components to SWC"), and `@swc/plugin-styled-components` is documented as the SWC equivalent of `babel-plugin-styled-components`'s behavior — but the plugins themselves are still ground-up Rust code, not a mechanical or tool-assisted translation of the Babel plugins' source, built with Vercel/Next.js engineering resources (`swc-project/plugins`) not comparable in scale to this project's. No migration precedent was found, in either direction, for any comparable scope-aware Babel plugin — checked across Preact Signals, MobX, Legend-State, Valtio, styled-components, and emotion — moving to oxc; though oxc's own fixed built-in pipeline (`oxc-transform`) already ships its own styled-components support, built in-tree independently of styled-components' own maintainers, so that absence is narrower than it first appears.

oxc itself now hosts one project of comparable sophistication to what this plugin would need: `oxc-transform-react`, an automatic-memoization pass equivalent to React Compiler's (shipped August 2026), claimed to run more than ten times faster than `babel-plugin-react-compiler`. Per oxc's own August 18, 2026 announcement, the underlying Rust port is not oxc-original: the React team built it first, oxc consumed it as a synchronized fork (`forked-react-compiler`), and then vendored it in-tree as `oxc_react_compiler`, completing the pieces the fork had left unfinished and improving its performance further. It is still first-party work living inside oxc rather than a userland plugin-authorship path, and oxc completing and optimizing it in-tree is still evidence that oxc's Rust-level traversal and semantic-analysis crates can host logic at this level of sophistication — but the architecture and the bulk of the original implementation are the React team's, not an oxc-original design from scratch. A community Rust-and-napi port of React Compiler for oxc, `eve0415/oxc-plugin-react-compiler`, existed separately and was archived once the official (React-team-originated, oxc-vendored) port superseded it — a real precedent for the Rust-plus-napi packaging path, though not one that is currently maintained.

## Goals for a future decision

- Preserve full correctness against the plugin's existing behavior: scope/binding-aware `useSignals` detection, nested-boundary skip logic, comment-directive handling, and wrapper detection for `memo`/`forwardRef`.
- Preserve the bundler-agnostic architecture: identical transform behavior reachable from Vite, Rollup, Webpack, Rspack, and esbuild through a single Node-callable function.
- Base any migration decision on a reproducible, apples-to-apples performance comparison specific to this plugin's logic, not on general-purpose benchmark claims for a toolchain's built-in transforms.
- Make the packaging, release, and maintenance burden of any alternative explicit before adopting it.

## Non-goals

- Choosing a replacement toolchain in this document. No implementation has been attempted for either alternative.
- Adopting general "N times faster than Babel" figures published by oxc or swc as evidence for this specific, custom, scope-aware transform, which those figures do not measure.
- Rewriting the transform for reasons other than measured performance need — for example, to adopt a toolchain for its own sake.

## Options to evaluate

### 1. Keep Babel (status quo)

Continue running the existing `@babel/core`-based plugin unchanged.

Advantages: no rewrite risk; full access to Babel's mature scope/binding API and comment-attached AST, both of which the plugin currently depends on directly; a proven bundler-agnostic `transformSync` design already in production across five bundler adapters. Disadvantages: Babel's raw parse/print performance is slower than oxc's or swc's built-in transforms; however, this project's own transform benchmark (`benchmarks/transform.mjs`) has not yet established whether that gap is actually significant relative to overall bundler or dev-server overhead at this project's typical file sizes, so the disadvantage is currently unquantified rather than demonstrated.

### 2. Rust-authored oxc integration

Reimplement the plugin's logic using oxc's Rust crates — `oxc_traverse` for traversal control and `oxc_semantic` for scope and binding resolution (`SymbolId`, `ReferenceId`, `Scoping`) — packaged as a napi addon that exposes the same `transformReactFineGrainedSignals(code, id, options) -> { code, map }` Node function signature, so the bundler-agnostic architecture is preserved at the call site.

Advantages: a potentially large raw transform speed gain if oxc's built-in-transform performance numbers generalize to this custom visitor; a napi addon is called the same way from Node regardless of bundler, unlike the WASM-plugin-hosted model swc's ecosystem uses. Disadvantages: this is a full reimplementation, not a port, of every scope-aware and comment-driven piece of logic, against Rust APIs the project has no current experience with; it requires a cross-platform napi build-and-release matrix (Windows/macOS/Linux, x64/arm64, plus musl) the project does not currently maintain; oxc-parser's comment handling returns a raw `comments[]` array not attached to AST nodes, a gap tracked upstream as oxc issue #19671, which is a direct, currently-unresolved risk to the `@useSignals`/`@noUseSignals` comment-directive mechanism; and while `eve0415/oxc-plugin-react-compiler` (see Prior art) shows a comparably sophisticated Rust-plus-napi plugin is achievable, there is no currently-maintained precedent for one shipped this way — that project was archived once superseded by an official port, not abandoned for being unworkable.

### 3. Rust-authored swc WASM plugin

Reimplement the plugin as a `VisitMut` implementation compiled to `wasm32-wasip1`, self-host a pinned `@swc/core` inside this project, and call `@swc/core`'s own `transformSync()` — passing the compiled WASM plugin's path via `jsc.experimental.plugins` — from the same shared Node function that all five bundler adapters already call into for the Babel path, using `swc_ecma_transforms_base::resolver`'s `SyntaxContext`/`Mark` hygiene model in place of Babel's `scope.getBinding()` for identifier resolution.

Advantages: `@swc/core.transformSync()` is a plain Node-callable function in the same shape as Babel's `transformSync()` — this is how community swc plugins are normally consumed (for example `swc-plugin-valtio`'s documented install path, or `@swc/jest` hosting a plugin from Node) — so calling it from inside the shared `transformReactFineGrainedSignals`-equivalent function needs no swc-integrated bundler tool (Next.js's compiler, `@vitejs/plugin-react-swc`, Rspack's swc-loader) and does not depend on esbuild having its own swc plugin hook, since the esbuild adapter never runs inside esbuild's own Go pipeline in the first place — it already calls this shared Node function from unplugin's `onLoad`/`transform` hook, exactly as it does for Babel today. The bundler-agnostic architecture is therefore not structurally lost by choosing swc; SWC's `SyntaxContext`/`Mark` model is also conceptually capable of expressing the same renamed- and namespace-import resolution guarantees the plugin currently gets from Babel's scope object, despite being a lower-level API. Disadvantages: `@swc/core`'s JS-facing `Visitor` class is deprecated and scheduled for removal — SWC's own RFC states JS-visitor support is "not in the current roadmap," `@swc/core` 1.x already emits deprecation warnings, and 2.x will remove both the plugin config option and `@swc/core/visitor` — so a Rust-authored WASM plugin is mandatory, not merely preferred: this is a full reimplementation of every scope-aware and comment-driven piece of logic against `SyntaxContext`/`Mark` semantics, not a JS-authorable port; it requires a `wasm32-wasip1` build-and-release pipeline the project does not currently maintain; even self-hosting a pinned `@swc/core` reduces but does not eliminate version-lock risk, because the plugin's compile-time `swc_core` version must still track whatever `@swc/core` version this project upgrades to over time, and the backward-compatible CBOR serialization `@swc/core` >=1.15.0 / Next.js >=16.1.0 gained on November 4, 2025 explicitly does not cover field deletions or type changes and follows a documented history of real crashes from `swc_core` version mismatches (`swc-project/swc` issue #8315) — so future `@swc/core` upgrades remain a live, if now narrower, compatibility risk; and no comparably sophisticated scope-aware, comment-directive-driven, auto-injecting plugin has a track record of shipping stably on this path — the closest analog, `@preact-signals/safe-react`, is a multi-year community effort with a history of SWC-path-specific correctness bugs being reported and fixed, not an example of the path being mature and low-risk.

### 4. Hybrid: fast parse via oxc or swc, Babel-compatible AST bridge for the existing plugin logic

Investigate whether a faster parser's output could be converted into a Babel-compatible AST and scope graph, so the existing plugin logic runs unmodified on top of a faster front end.

Advantages: could isolate speed gains to parsing and printing, which is often the bulk of transform cost, without reimplementing the plugin's traversal, scope-resolution, or comment-matching logic. Disadvantages: no such bridge is known to exist for either toolchain today — Babel's AST and scope model differ from oxc's and swc's enough that a faithful bridge is itself a nontrivial, unproven engineering effort; it would need prototyping and correctness validation before it could even be evaluated against the other options; and it may not end up materially simpler than a from-scratch reimplementation once semantic-preserving translation between AST and scope models is accounted for.

### 5. Do nothing until the current transform is actually measured as a bottleneck

Extend `benchmarks/transform.mjs`, or add a comparable harness, to establish real per-file and per-project transform time under this project's typical file sizes and usage patterns, and compare that against overall dev-server and build time, before deciding whether a toolchain change is justified at all.

Advantages: the cheapest option; avoids speculative rewrite cost; produces the evidence needed to make any of the other options credible. Disadvantages: defers the question rather than answering it — this is offered as a prerequisite step alongside the other options, not a competing end state.

## Decision criteria

- Correctness parity with the full existing `tests/transform.test.ts` suite (modes `manual`/`auto`/`all`, transform kinds `inject`/`managed`, comment annotations, nested-boundary skip logic, `memo`/`forwardRef` wrapper detection, renamed/namespace import resolution, TS+JSX+decorators parsing) before any toolchain is treated as a drop-in replacement.
- A measured, reproducible before/after comparison using an extended `benchmarks/transform.mjs`-style harness, covering both small and large files and both transform-candidate and non-candidate sources, run on the same hardware.
- Whether the bundler-agnostic architecture (identical behavior across Vite, Rollup, Webpack, Rspack, and esbuild through one Node function) is preserved or narrowed.
- Packaging and release burden: whether the option requires a new native, napi, or WASM build-and-publish pipeline the project doesn't currently maintain, and which platforms and architectures it must cover.
- Long-term maintainability given the project's current skill set (TypeScript-authored) versus a Rust-authored path, including realistic bus-factor and onboarding cost for contributors.
- Ecosystem and version-lock stability, informed by the documented swc WASM ABI breakage history and the relative immaturity of oxc's JS-facing plugin surfaces.

## Current recommendation

Stay on Babel for now. Neither oxc nor swc currently offers a JS/TS-authorable path for this plugin's logic; both would require a from-scratch Rust reimplementation. oxc has no mechanism today for exposing arbitrary custom transform logic to Node at all — `oxc-parser` exposes no scope/binding API and has an open comment-attachment gap, and `oxc-transform` exposes only its fixed built-in pipeline. swc's Rust WASM path can preserve the bundler-agnostic architecture, by calling a self-hosted `@swc/core.transformSync()` from the same shared Node function the Babel path uses today, but it still forces a full Rust reimplementation against `SyntaxContext`/`Mark` semantics (the JS-facing `Visitor` API is deprecated and being removed in 2.x), demands a `wasm32-wasip1` build-and-release pipeline the project doesn't have, and carries version-lock risk the November 2025 ABI stability fix narrows but does not remove, since that fix does not cover field deletions or type changes. Neither Rust path has a stable precedent for a plugin this sophisticated: oxc's own comparable effort (`oxc-transform-react`) is the React team's ported and in-tree-vendored work rather than a userland-authorable pattern, and swc's closest analog (`@preact-signals/safe-react`) remains a multi-year community effort. Before revisiting this question, the transform should be measured (per option 5 above) to establish whether Babel's overhead is actually significant relative to overall build and dev-server time for this project's typical usage. This statement records the current findings; it does not close the design question or commit to Babel indefinitely.
